# 출제기준

새 생성 엔진(`src/lib/study/gen/`)이 **학습 설계**와 **출제** 때 읽는 판단 기준이다. 코드를 고치지 않고 이 폴더만 고쳐서 문제 품질을 올리는 것이 목적이다.

- 코드에 남는 것: 출력 형식(JSON 칸의 뜻), 분류 단계 기준, 검사.
- 이 폴더에 있는 것: 무엇을 목표로 고르고, 어떤 문제를 어떻게 내는지에 대한 판단.

## 무엇이 어느 호출에 들어가나
| 파일 | 학습 설계 | 출제 |
|---|---|---|
| `공통.md` | 전부 | 전부 |
| `목표설계.md` | `## 원칙` + 고른 목적의 `## 목적: …` 절 | - |
| `출제/원칙.md` | - | 전부 |
| `출제/형식.md` | - | 전부(세 형식) |
| `출제/목적.md` | - | 고른 목적의 절 |
| `출제/종류.md` | - | 그 목차 목표들의 종류 절만 |
| `예시/좋은예.md`, `예시/나쁜예.md` | - | 전부 |

- `README.md`, `변경기록.md`, `개선후보.md`는 모델에 들어가지 않는다.
- 엔진은 넣은 파일과 내용 해시(**기준 버전**)를 호출 기록마다 남긴다. 실험실 호출 표의 "기준" 칸에서 볼 수 있다.
- 절 제목(`## 목적: 핵심 암기`, `## 종류: 공식`)은 엔진이 찾는 열쇠다. 바꾸면 그 절이 빠진다. 테스트가 이를 잡는다.

## 규칙 쓰는 법
- **한 줄에 규칙 하나**, 앞에 ID(`[출제-3]`)를 붙인다. ID는 지우지 않고, 없앤 규칙의 번호는 다시 쓰지 않는다. 보고서·변경기록·나쁜 예가 ID로 규칙을 가리킨다.
- **관찰된 실패에 근거해서만** 규칙을 더한다. 근거 사례는 `변경기록.md`에 적는다.
- 규칙보다 **예시가 강하다.** 좋은 예와 나쁜 예는 "무엇이 좋았나/틀렸나 → 어느 규칙" 한 줄로 쓴다.
- **평가 자료의 문제는 예시로 쓰지 않는다.** 그 자료에서 점수가 오르는 것이 실력인지 암기인지 구분할 수 없게 된다.
- **크기 예산**: 한 호출에 들어가는 기준은 출제 6,000자, 학습 설계 3,000자 이하로 둔다(테스트가 검사). 늘리고 싶으면 합치거나 뺄 규칙부터 찾는다. 길이보다 서로 부딪치는 규칙이 성능을 더 떨어뜨린다.

## 개선 회차 (특정 시점에 한 번씩)
신고가 몇 개 쌓였을 때, 또는 큰 변경 뒤에 돌린다.

1. **재료 모으기**: `개선후보.md`에 보인 문제를 쌓는다. 출처는 실험실 실측, 결과보고, 사용자의 신고·다시 만들기, 자기 확인에서 반복해서 틀리는 문제다. 항목마다 실행 ID와 문제 번호를 적는다.
2. **고칠 것 고르기**: 같은 원인으로 묶이고 두 번 이상 보인 것부터 고른다. 한 회차에 2~4개로 제한한다. 많이 바꾸면 무엇이 효과였는지 모른다.
3. **후보 폴더에서 고치기**: `출제기준`을 `출제기준-후보`로 복사해 고친다. 원본은 그대로 둔다.
4. **전후 비교**: 실험실 `/lab/gen`에서 같은 자료·모델로 "기준 폴더"만 `출제기준`과 `출제기준-후보`로 바꿔 각각 실행한다.
   - 평가 자료와 확인용 자료(개선에 쓰지 않은 자료) 모두에서 비교한다.
   - 볼 것은 고치려던 문제가 줄었는지, 다른 것이 나빠지지 않았는지, 호출 수·시간이다.
5. **반영**: 나아졌으면 사용자가 승인하고, 후보 내용을 `출제기준`으로 옮긴다. `변경기록.md`에 버전, 바꾼 규칙 ID, 근거, 전후 결과를 남기고 `개선후보.md`에서 해당 항목을 지운다.
