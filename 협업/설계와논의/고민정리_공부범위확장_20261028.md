# Recaller 공부 범위 넓히기: 고민 정리 (2026-10-28)

GPT에게 의견을 들어 보려고 정리한 것이다. 아직 **구상 전 단계**이고 정해진 것은 없다. "사용자"는 Recaller를 만드는 학생(개발 경험이 많지 않음), "Claude"는 함께 개발하는 AI다.

## 배경: Recaller가 지금 하는 것

- PC에서 도는 학습 앱(Next.js, 로컬). 캡스톤 졸업작품.
- 핵심 흐름: **자료 → 문제 → 결과를 지식으로 기록(만남·몰랐음·앎·졸업) → 날짜 간격 복습(상자 방식)**. 지식끼리는 고리(연결)로 이어지고, 같은 지식은 이름·임베딩·AI 판정으로 합친다.
- 공부 갈래 셋:
  - **PDF**: AI가 문제를 만들고, 맞고 틀린 결과가 지식으로 간다.
  - **웹 글**: 지식을 잡아낸다.
  - **코드(알고리즘)**: 주소나 주제를 넣으면 AI가 문제를 세팅하고, 숨은 테스트를 자동으로 만들고 스스로 검증한다. 4개 언어 로컬 채점, 힌트 3단계, 틀린 기록이 지식으로 이어진다.
- 제품 원칙: "교재를 대신 읽어 주는 AI가 아니라, 내가 직접 기억하고 쓸 수 있게 만드는 훈련". 능동 인출을 중심으로 한다.

## 고민이 시작된 곳

알고리즘 말고 **개발 기본기 전반**(웹, 백엔드, 데이터 등)도 Recaller로 공부할 수 있게 넓히면 어떨까.

## 대화 흐름

### 1. 직군별 "기본기 과제"를 뽑아 봄 (Claude)

웹 풀스택이면 "로그인되는 게시판(CRUD)을 처음부터 만들어 배포하기"가 보통 기준이다. 다른 직군도 같은 식으로 뽑았다.
- 프론트엔드: API 붙인 쇼핑몰 화면
- 백엔드: 인증·권한 있는 REST API
- 모바일: 로그인 + 목록 + 오프라인 저장 + 푸시
- 게임: 2D 플랫포머 한 판
- 데이터 엔지니어: 매일 도는 ETL 파이프라인
- 데이터 분석: 공개 데이터 분석 보고서
- ML: 학습 → 평가 → 서빙
- LLM 응용: RAG 봇 + 평가 세트
- 임베디드: 센서 읽기
- 시스템: 간단한 셸
- DevOps: 컨테이너 + CI/CD
- 보안: 취약한 웹앱 고치기
- QA: 테스트 자동화
- 그래픽스: 소프트웨어 래스터라이저
- 알고리즘: 단계별 문제 풀기

### 2. 앱에서 지원할 만한 보편적인 것 (Claude)

알고리즘(이미 있음), 웹 풀스택(게시판), 백엔드 API, 데이터 분석(SQL·pandas). 모바일·게임·임베디드는 실행 환경이 달라 뒤로 미룬다.

### 3. 실제로 어떻게 돌아가나 (Claude 구상)

- **프로젝트 = 단계 목록**: 서버 띄우기 → 회원가입 → 로그인 유지 → 글쓰기 → 내 글만 수정 → … → 배포.
- 단계마다 붙는 것
  - 알아야 할 지식(지식 카드)
  - 할 일과 완료 기준(예: "같은 이메일이면 409")
  - **자동 확인**: 앱이 사용자가 PC에서 띄운 서버에 진짜 HTTP 요청을 보내 상태 코드와 응답을 대본과 비교한다. 로컬 앱이라 가능하다. 이전 단계 검사도 다시 돌려 기능이 깨지지 않았는지 본다.
- 막히면 힌트 3단계(앱이 서버 로그와 프로젝트 파일을 직접 본다), 통과 뒤 AI 코드 리뷰(보안·설계 조언, 판정은 아님).
- 틀린 것과 지적받은 것은 지식으로 기록 → 복습.
- 데이터 분석은 작은 SQLite DB에 쿼리를 실행해 결과 표를 비교한다(지금 채점기와 비슷).

### 4. 편집기: 내장 vs 외장

- 내장: 지금 코드 탭에 Monaco가 있다. 여러 파일, 서버 켜기·로그까지 붙이면 2~3일이 더 든다.
- **외장(VS Code)으로 가기로 생각 중**(사용자). Claude는 이렇게 연결하자고 제안했다.
  - 앱에서 [VS Code로 열기]
  - 검사 결과의 "파일:줄"을 누르면 그 줄로 이동
  - 앱이 프로젝트 폴더를 직접 읽음
  - 앱이 서버를 켜고 로그를 잡음
  - 나중에 VS Code 확장(사이드바에 단계·검사·힌트)
- Cursor는 VS Code를 바탕으로 만들어서 대부분 같이 된다.

### 5. 사용자의 방향 전환 (중요)

> "처음부터 끝까지 다 짜는 건 좋은데, 그 시절 그게 화두이던 사람들이 열정적으로 판 것처럼 팔 필요는 없다고 생각해. 내가 원하는 건 현시대의 AI 기술을 활용해서 효율적으로 공부하는 거야."

> "결과물은 프로젝트가 아니라 머리에 남아야 함. 프로젝트를 하며 기본기가 쌓이는 게 중요한 거임. 프로젝트 만든 거 보여 주려고 만드는 게 아니라."

> "내가 그렇게 개발 실력이 좋지 않아서 내 이상의 사람이 뭘 원하는지 모름."

### 6. 사용자가 꼽은 고민 세 가지

1. 학습자가 얼마나 능동적으로 참여할 것인가
2. 어느 정도를 AI에게 맡길 것인가
3. 어느 부분을 코어로 학습시킬 것인가

### 7. Claude가 제안한 생각의 틀

**(1) 세 고민은 하나로 묶인다.** "끝났을 때 머리에 무엇이 남아야 하나"를 정하면 나머지가 따라온다.

**(2) 코어로 남길 것 vs AI에 맡길 것**
- 남길 것
  - 원리와 구조(요청 흐름, 상태가 어디 있나)
  - 판단(세션 vs JWT, 테이블 구조)
  - AI가 자주 틀리는 곳(권한·보안·동시성·경계 조건)
  - 검증과 디버깅
- 맡길 것: 문법 세부, 라이브러리 이름, 반복되는 틀 코드, 설정, 배포 명령어
- 기준 질문: **"AI가 틀렸을 때, 이걸 모르면 알아챌 수 있나?"** 못 알아챈다면 코어다.

**(3) 참여 수준의 사다리**
보기 → 예측 → 설명 → 찾기(버그) → 고치기 → 만들기. 위로 갈수록 오래 남지만 힘들다. 처음 배우는 사람은 잘 짜인 예시가 낫고, 익숙해질수록 도움을 줄이는 게 낫다(일반적으로 알려진 학습 연구 내용, 출처 확인은 안 함).

**(4) 지식 상태에 따라 AI에 맡기는 정도를 개념마다 다르게** (Recaller에 이미 지식 상태가 있어서 할 수 있음)

| 상태 | AI | 학습자 |
|---|---|---|
| 처음(만남) | 짜고 설명 | 보고 예측 |
| 몰랐음 | 짜되 일부를 비우거나 버그를 심음 | 설명·찾기·고치기 |
| 앎 | 틀만 | 핵심을 직접, 또는 AI에 정확히 지시 |
| 졸업 | 전부 | 검사만 |

**(5) AI 시대 활동 아이디어**
- AI로 만든 내 프로젝트를 교재로 쓴다(흐름 지도, 꼭 알아야 할 결정 5개 → 지식 카드).
- 코드를 보여 주지 않고 묻는다("로그인 상태는 어디 저장돼?").
- **버그 찾기**: 코드 문제에서 쓰는 "흔한 실수를 일부러 넣은 풀이" 기술을 프로젝트에 적용한다. 권한 검사 한 줄 빼기 같은 버그를 심고 학습자가 찾게 한 뒤, 검사기로 확인한다.
- 바꿔 보기 과제(AI를 써도 됨)를 낸 뒤 "AI가 짠 코드를 설명해 봐".
- 명세를 써서 AI에게 시키고 검증하는 연습.

### 8. 사용자의 나이브한 상상 (지금 가장 유력한 방향)

> "프로젝트를 만들 때 각 단위마다 코어 아이디어가 있을 거고, 얘가 무슨 역할을 해 준다 이런 게 있을 거고, 그런 게 모여서 프로젝트가 되는 건데, 그 코어 아이디어·역할 그런 거 단위로 보는?"

Claude는 이렇게 받았다. 경험 많은 개발자도 프로젝트를 부품과 역할로 본다. 부품 하나를 카드 한 장으로 만든다.

```
부품: 인증 검사(미들웨어)
역할: 요청이 로직에 닿기 전에 누구인지 확인, 모르면 돌려보냄
코어 아이디어: 보호된 요청은 모두 같은 문 하나를 지나게 한다
받는 것 → 내는 것: 요청 + 쿠키/토큰 → 사용자 정보 붙여 다음으로, 또는 401
이어지는 부품: 세션/토큰, 글 처리 로직
없으면?: 누구나 남의 글을 지울 수 있다
흔한 실수: 어떤 경로에 문을 안 붙임
```

- 부품별 활동: 역할 맞히기, 없애 보기(실제로 빼고 검사기를 돌림), 연결 잇기, 버그 찾기, **핵심 몇 줄만 직접**(나머지는 AI가 짠 것을 읽음)
- Recaller와 맞물리는 점
  - 부품 = 지식 하나, 부품 사이 연결 = 고리, 활동 결과 = 기록 → 복습
  - 프로젝트 하나가 끝나면 지식 지도가 남는다.
  - 다른 프로젝트에서 같은 부품을 만나면 "다시 만남"이 된다.

## GPT에게 묻고 싶은 것

1. **방향 자체**: "AI가 코드를 짜고, 학습자는 부품의 역할·코어 아이디어·연결·흔한 실수를 익힌다"는 방식이 기본기를 쌓는 데 실제로 효과가 있을까? 직접 타이핑하는 경험을 얼마나 줄여도 될까?
2. **코어의 기준**: "AI가 틀렸을 때 모르면 알아챌 수 있나?" 외에 더 좋은 기준이 있나? 웹 게시판이라면 코어 부품은 무엇무엇인가?
3. **부품 단위**: 프로젝트를 부품으로 나눌 때 적당한 크기는? (함수? 모듈? 기능? "인증 검사", "세션", "입력 검증" 수준이면 적당한가?)
4. **참여 수준**: 역할 맞히기, 없애 보기, 버그 찾기, 핵심만 직접 중 기억에 가장 오래 남는 건? 초보와 중급의 순서는 어떻게 달라야 하나?
5. **AI에 맡기는 정도를 지식 상태로 조절**하는 아이디어의 함정은?
6. **나보다 실력 있는 사람이 원하는 것**: 중급 이상 개발자는 이런 앱에서 무엇을 원할까? 아니면 처음부터 초보에게만 집중하는 게 맞을까?
7. **비슷한 시도**: 이미 이런 방식으로 개발을 가르치는 서비스나 연구가 있나? 있다면 무엇을 배울 수 있나?
8. **캡스톤 범위**: 남은 기간에 이 중 어디까지 보여 주는 게 현실적인가? (지금 앱의 PDF·코드·지식·복습은 동작한다.)
