# Recaller 개발 학습 확장: 설계 평가

## 결론

방향은 타당하다. 다만 ‘부품을 이해하는 학습’에서 끝나면 개발 기본기를 충분히 익히기 어렵다.

내가 추천하는 방향은 다음과 같다.

> AI가 구현의 부담을 줄여 주되, 학습자는 소프트웨어의 구조를 이해하고, 동작을 예측하고, 오류를 발견하고, 핵심을 수정하며, 다른 상황에도 적용할 수 있도록 훈련하는 것.

여기서 중요한 구분이 있다.

- 프로젝트 완성: 실제로 작동하는 프로그램을 만드는 것.
- 개발 역량 획득: 그 프로그램이 왜 작동하는지 알고, 문제가 생기면 원인을 찾아 해결할 수 있는 것.

Recaller는 두 번째를 목표로 해야 한다. 첫 번째는 학습을 위한 실험 환경이자 결과물이다.

### 연구는 이 방향을 얼마나 뒷받침할까?

2026년 발표된 뮌헨공대 연구에서는 프로그래밍 입문 학생 275명을 대상으로 AI 지원 방식에 따른 학습 효과를 비교했다. AI를 사용한 집단은 과제 수행 점수가 높았지만, 지식 향상이나 코드 이해도에서는 AI를 사용하지 않은 집단보다 뚜렷하게 우수하지 않았다.&#x20;

## 1. 직접 코딩을 얼마나 줄여도 될까?

반복 구현은 많이 줄여도 되지만, 핵심 로직의 독립적인 구현 경험까지 없애면 안 된다.

2026년 Anthropic이 개발자 52명을 대상으로 진행한 실험에서는 AI 지원 집단의 사후 평가 평균이 50%, 직접 코딩 집단은 67%였다. 특히 디버깅에서 차이가 컸다. 다만 짧은 과제 직후 측정한 소규모 연구라 장기적인 학습 효과까지 입증한 것은 아니다.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://www.anthropic.com\&sz=32)

앤트로픽



여기서 중요한 건 타이핑량과 사고량을 분리하는 것이다.

| AI에게 맡기기 적합       | 학습자가 직접 해 봐야 할 것         |
| ----------------- | ------------------------ |
| 반복적인 CRUD 보일러플레이트 | CRUD 요청이 DB까지 도달하는 흐름 설명 |
| 프로젝트 설정, 기본 UI    | API 응답과 상태 변화 예측         |
| 이미 이해한 일반적인 코드    | 조건문·쿼리·권한 검사 핵심 로직 구현    |
| 테스트 실행, 로그 수집     | 실패 원인 추론, 테스트 케이스 설계     |
| 익숙한 라이브러리 사용법     | 새로운 요구사항에 맞게 코드 수정       |

예컨대 로그인 기능을 학습할 때 세션 관리 라이브러리를 직접 만드는 건 낭비일 수 있다. 하지만 서버가 현재 사용자를 어떻게 확인하고, 인증되지 않은 요청을 어떻게 거부하는지는 직접 구현하거나 수정해 봐야 한다.

최종적으로는 다음을 구분해 측정하는 게 좋다.

- 이해: 코드 없이 원리를 설명하고 결과를 예측할 수 있는가?
- 적용: 익숙하지 않은 사례에서도 핵심 로직을 구현하거나 수정할 수 있는가?
- 검증: 잘못된 구현을 발견하고 왜 잘못됐는지 입증할 수 있는가?

특히 마지막 두 가지가 없으면 Recaller가 개발 훈련기보다 코드 설명 학습기에 가까워질 위험이 있다.

## 2. 코어의 기준과 웹 게시판의 핵심 부품

Claude가 제안한 질문인 "AI가 틀렸을 때 이걸 모르면 알아챌 수 있나?"는 좋은 기준이다. 하지만 그것만 사용하면 오류 검출에 치우친 교육과정이 될 수 있다.

나는 코어를 판단할 때 네 가지를 보겠다.

| 기준 | 핵심 질문                         |
| -- | ----------------------------- |
| 원리 | 이것이 왜 필요한지 설명할 수 있어야 하는가?     |
| 판단 | 여러 구현 방식 중 무엇을 선택할지 결정해야 하는가? |
| 검증 | 동작이 틀렸거나 위험할 때 알아챌 수 있어야 하는가? |
| 전이 | 다른 프로젝트에서도 반복해서 사용되는 지식인가?    |

이 네 기준을 모두 만족해야 하는 건 아니다. 중요도와 재사용성, 초보자의 선행지식에 따라 선정하면 된다.

### 게시판 프로젝트를 분해한다면

사용자 요청이 처리되는 구조

브라우저 / 클라이언트

라우터 · 입력 검증

어디로 보낼까? 요청이 유효한가?

인증 · 권한 확인

누구인가? 이 작업을 해도 되는가?

비즈니스 로직

글 작성, 수정, 삭제 규칙

데이터 접근 · DB

조회, 저장, 트랜잭션

결과가 다시 HTTP 응답으로 반환

| 코어 부품    | 반드시 이해해야 할 아이디어         |
| -------- | ----------------------- |
| HTTP·라우팅 | 요청과 응답, 메서드, 상태 코드      |
| 입력 검증    | 클라이언트 입력을 신뢰할 수 없음      |
| DB·SQL   | 영속성, 관계, 제약조건, 안전한 쿼리   |
| 비밀번호·인증  | 비밀번호 해싱, 사용자 식별, 세션     |
| 인가(권한)   | 로그인했어도 모든 자원에 접근할 수는 없음 |
| 비즈니스 로직  | 사용자의 요구사항을 명확한 규칙으로 변환  |
| 오류 처리    | 정상·실패·예외를 구분한 응답        |
| 테스트      | 기대 동작과 실제 동작을 비교, 회귀 방지 |

여기에 프론트엔드까지 본격적으로 학습시킬 경우 상태 관리, 비동기 데이터 흐름, UI 렌더링을 별도 코어로 추가해야 한다.

## 3. 부품 단위는 어느 크기가 적당한가?

'인증 검사', '세션', '입력 검증' 정도는 적당한 크기다. 다만 부품과 지식을 1:1로 대응시키는 설계에는 반대한다.

이유는 소프트웨어의 구성 단위와 사람이 기억해야 하는 지식의 단위가 다르기 때문이다.

프로젝트: 로그인되는 게시판

기능: 로그인

사용자가 로그인한다

기능: 글 삭제

본인 글만 삭제한다

부품: 세션 검사

요청자의 신원을 확인

부품: 소유권 검사

대상 자원의 접근 권한 확인

인증과 인가의 차이

401과 403의 차이

소유권은 서버에서 검사

기능은 여러 부품을 이용하고, 부품은 여러 지식을 포함한다. 동일한 지식은 다른 프로젝트에서도 재사용된다.

추천하는 단위 체계는 이렇다.

| 단위    | 기준              | 예시                   |
| ----- | --------------- | -------------------- |
| 프로젝트  | 완성할 소프트웨어       | 게시판                  |
| 기능/단계 | 사용자가 달성할 결과     | 내 글 삭제               |
| 부품    | 독립된 역할과 책임      | 소유권 검사               |
| 지식    | 인출하고 재사용할 개념·원리 | 서버에서 소유권을 검증해야 한다    |
| 코드 위치 | 구현을 관찰할 대상      | `posts.ts`의 권한 검사 구간 |

부품은 \*\*'하나의 책임을 설명할 수 있는 크기'\*\*가 좋다. 함수 하나에 여러 책임이 있을 수도 있고, 하나의 책임이 여러 파일에 걸칠 수도 있다.

그리고 모든 지식이 부품인 것도 아니다. SQL 트랜잭션, 경쟁 상태, 관심사의 분리 등은 여러 부품에 적용되는 원리다. 이들을 억지로 부품으로 만들 필요가 없다.

Recaller의 기존 지식 저장소를 그대로 활용하되, 프로젝트·부품·코드 위치를 지식과 연결하는 별도 관계로 관리하는 편이 자연스럽다.

## 4. 어떤 학습 활동이 가장 효과적인가?

활동별로 기르는 능력이 달라서 '버그 찾기가 가장 오래 남는다'처럼 일률적인 순위를 매기기는 어렵다.

다만 장기 기억에는 반복적인 인출과 간격 학습이 중요하고, 실제 코딩 능력을 원한다면 직접 코드를 생성하는 연습이 필요하다. 2026년 250명 대상 프로그래밍 교육 실험에서도 직접 코드 작성과 피드백을 경험한 집단의 새로운 코드 작성 과제 성과가 높았다.&#x20;

내가 제안하는 활동별 역할은 다음과 같다.

| 활동          | 주로 훈련하는 능력         |
| ----------- | ------------------ |
| 역할 맞히기      | 구조 인식, 개념 회상       |
| 결과 예측       | 실행 흐름 이해           |
| 없애 보기       | 부품의 존재 이유, 인과관계 이해 |
| 버그 찾기       | 진단, 문제 해결          |
| 핵심 코드 수정    | 구현, 기존 지식 적용       |
| 새로운 상황에서 구현 | 독립적인 문제 해결, 전이     |

내가 특히 좋게 보는 활동은 \*\*'없애 보기 → 결과 예측 → 실제 테스트 → 수정하기'\*\*다.

가령 소유권 검사를 없애면 무슨 일이 발생하는지 먼저 예측하게 한다. 이후 실제로 다른 사용자의 게시물을 삭제하는 요청을 보내 보고, 마지막으로 검사 로직을 복구하게 한다.

단순히 '권한 검사가 중요하다'는 설명보다, 그 코드가 없을 때 시스템이 어떻게 망가지는지 직접 관찰하는 것이다.

단, 오류 사례로 배우는 방식도 무조건 우월하지는 않다. 2025년 40개 연구를 종합한 체계적 문헌고찰에 따르면, 잘못된 예제의 효과는 오류를 어떻게 설명하고 학습자에게 어떤 지시를 주느냐에 따라 달라진다. 복잡한 오류를 초보자에게 무작정 찾으라고 하면 인지적 부담이 커질 수 있다.&#x20;

## 5. 지식 상태에 따라 AI 개입을 조절하는 아이디어의 함정

아이디어 자체는 좋다. 다만 지식 상태와 학습자의 수행 능력을 동일하게 취급하면 문제가 생긴다.

예를 들어 인증 개념을 문제로 여러 번 맞혀 '졸업' 상태가 되었어도, 인증 미들웨어를 직접 구현하거나 디버깅할 수 있다는 보장은 없다.

또한 '몰랐음' 상태인 사람에게 버그 찾기를 시키면 오히려 정답을 이해하기도 전에 복잡한 문제를 풀어야 할 수 있다.

내가 추천하는 방식은 기존 지식 상태를 유지하면서, 개발 학습의 수행 기록을 별도로 추가하는 것이다.

| 기존 지식 상태 | 추가로 볼 수행 증거             |
| -------- | ----------------------- |
| 만남       | 설명을 읽고 결과를 예측했는가        |
| 몰랐음      | 힌트가 필요했는가, 어떤 오개념이 있었는가 |
| 앎        | 도움 없이 수정·검증했는가          |
| 졸업       | 시간이 지난 뒤 다른 문제에 적용했는가   |

특히 다음 두 가지는 구분해야 한다.

프로젝트 검사 통과 ≠ 학습 성취.

AI가 전부 구현해서 테스트를 통과했다면 프로젝트는 성공했지만, 학습자가 개념을 이해했다고 기록하면 안 된다.

반대로 테스트에 실패했어도 학습자가 정확하게 원인을 예측했다면 그 개념에 대한 이해 증거는 남길 수 있다.

따라서 AI 도움 수준은 지식 상태로 \*추천\*하되, 실제 학습 성취는 수행 활동, 힌트 사용 여부, 독립적인 재평가를 함께 보고 판단하는 게 좋다.

그리고 '졸업'은 AI에게 전부 맡긴다는 의미보다 이제 이해 연습 대신 실제 활용과 간격을 둔 검증으로 넘어간다는 의미가 낫다.

## 6. 중급 이상 개발자는 무엇을 원할까?

중급자에게도 가능성은 있다. 다만 초보자와 같은 훈련을 강제로 반복하게 해서는 안 된다.

중급자는 보통 기능의 역할 자체를 배우기보다, 이해하고 있다고 생각했던 부분의 빈틈을 찾아내는 활동에서 더 많은 가치를 얻을 수 있다.

예를 들면 이런 질문이다.

> AI가 구현한 회원가입 API는 모든 테스트를 통과했다. 하지만 동시에 같은 이메일로 회원가입 요청 두 개가 들어오면 어떻게 될까?

중급자에게 의미가 있을 만한 기능은 실제 코드베이스 분석, 까다로운 실패 사례, 변경 요구사항, 테스트 설계, 설계 선택의 비교다.

반면 버튼을 누를 때마다 역할 맞히기 문제가 나오거나, 이미 아는 개념을 반복해서 설명해 주면 오히려 방해가 된다.

여기에 나는 새로운 상황으로의 전이 과제 하나를 반드시 포함시키고 싶다.

게시판에서 권한 검사를 배웠다면, 마지막에는 메모 API처럼 구조가 조금 다른 기능을 제시하는 것이다. 학습자는 AI가 준비한 기본 코드에서 같은 원리를 적용해야 한다.

이것이 단순히 그 게시판 코드를 외운 것인지, 원리를 이해한 것인지 확인하는 중요한 장치가 된다.

### 구현에서 특히 주의할 부분

기술적으로 가장 큰 위험은 화면 제작보다 프로젝트 실행과 자동 검사의 신뢰성이라고 본다.

먼저 검증된 프로젝트 템플릿, 고정된 단계별 명세, 재현 가능한 오류 사례와 테스트를 준비하는 편이 좋다. 테스트 기대값은 AI가 즉석에서 판정하게 하지 않고, 코드로 검증해야 한다. AI는 검사 결과를 해석하고 힌트를 제공하는 역할에 집중시키는 것이다.

버그를 심는 기능도 처음에는 AI가 사용자의 임의 파일을 수정하는 방식보다, 준비된 버그 버전을 별도의 실습 작업공간에 적용하는 방식이 안전하고 재현 가능하다.

또한 로컬 앱에서 서버를 실행한다면 작업 디렉터리 제한, 프로세스 종료, 포트 충돌, 테스트용 DB 격리, 파일 읽기 권한 등을 처리해야 한다. 특히 자동 검사가 실제 사용자 데이터를 변경하지 않게 하는 것이 중요하다.

일반적인 모든 GitHub 프로젝트를 가져와 AI가 자동으로 코스를 제작하는 기능까지 구현하는 것은 현재 범위에서 권하지 않는다. 코드베이스 분석, 학습 목표 생성, 테스트 생성, 보안·실행 환경까지 동시에 해결해야 하므로 완성도가 떨어질 가능성이 높다.

대신 고정된 코스 하나라도 위 기능을 모두 실제로 수행하고, 다른 코스를 추가할 수 있도록 단계·검사·지식 연결 정보를 데이터로 분리해 두는 방향이 적절하다.

남은 정확한 개발 기간과 현재 코드 구조를 확인하지 않았으므로 일정까지 확정할 수는 없다. 다만 위 범위는 기존 PDF·코드·지식·복습 시스템을 활용한다는 전제에서 캡스톤의 주요 확장 목표로 잡을 만하다. 쉬운 작업이라고 보기는 어렵다.

## 최종적으로 바꾸고 싶은 설계 철학

Claude가 정리한 방향에서 내가 수정하고 싶은 건 딱 세 가지다.

첫째, 부품을 지식과 동일시하지 말 것. 부품은 시스템을 설명하는 단위이고, 지식은 학습자가 기억하고 적용해야 하는 단위다. 서로 연결하되 분리해야 한다.

둘째, 이해하는 것과 구현할 수 있는 것을 구분할 것. AI가 대부분 코드를 작성해도 상관없지만, 학습자가 독립적으로 수행해야 하는 핵심 활동은 남겨야 한다.

셋째, 프로젝트 완성보다 지식의 전이를 평가할 것. 게시판 권한 검사를 배웠다면 다른 프로젝트에서도 그 원리를 활용할 수 있어야 한다.

내가 생각하는 Recaller의 차별화 방향은 다음 한 문장이다.

> AI와 함께 소프트웨어를 만들되, 그 과정에서 배운 원리를 직접 검증하고 다른 문제에도 적용할 수 있도록 훈련하는 학습 시스템.

이 방향이라면 Recaller가 원래 가지고 있던 PDF 기반 학습, 알고리즘 문제 풀이, 지식 저장소, 연결, 간격 복습이 서로 동떨어진 기능이 아니라 하나의 학습 체계로 이어질 수 있다.
