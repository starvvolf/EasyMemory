# 생성 엔진 v3 설계 (Claude 안) · 2026-10-19 고정

이 문서는 아스트라(GPT) 안과 비교하기 위해 **구현 전에 고정한** Claude 안이다. 이후 수정은 아래 "변경" 절에 날짜와 이유를 덧붙이고 본문은 고치지 않는다.

## 1. 진단: 현재 엔진(v2)이 품질을 잃는 곳

현재 흐름: 목차 → 단원별 분류(짧은 인용 조각) → 단원별 설계(조각마다 "떠올릴 것" 한 줄) → 단원별 출제(한 줄 + 짧은 인용만 보고) → 코드 검사 → 저장. AI 판정단은 실험실에서만 돈다.

| 관찰된 문제 (근거) | 생기는 곳 | 원인이 된 구조·규칙 |
|---|---|---|
| 조건 누락: 그래픽스03 `q-s5-o8` "근·원 경계 → (-1,-1,-1)/(1,1,1)" (원문은 특정 모서리) | 설계 | `recall`은 "떠올려야 하는 것 하나"(designPrompt), [설계-1] "목표 하나 = 떠올릴 것 하나" → 짧게 줄이며 조건을 뗌. 근거 인용이 식 한 조각이라 조건이 처음부터 안 따라옴. 성립 조건을 담을 칸이 없음 |
| 정답 노출: 그래픽스03 `q-s6-o5` 대응표 전체를 주고 "near는 몇 번?" | 출제 | [출제-3] "풀이에 필요한 조건은 본문에 모두 넣는다"와 [출제-2] "정답·결정적 단서 금지"가 충돌. 목표 동사(찾을 수 있다=적용)와 recall(순서=암기)이 어긋남. "문제가 주는 것 / 학습자가 꺼낼 것" 구분이 없음 |
| 이유·비교 누락: 그래픽스04 Bresenham의 "왜 DDA 대신"이 목표에 없음 | 분류·설계 | 이유 문장이 '설명'으로 분류되고 [목적-핵심-1]이 core를 "핵심 지식·재사용 패턴"으로 한정. 단원별 처리라 단원을 넘는 관계는 볼 수 없음 (개선후보 8번에 10/12부터 기록됐으나 미반영) |
| 자잘한 문항 과다: 04 DDA 갱신식 방향별 4개, Screen Grid 장점 3개, 비프로그래머용 패키지 특징이 core → 84문항 | 설계 | [설계-1] 원자화 + 예산 개념 없음 |
| 묻는 방향: "이름 → 쓰는 상황" (유니브는 "상황 → 방법") | 설계·출제 | [공통-4]가 있으나 설계에서 강제되지 않음 |
| 출제자가 잘린 정보를 복구 못 함 | 출제 | authorPrompt에 단원 원문이 없음(목표·cue·recall·짧은 인용·소재만) |
| 위 문제들이 걸러지지 않음 | 검사 | 코드 노출 검사는 "정답 글자(3자 이상)가 본문에 있나"뿐(답 `5`는 검사 대상 아님). "recall이 본문에 있나"는 목표 문장에만 적용. 판정단은 실험실 전용이고, 맨손 학습자 신호는 10/12에 꺼짐, 전문가는 "보이나"만 보고 "유도되나"는 안 봄, 잘린 recall을 기준으로 받아 원문 대조가 끌려감 |
| 호출 비효율: 31쪽 새 자료 55회(그림 읽기 쪽마다 1회 + 단원마다 분류·설계·출제) | 전체 | 쪽별 그림 읽기, 단원별 분류·설계 분리 |

## 2. 원칙

1. **외울 것 = 사실 + 성립 조건.** "짧게"보다 "조건을 잃지 않게"가 우선한다.
2. **core = 핵심 지식 + 이유·구별 기준(왜, 언제, 무엇이 다른가).**
3. **배울 가치 단위로 묶고, 문제 수는 예산으로 정한다.** 한 문항 한 과제는 유지한다.
4. **모든 단계가 원문을 본다.** 앞 단계의 정리와 원문이 다르면 원문을 따른다.
5. **상황 정보는 주고, 꺼낼 것은 주지 않는다.** 문항마다 `given`/`mustRecall`/`conditions`를 계약으로 둔다.
6. **묻는 방향은 실제로 쓰는 상황대로**(고르는 지식이면 상황 → 방법).
7. **검사는 관문이다.** 실제 생성에서 걸러 재출제한다. 뜻으로 본다(글자만 보지 않는다).

## 3. 구조

```
① 전체 읽기 (PDF 통째, 자료마다 1번, 저장·재사용) → 목차 + 지식 지도 + 그림 쪽 옮김
② 출제 계획 (지도만 읽음, 1번)                     → 문항 계획(종류·주는 것·꺼낼 것·조건·근거)
③ 단원별 출제 (단원 원문 전체 + 지도 + 계획)        → 문항
④ 관문 검사 (코드 + 단원당 AI 1번)                  → 걸리면 이유를 붙여 1번 재출제
```

### ① 전체 읽기 — 입력: PDF 파일 + 쪽별 글자 층 / 출력
- `sections`: 단원(제목, 쪽, 시작 글자, 세부 항목). 지금 목차와 같은 역할(공부 순서·범위·출제 단위).
- `concepts`: 지식 단위. 이름(원문 표기), 종류(정의/식/절차/규칙/사실/용어), 내용, **성립 조건[]**, 단계[](절차일 때), 근거(쪽 + 원문 인용, 조건이 담긴 문장 단위), 중요도(상/중/하 + 이유), 단원.
- `relations`: 개념 사이. 종류(이유/비교/선택 기준/순서/포함/헷갈리는 짝), 설명, 근거. 단원을 가로질러도 된다.
- `materials`: 원문 예시·수치·표·그림(문제 소재), 붙는 개념.
- `skips`: 뺄 것(강의 안내 등), 읽기 불확실한 곳.
- `pageNotes`: 글자 층이 빈약한 쪽(그림·수식·표 위주)의 내용을 옮긴 것. 쪽별 그림 읽기 호출을 대신한다.
- 인용은 글자 층과 대조해 확인하고, 못 찾으면 버리지 않고 "미확인"으로 표시한다(그림 속 글자일 수 있음).

### ② 출제 계획 — 입력: 지도 + 목적·메모·신호 / 출력
- 문항 계획 목록. 각 항목: 단원, 종류(`상황선택`/`적용계산`/`이유`/`구별`/`용어`/`절차`/`사실`), 목표 문장, `given`(문제가 주는 상황·정보), `mustRecall`(학습자가 꺼낼 것), `conditions[]`(문항에 반드시 들어갈 조건), 근거 개념·관계, 중요도(core/support).
- 예산: 자료 분량과 목적에 맞춘다. 자잘한 사실은 합치고, 같은 지식을 방향만 바꿔 두 번 묻지 않는다. 이유·구별·선택 기준 관계는 문항으로 살린다.
- 이 계획이 지금의 "목표"(확인 화면·정리 화면)가 된다.

### ③ 단원별 출제 — 입력: 단원 원문 전체(글자 층 + pageNotes) + 그 단원의 지도 + 계획
- 규칙: 상황 정보(given)는 주고 mustRecall은 주지 않는다. conditions는 빠짐없이 쓴다. 원문 표기 유지. 계산은 직접 검산. 형식 규칙(choice/short/self-check)은 기존 출제기준 형식 규칙을 따른다.

### ④ 관문 검사
- 코드: mustRecall이 문항 본문(정답 공개 전 글)에 그대로 들어 있으면 노출. conditions의 핵심 낱말이 본문에 빠지면 조건 누락 의심. 기존 형식·노출 검사 유지.
- AI(단원당 1번, 가벼운 모델): 문항마다 ㉠ "과목 지식 없이 문제 글만으로 답이 유도되나? 그렇다면 근거 문장" ㉡ "원문과 대조해 다르게 읽으면 정답이 틀려지는 해석이 있나? 빠진 조건" — 기준은 원문(지도 요약 아님).
- 걸린 문항은 이유를 붙여 1번 재출제. 그래도 걸리면 경고와 함께 남기되 표시한다.

## 4. 비용 예상 (실측으로 확인할 것)
| 자료 | 현재(새 자료) | v3 |
|---|---|---|
| 31쪽, 6단원 | 55회 | 약 18~20회 (①1 + ②1 + ③6~8 + ④6 + 재출제) |
| 52쪽, 8단원 | 79회 | 약 24~26회 |

①은 큰 입력(PDF 전체), ③은 단원 원문 전체를 받으므로 토큰은 비슷하거나 약간 늘 수 있다.

## 5. 재사용
- ①의 결과(지도)는 자료마다 저장한다. 목적 변경·기출형·다시 만들기는 ②부터 다시 한다.
- 지도는 읽기 화면 기능(용어 지도, 목표 설명, 목차 표시)의 공통 바탕이 될 수 있다(후속).

## 6. 지키는 것
- 목차별 범위 덮기와 쪽 근거, 원문 강조, 확인 화면, 신고 재출제, 판정단, 기출형 경로.
- 기본 엔진(v2)은 그대로 두고 v3는 실험실의 엔진 선택지로 둔다.

## 7. 비교와 채택
- 대상: 현재 엔진 / Claude v3 / 아스트라 안 / 유니브 기본형.
- 자료: 그래픽스03, 04 + 두 설계 모두 보지 않은 확인용 자료 1개 이상.
- 블라인드 채점: 범위 커버, 상황·적용·이유 비율, 오류(정답 틀림·노출·조건 누락), 문제당 학습 가치, 호출·토큰·시간.
- 채택: 오류는 유니브 이하, 범위·깊이는 유니브 이상.

## 변경
### 2026-10-19 첫 실제 실행(그래픽스03 1~12쪽, 14호출 5분 40초) 뒤
- **관문 버그 수정(구현 실수)**: "문제 글만으로 답이 나오나"를 판단하는 호출에 단원 원문을 함께 넣어, 모델이 원문 문장을 근거로 거의 모든 문항을 걸렀다(3단원 모두 1차 탈락 → 재출제 → 2차도 같은 이유). 설계는 "문제 글만"이었으므로 구현을 설계에 맞췄다: 유도 판단은 문제 글만 보는 호출, 원문 대조는 원문을 보는 호출로 나눠 동시에 돌리고, 유도 판단의 근거 문장이 실제 문제 글에 있을 때만 인정한다. 관문 호출은 단원당 1번 → 2번(둘 다 가벼움).
- **전체 읽기 분할(시간)**: 한 호출이 목차·지도·그림 쪽 옮김을 한꺼번에 쓰느라 142초(출력 7천 토큰) 걸렸다. 목차 호출 1번 뒤 단원별 지도 호출을 4개씩 동시에 돌린다. 모든 읽기 호출은 같은 지시 + 같은 PDF를 앞에 두어 두 번째부터 프롬프트 캐시를 쓰게 한다(PDF를 글보다 앞에 보내도록 바꿈). 단원 간 관계는 각 단원 호출이 전체 목차를 보고 관계 문장에 다른 단원을 적는다(같은 호출 안에서 id로 잇지는 못함 — 원래 설계보다 약해진 점).
- **단원 출제 동시 처리(시간)**: 단원 출제·관문을 3개씩 동시에, 단원마다 끝나는 대로 저장.
- **진행 표시(체감)**: 스트리밍으로 들어오는 응답을 세어 "개념 n개", "문항 n개 쓰는 중" 등을 화면에 보인다. 호출 기록에 캐시 토큰을 남긴다.
- 하지 않은 것: 고른 쪽만 PDF로 잘라 보내기(PDF 편집 부품 추가 필요), 문항 하나씩 바로 검사·공개(부분 JSON 해석).

### 2026-10-19 "만들면서 바로 읽기" 흐름에 맞춤
사용 흐름(시작하면 바로 읽기 → 진행이 보임 → 목차·목표가 먼저 → 읽는 단원부터 문제 → 통과한 문제만)에 맞춰 점검하고 고쳤다.
- **보류**: 관문에 두 번 걸린 문항은 경고를 달고 공개하던 것을 바꿔, 공개하지 않고 `보류` 사유로 빠진 목록에 남긴다(원칙 7과 "통과한 것만 보인다").
- **읽는 단원부터**: 읽기 화면이 쪽을 옮기면 `POST /api/lab/gen/:id/focus {page}`로 알린다(모델 호출 없음, 서버 메모리). 출제는 고정 3개 묶음 대신 빈 자리가 날 때마다 "읽는 쪽이 든 단원 → 그 뒤 → 그 앞" 순서로 다음 단원을 고른다(v2도 같은 순서, 한 번에 하나).
- **목차·목표 먼저**: 상태 응답에 단원별 계획 목표와 상태(만들 차례/만드는 중/준비/보류, 보류 문항 수)를 실어, 문제가 하나도 없을 때도 읽기 화면의 목차와 "이 쪽에서 익힐 것"이 계획에서 바로 뜬다. 첫 단원이 준비돼 실제 자료로 바뀐 뒤에도 진행 표시와 단원 상태가 그대로 보인다.
- **지도 재사용**: 다시 만들기(fork)가 지식 지도를 복사해 전체 읽기를 다시 하지 않는다. 용어 지도는 지식 지도 글을 먼저 받고 쪽 글자는 그만큼 줄여 받는다.
- **선택**: 공부 화면의 자료 만들기에 "새 엔진(v3, 실험)" 체크를 두었다(기본은 v2, 기출형과는 같이 쓰지 않음).
- **흐름 점검 기록**: 실행마다 `timeline`에 시작·목차·목표·확인 대기·단원 시작/열림(문항 수·보류 수)·읽는 쪽 변경·완료 시각을 남긴다. 실험실 "사용 흐름 점검"이 이를 화면 요소 기준으로 보여 주고, 읽는 쪽을 옮긴 뒤 다음 단원이 그 단원이었는지 ✓/✗로 표시한다. v3 목차는 전체 읽기 첫 호출(목차) 직후 공개한다.
