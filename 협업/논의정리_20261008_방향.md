## 1. 지금 어디까지 왔나

- **화면**: 되짚기(`/study`)에서 자료 만들기, 읽기, 모르는 것 노트, 연습, 신고·다시 만들기가 동작한다. 실험실(`/lab`)도 동작한다.
- **생성**: 앱이 ChatGPT 계정으로 6단계(분석 → 개념 구조 → 학습 설계 → 활동 설계 → 카드 → 출제)를 돈다.
  - 가짜 모델로는 전 구간이 통과한다.
  - 실제 모델로는 활동 설계까지 통과했다.
  - **끝까지 성공한 실행은 0건**이다. 카드 근거 실패를 고쳤고, 실측을 기다리는 중이다.
- **실측 예산**: 60회 중 20회를 썼다(검증기록 11).
- **실측 실패의 공통점**: 모델 품질 문제가 아니라 **우리 쪽 입력과 검사**에서 났다.
  - 원문을 안 보냄
  - MCP 도구를 전제로 한 지시문
  - 카드 단계에 엉뚱한 원문을 줌
  - 형식 경계가 지나치게 깐깐함

## 2. 검사 정리 (제안)

엔진에 검사가 120개 있다. MCP 대화용으로 만들어 깐깐하고, 앱 호출에서는 검사 하나가 걸릴 때마다 AI 호출이 한 번 더 나간다.

**남길 것: 세 종류만 막고 다시 시킨다**

| 남길 검사 | 이유 |
|---|---|
| 원문에 없는 내용 (근거 인용이 실제 원문에 있나, 쪽이 범위 안인가) | 틀린 걸 외우게 됨 |
| 끊긴 연결 (없는 개념 참조, 쪽 근거 없는 목표, 하위 개념 없는 개념 구조) | 다음 단계가 터짐 |
| 풀 수 없는 문제 (정답 노출, 빈칸 개수, 객관식 정답 누락) | 사용자가 직접 겪음 |

**나머지는 이렇게 바꾼다**

| 지금 | 바꾸면 |
|---|---|
| 형식 규칙 (경계, 번호, 들여쓰기), 정해진 값 목록 | **structured output**(칸과 고를 수 있는 값을 정한 JSON). ChatGPT 계정 연결에서 되는지 확인 필요 |
| 개수 제한 (목표 60개 등) | **사용자가 조절**할 수 있게 |
| 중복 (코드가 문장·개념 번호를 비교) | 거부하지 말고 **합친다**. 뜻이 같은 중복은 잡지 않음 |
| 개념–목차 칸 연결 (`@목차` 번호 요구) | **쪽만 맞으면 통과**, 칸 연결은 엔진이 쪽으로 붙임 |
| 활동 설계·카드 단계 | 되짚기 경로에서는 **건너뜀**. 원래 카드 엔진의 끝 단계였고, 출제가 뒤에 덧붙으며 결과를 안 쓰게 됐다. 옛 MCP 덱 발행 경로는 그대로 둔다. 활동 설계의 판단("무엇을 보여 주고 무엇을 떠올리게 할지")은 출제 지시로 옮긴다 |

**주의**: 검사를 통과해도 품질이 보장되지 않는다. 품질은 실험실에서 사람이 본다.

## 3. 학습 설계의 이상형 (제안)

지금은 "무엇이 핵심인지, 어떻게 쪼갤지, 무엇을 떠올리게 할지"를 모델 한 번에 맡긴다. 그래서 범위가 크면 뭉치고, 작으면 잘게 쪼갠다. 목적도 거의 반영되지 않는다.

```
① 분류   원문 덩어리를 성격으로 나눔 (자료만 봄)
         핵심 지식 · 재사용 패턴 · 예시 · 설명 · 연습문제 · 부가 정보
② 고르기 목적이 기준 (그냥 읽기 / 이해 / 핵심 암기 / 통암기) + 노트 약점·신고 우선
③ 설계   고른 것마다 "무엇을 보고 → 무엇을 떠올리나". 단위 = 개념 하나. 방향 = 실제 쓰는 상황 기준
```

- 장점: 실패 지점이 분명해진다. 목적을 바꿔도 ①은 재사용한다. AGENTS.md 원칙이 실제 규칙이 된다.
- **작은 첫걸음**: 개념 구조에 성격 표시 한 칸을 추가하고, 학습 설계에 목적별 고르기 규칙을 넣는다. 실험실에서 목적만 바꿔 결과가 달라지는지 본다.

## 4. 출제 방식 (제안)

**사용자의 원래 아이디어**: AI에게 "워드"를 쥐여 주고 출제자처럼 문제 모양을 직접 설계하게 한다. 이 핵심(닫히지 않은 문제 형식, 다듬어 완성)은 지킨다.

**지금의 문제**: API 방식에서는 "워드"가 아니라 문서 내부 코드를 한 번에 손으로 쓰게 하는 상태다.

| 지금 | 바꾸면 |
|---|---|
| 문서 전체를 한 번에 씀, 수정 1회 | **목표마다 따로**(동시에), 틀린 문항만 다시 |
| AI가 좌표(x·y·너비·높이)까지 씀 | AI는 **블록 종류와 순서만**, 배치는 코드가 위에서 아래로 쌓음. 단순 배치 옵션 몇 개 제공 |
| AI가 출처를 글자 그대로 베낌 | **엔진이 붙임** |
| 형식을 AI가 아무 기준 없이 고름 | **목적이 후보를 정하고** AI가 그 안에서 고름 (클릭만으로 / 주관식 플래시카드 / 통암기) |

**스킬 + 하네스로 출제 실력 올리기**
- **스킬(교본)**: 목표 종류와 목적에 맞는 참고 문서만 골라 넣는다. 좋은 예·나쁜 예를 쌓는다.
- **하네스(조교)**
  - "정답 공개 전 학생 화면"을 만들어 검사 결과와 함께 돌려준다. 미리보기를 대신한다.
  - 검사 오류 문장을 고치는 방법까지 담아 쓴다.
  - 스킬 버전을 실험실에서 비교한다.

**에이전트형 vs 코드 주도형**
- 차이는 MCP냐 API냐가 아니라 **누가 반복을 이끄느냐**다.
- API의 **도구 호출**로도 앱 안에서 에이전트형을 돌릴 수 있다. MCP는 쓰지 않는다.
- 추천
  1. 코드 주도형으로 안정된 기준선을 만든다.
  2. **출제만** 에이전트형 판을 만들어 실험실에서 품질·시간·비용을 비교한다.
  3. 차이가 크면 출제를 에이전트형으로 바꾼다.
- ChatGPT 계정 연결에서 도구 호출이 되는지 확인이 필요하다.

## 5. 사용자 스케치에서 나온 것

- **목적이 흐름 전체를 바꾸는 스위치**
  - 그냥 읽기: 노트만
  - 이해: 적게, 설명형, 목차 끝마다
  - 핵심 암기: 핵심만
  - 통암기: 전부, 반복
- **문제 시점**: 다 읽고 나서 vs 목차 중간. 추천은 **목차 단위가 끝날 때**다. 이걸 하려면 목차 단위 생성이 필요하고, 그러면 "큰 자료 나누기"도 함께 풀린다.
- **자료별 상태판**: 간단 요약, 취약점, 학습 설계 상태를 한 화면에 모은다. 지금 흩어진 기록을 모은다.
- **모르는 것 처리**: 맥락(그 쪽 원문)과 함께 답하고 → 저장 → 지식 보관·취약점 → 다시 보기·문제 활용. 1단계는 구현됐고, 문제 활용(노트 2단계)이 남았다.

## 6. 학습 에이전트로 가려면

**정의**: 학습자 관찰 → 다음 행동 판단 → 행동 → 결과로 조정. 이 고리가 시간에 걸쳐 돈다.
**지금**: 문제를 만드는 공장과 그걸 푸는 화면이다. 고리가 끊겨 있다.

| 필요한 것 | 지금 부족한 점 |
|---|---|
| 학습자 상태 (기억) | 풀이(브라우저)·노트(서버)·신고(브라우저)가 흩어짐. 개념 단위 지도가 없음 |
| 판단 | AI가 "다음에 뭘 할지" 정하는 부분이 없음 |
| 행동의 종류 | 약점 하나에 맞춘 문제, 다른 설명, 난이도 조절이 없음 |
| 결과 반영 | 풀이·노트가 다음 생성에 안 들어감 |
| 목표·계획 | 시험일, 범위 계획이 없음 |
| 효과 측정 | 없음 |
| 기반 | 실제 생성 성공 0건 |

**새 자료에 알아서 적응하려면**
1. 자료 파악(종류)
2. 학습자 프로필(자료를 넘어선 기억)
3. 전략 모음(종류 × 목적)
4. 첫 진단
5. 결과로 다음 장 조정

가장 작은 판은 이렇다: 자료 종류 3~4개, 약점 목록 공유, 종류 × 목적별 지침 몇 줄. 그다음 목차 단위 생성 위에 4·5를 붙인다.

**순서**
1. 생성 안정화
2. 학습자 상태 통합
3. 작은 행동 늘리기(노트 2단계부터)
4. 판단 붙이기("오늘 할 것" 제안)
5. 결과로 조정, 목표·계획, 효과 측정

## 7. API에서 맥락(기억) 다루기

- API는 아무것도 기억하지 않는다. ChatGPT·Claude 앱도 사실 앱이 기억을 저장하고 매번 넣어 주는 방식이다.
- **원칙**
  - 대화 기록이 아니라 **정리된 상태**를 저장한다.
  - 호출마다 **필요한 조각만** 넣는다.
  - **안 바뀌는 것은 앞, 바뀌는 것은 뒤**에 둔다(캐싱).

```
① 지침(스킬)      거의 안 바뀜 → 맨 앞
② 학습자 프로필   가끔         → 짧은 요약
③ 자료별 상태     자주         → 이번 일 관련분만 (개념별: 앎/약점/안 봄)
④ 원문            고정         → 필요한 쪽만
⑤ 이번 대화       지금         → 최근 몇 턴 + 앞부분 요약
```

- **지금**: ④⑤는 하고 있다. ③은 흩어져 있고 AI 호출에 안 들어간다. ②는 없다. 캐시를 고려한 순서는 아직 안 했다.
- 6장의 "학습자 상태 통합"이 이 문제의 답이다.

## 8. 토큰·비용·속도 감각

- 한글 1글자 ≈ 1토큰이다. A4 한 장 프롬프트 ≈ 1~2천 토큰, 44쪽 자료 전체 ≈ 2~3만 토큰이다. 모델은 한 번에 수십만 토큰 이상을 받는다.
- **입력은 싸고 빠르다. 느리고 비싼 건 출력과 추론(생각)이다.** Recaller가 느린 원인도 프롬프트 길이보다 긴 출력(문서 한 번에 쓰기)과 단계 수일 가능성이 크다.
- 긴 대화는 매 턴 앞 대화를 다시 보내서 누적되지만, **캐싱**(앞부분이 같으면 재사용)과 잘라내기로 버틴다. Recaller 생성은 호출마다 독립이라 누적되지 않는다.
- **조심할 건 길이가 아니라 잡음**이다. 부딪치는 지시, 필요 없는 정보가 성능을 떨어뜨린다. 이번 실측 실패 두 건이 정확히 이 경우였다.
- **기준: 길게 줘도 된다, 깨끗하게 줘라, 짧게 받아라.**
- 실제 토큰 사용량은 아직 모른다. 실측 기록에 "미기록"으로 남았다.
