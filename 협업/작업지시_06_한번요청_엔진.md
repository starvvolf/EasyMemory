## 지금 화면이 하는 일 (바뀐 것)
- 새 자료: PDF를 올리면 질문 3개(목적, 할 수 있어야 할 것, 범위)를 묻는다. 답으로 "이렇게 만들게요" 문장을 만들고, **요청 하나**(`stopAfterStage: "cards"`, 목표 선택 없음)를 올린 뒤 바로 읽기로 넘어간다. 문장은 요청의 `purpose`에 그대로 들어간다.
- 화면은 5초마다 요청 상태를 본다: 대기 → AI가 만드는 중(n/6단계) → 문제 검사·기록 중 → 준비됨.
- **"준비됨"의 조건**: `/api/personalization-lab` 목록에 `originRunId`가 그 요청의 `runId`와 같은 문서가 나타나는 것. 즉 출제 편집틀에서 `record_problem_iteration`까지 끝나야 한다.
- 품질 검사(`tools/problem-authoring-lab/quality.ts`)에 error로 걸린 문항은 화면에서 빼고 "빠진 문항 N"으로 보여 준다.

## 할 일
1. **"처리해" 한마디로 끝까지**
   - 담당 AI가 대기 요청을 받으면 다음을 한 번에 이어서 하게 한다.
     - `study-forge-mcp`로 5단계 처리
     - 브리지로 source packet 만들기
     - `problem-authoring-lab`으로 작성, 검사, `record_problem_iteration`
   - 절차를 MCP 서버 안내문(instructions)이나 도구 설명, 출제 지침에 고정한다. 사람이 중간에 다시 지시하지 않아도 되게 한다.
   - 요청 상태 "완료" 뒤 출제 기록까지 걸리는 공백을 없앨 방법이 있으면 제안한다(예: 출제 기록을 요청의 마지막 단계로 넣기, 계약 변경이라 먼저 보고).
2. **질문 답을 엔진 입력으로**
   - 지금은 답이 `purpose` 문장 안에만 들어 있다. 문제 설계 단계가 "할 수 있어야 할 것"(용어·정의 말하기 / 식·절차 쓰기 / 계산·적용하기 / 비슷한 것 구별하기 / 말로 설명하기)을 읽고 **형식을 고르는 근거**로 쓰게 한다.
   - 구조화된 칸으로 넘길지(계약 변경), 문장에서 읽을지 판단하고 이유를 남긴다. 화면은 `answers: { purpose, abilities }`를 이미 들고 있어 넘기기 쉽다(`src/app/study/DejipgiStudy.tsx`의 `builder.start`).
3. **단계별 검사 두 가지 추가**
   - 학습 설계: `sourceText`(또는 새 칸)에 **원문 구절이 글자 그대로** 남는지. 지금은 "PDF 11쪽의 … 행렬식" 같은 요약이라 원문 표기(`T⁻¹`) 검사가 동작하지 않는다(`협업/결과보고_02_Claude_20260929.md`).
   - 문제 설계: 사용자가 고른 "할 수 있어야 할 것"과 형식이 맞는지. 예를 들어 계산을 골랐는데 계산 문항이 하나도 없거나, 절차를 골랐는데 순서형이 없으면 경고한다.
4. **"다시 만들기" 준비 (선택)**: 화면의 "이 문제 이상해요" 신고(이 브라우저의 기록)로 해당 목표만 다시 만드는 요청은 기존 `selectedObjectiveIds` + `reuse`로 가능하다. 화면 연결은 나중에 하므로, 엔진 쪽에서 막히는 점만 확인한다.
