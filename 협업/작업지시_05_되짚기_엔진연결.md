# 작업지시 05: 되짚기 화면(`/study`)을 기존 생성 엔진에 연결

- **선행 조건**: 없음. 02(검증기)가 먼저 끝나면 3단계 검사 결과가 더 의미 있어진다.
- **대상**: 원본 개발 저장소, 브랜치 `claude/local-state-20260928`(PR starvvolf/EasyMemory#1)에서 이어서 한다.
- **근거 문서**: `협업/되짚기/README.md` 맨 아래 "Recaller로 옮긴 판" 절
- **범위 제한**
  - 되짚기 화면의 UI·UX(탭 구성, 3단계 흐름, 문구, 기록 규칙)는 바꾸지 않는다. 사용자가 이 화면을 기준안으로 정했다.
  - 연결 방식은 **기존 엔진 방식**을 따른다(자료 등록 → 요청 대기 목록 → 담당 AI가 MCP로 실행 → 출제 편집틀 기록). 화면에 맞추려고 엔진 흐름을 새로 만들지 않는다.
  - **유료 재생성(MCP·API)은 사용자 확인 없이 돌리지 않는다.** 연결 확인은 기존 실행 기록이나 목(mock)으로 한다.
  - 공용 계약(요청 스키마, `src/lib/types.ts` 등)을 바꿔야 하면 바로 고치지 말고 결과보고에 제안으로 남긴다(`docs/GENERATION_ENGINE_BOUNDARY.md`).

## 지금 상태 (Claude가 해 둔 것)
- `/study` 페이지: 되짚기 v9의 연습·읽기·기록 화면이 Recaller 출제 문서(`/api/personalization-lab`)를 풀 수 있게 연결돼 있다.
- **자료 만들기 탭은 화면만 있다.** 3단계(자료 올리기 → 학습목표 고르기 → 문제 생성·검사) 화면은 원본 그대로다.
  - 동작하는 것: PDF 고르기·끌어 놓기, 텍스트 붙여 넣기, 브라우저에서 쪽별 글자 읽기, 쪽 범위와 학습 목적 입력
  - 동작하지 않는 것: "학습목표 설계", "문제 만들기", "저장하고 읽기 시작" 버튼. `env.builder`가 비어 있어서 버튼이 꺼져 있고, 화면 위에 "엔진에 아직 연결하지 않았다"는 안내가 나온다.
- 질문 창도 화면만 있다(답변 연결 안 됨, 유료 호출). 이번 작업 범위가 아니다.

## 연결할 자리
`src/app/study/DejipgiStudy.tsx`에서 `mountDejipgi(root, env)`에 넘기는 `env`에 **`builder`를 채우면** 화면이 그대로 동작한다. 형식은 `src/app/study/dejipgi-app.d.ts`의 `DejipgiBuilderEngine`에 있다.

| 화면 버튼 | 호출 | 돌려줄 것 |
|---|---|---|
| 1단계 "학습목표 설계" | `builder.design({ file, sourceName, pages, from, to, goal, signal, onStatus })` | `{ title, objectives: [{ id, statement, kind, importance: "core"\|"support", pages, quote }] }` |
| 2단계 "문제 만들기" | `builder.author({ objectives(선택된 것), sourceName, pages, goal, signal, onStatus })` | `{ items, report: { made, repaired, converted, dropped, dup, warned }, log? }` |
| 3단계 "저장하고 읽기 시작" | `builder.save({ title, sourceName, objectives, items })` | `{ deckId? }`. 저장 뒤 화면이 `env.loadDecks()`로 목록을 다시 불러온다 |

- `onStatus(문구)`를 부르면 화면 위 진행 표시가 바뀐다. 요청 대기나 AI 실행 중처럼 오래 걸리는 동안 단계와 상태를 보여 준다(예: "AI 실행 대기 중 · 담당 AI 대화에서 요청을 처리해 주세요", "학습 설계 중 3/5").
- `signal`이 abort되면 기다리기를 멈춘다. 화면의 "멈추기" 버튼과 연결돼 있다.
- `items`의 형식은 `src/lib/study/from-authoring.ts`의 `StudyItem`과 같다. 출제 문서를 옮길 때는 이미 있는 `toStudyDeck()`을 쓴다.

## 쓸 수 있는 부품 (이미 있음)
- `env.listSources()`, `env.uploadPdf(file)`: `/api/mcp-runs/sources` (PDF 등록, 로컬 실험 모드 전용)
- `env.listRequests()`, `env.createRequest(sourceId, pageText, purpose)`: `/api/mcp-experiment-requests` (요청 저장·상태)
- `src/lib/study/request-form.ts`: `/mcp-runs`와 같은 기본값으로 요청 본문을 만든다. 실제 요청 스키마 통과 테스트가 있다.
- `/mcp-runs` 화면의 `ExperimentRequestPanel`: `stopAfterStage`, 이전 단계 출력 재사용(`reuse`) 사용 예

## 사용자에게 먼저 확인할 결정
1. **2단계 목표 고르기**: 지금 요청 형식에는 "고른 목표만 문제로 만들라"를 전할 칸이 없다(쪽·목차 범위만 있다). 선택지는 다음과 같다.
   - (가) 요청 계약에 선택 목표 목록을 추가한다. 계약 변경이라 제안부터 한다.
   - (나) 목표는 보여 주기만 하고 전체로 만든다.
   - (다) 다른 방법
   
   사용자는 아직 정하지 않았다.
2. **1단계 버튼의 뜻**: `stopAfterStage: "learning-design"` 요청으로 목표까지만 만들고, 2단계에서 `reuse`로 이어서 문제까지 만드는 방식이 기존 엔진과 가장 가까워 보인다. 다르게 판단하면 이유를 남긴다.
3. **마지막 출제 편집틀 단계**: 되짚기 목록에 뜨려면 `record_problem_iteration`까지 끝나야 한다. 이 단계를 요청 흐름에 어떻게 넣을지 정한다.
