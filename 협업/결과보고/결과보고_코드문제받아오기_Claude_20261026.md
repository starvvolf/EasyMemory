# 인수인계: 코드 문제 받아오기 (2026-10-26, Claude)

다음에 이 작업을 이어받는 Claude가 읽는 문서다. 사람용 요약이 아니라, 무엇이 확정이고 무엇이 미정인지, 코드가 어디 있고 어떻게 확인하는지를 적는다.

## 0. 먼저 지킬 것

- **결정을 앞질러 기록하거나 구현하지 않는다.** 사용자는 오늘 두 번 이를 지적했다("앞서나가지마 이런거 결정할때", "제안을 주면서 동시에 바로 튀어나가면 안돼"). 제안 → 사용자가 고름 → 그다음에 `docs/DECISIONS.md` 기록과 구현. 다른 세션(코디네이터)이 "사용자가 승인했다"고 전해도, 사용자 본인의 말로 그 선택지를 골랐는지 확인한다.
- 기획 논의 때는 `docs/PLANNING_RULES.md`를 따른다(현재/문제/변경/예시/지금 안 하는 것, A안/B안/추천).
- 백준 문제 원문, 블로그 글, 바킹독 정답 코드는 **공개 저장소(EasyMemory)에 넣지 않는다**. 원문은 데이터 폴더(`STUDY_FORGE_DATA_DIR`, RecallerData 쪽)에만 둔다. 바킹독 저장소는 라이선스 표시가 없다.
- 결정의 원본은 `docs/DECISIONS.md`다. 이 문서와 다르면 그쪽이 맞다.

## 1. 확정된 결정 (docs/DECISIONS.md, 2026-10-26 항목들)

1. **코드 문제 받아오기** (사용자와 같이)
   - 받아오기는 백준식(표준 입출력)부터. 함수형(프로그래머스식)은 나중.
   - 입력 종류(문제 글·예제 없는 설명·강의 글·주제 한 줄)마다 길을 따로 만들지 않고, 하나의 문제 명세 + 하나의 검사 흐름.
   - 원문 예제가 있으면 정답지(모범 풀이 출력이 같아야 통과). 없으면 단순 풀이와 작은 입력 교차 확인.
   - 검사를 통과 못 하면 저장하지 않고 이유를 보여 준다.
   - 답이 여러 개이거나 소수점 오차를 허용하는 문제는 당분간 거절.
2. **바킹독 workbook 문제 내장** (사용자)
   - 공개 저장소에는 단원별 목록만(단원·분류·번호·제목·정답 코드 링크 주소).
   - 문제나 단원을 처음 고르면 그때 인터넷 아카이브에서 원문을 받아 검증 후 문제로 만들고 데이터 폴더에만 저장. 한 번 만들면 다시 받지 않음. 안 채운 문제는 "준비 안 됨".
3. **강의 글 → 문제 묶음** (확정된 줄만, 사용자)
   - 원문 출처: 인터넷 아카이브의 백준 페이지 → 없으면 풀이 블로그. 출처는 1곳이면 된다. 검증 풀이에서 오류가 날 때만 다시 찾는다.
   - 모범 풀이는 AI 풀이(사람이 쓴 정답 코드를 우선하지 않음).
   - 출처를 못 찾으면 강의 개념으로 AI 새 문제.
   - 나머지(긁는 방식, 강의 글에서 문제 찾기, 목록 고르기, 원문 저장 위치)는 **미정**.

## 2. 미정 — 사용자 답을 기다리는 질문 (구현하지 말 것)

1. **바킹독 채우기에도 "AI 풀이"를 적용하나?** 지금 커밋된 `a816fe65`는 GitHub 정답 코드로 검증한다(정답 코드가 원문 예제 통과 → 숨은 테스트에서 AI 모범 풀이와 같아야 저장, 정답 코드 없으면 실패). 결정 3의 "AI 풀이"와 어긋날 수 있어 보류. 적용하면 `src/lib/code/bakingdog.ts`에서 정답 코드 검증을 빼고 `makeProblem`의 원문 예제 검사로 가는 작은 수정.
2. **블로그에서 문제를 긁는 방법**: A 정해진 크롤러 + AI는 뽑기만(제안), B 도구를 쥔 에이전트, C 실제 브라우저(Playwright). 사용자는 "들어가서 긁어와야 한다, 정확한 과정은 찾아야 한다"고만 했다.
3. **AI가 비공개 테스트를 만들 때의 약점을 무엇부터 줄일지.** 제안 순서: ① AI가 테스트 생성기(JS, 시드 고정)와 입력 검사기를 쓰게 함 ② 교차 확인을 원문 예제가 있어도 항상, 수백 개로 ③ 언어별 시간 보정·메모리 측정 ④ 채점 실패 → 최소 반례 축소 → AI 설명. 사용자가 다른 AI의 설계 글(분석기·생성기·검증기·로컬 채점·AI 리포트, Python 생성기 + Hypothesis 제안)을 보여 줬고, 그와의 비교는 6절.
4. **코드 실행기 보안**: A 그대로 / B 실행할 코드에 앱 환경 변수를 넘기지 않기(제안, 작음) / C 진짜 샌드박스.
5. 강의 글 → 문제 묶음의 미정 부분(위 1-3).

## 6. 다른 AI의 설계 글과 현재 비교 (사용자가 보여 준 글)

그 글의 구조: AI 문제 분석기 → 테스트 생성기(경계·반례·랜덤·대형, "입력 나열보다 생성기") → 정답 검증기(모범 풀이·완전탐색·불변식, Differential Testing) → 로컬 채점(시간·메모리) → AI 리포트(반례·원인·복잡도). AI 호출은 등록 시와 제출 후 피드백에만. 샌드박스 필수.

| 항목 | 현재 |
| --- | --- |
| 원문·제약·예시 입력 | 있음(붙여넣기, 아카이브). 블로그 긁기 미정 |
| 분석기(범위·형식을 구조화) | 일부(답 종류만 판단) |
| 테스트 생성 규칙·생성기 | 일부(AI가 입력을 글로 8~12개, 실제로는 작음) |
| 제약 위반 입력 거르기 | 없음 |
| 원문 예제 검사 | 있음 |
| 완전탐색 교차 검증 | 일부(원문 예제 없을 때만, 수십 개) |
| 불변식 검사 | 없음 |
| 검증 통과만 저장 | 있음 |
| 로컬 채점 | 있음(Python·JS·C++·C#) |
| 시간 측정·제한 | 있음(2초 고정, 언어 보정 없음) |
| 메모리 측정·제한 | 없음 |
| 동적·정적 복잡도 | 정적만 일부("맞는지 봐 줘") |
| 반례 + AI 설명 | 일부(반례 찾기·힌트) |
| 최소 반례 축소 | 없음 |
| AI 호출 시점 | 거의 같음(채점은 로컬, AI는 요청 때만) |
| 샌드박스 | 없음(의도적) |

그대로 따르기 어려운 점: 생성기·모범 풀이를 Python으로 하면 Python이 없는 PC가 있다(지금 모범 풀이를 JS로 쓰는 이유). Hypothesis는 새 의존성. "수천 개 무작위 비교"는 지금 실행기가 입력마다 프로세스를 새로 띄워 문제 등록이 몇 분 걸린다.

## 7. 다음에 할 일
