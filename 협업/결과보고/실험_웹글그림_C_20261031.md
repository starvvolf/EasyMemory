# 그림 섞인 웹 글을 PDF 없이 지식으로: 네 방법 비교 (C, 2026-10-31)

글: inpa.tistory.com "완전히 정복하는 프로세스 vs 스레드 개념"(본문 약 1.7만 자, 소제목 h2 6개·h3 13개, 그림 32장 중 GIF 3장). 문제는 만들지 않고 지식(카드 + 자료 전체 정리)까지만. 방법마다 한 번씩 돌렸다(새벽 2~3시, 모델 gpt-6.1-terra low).

실험 도구: `src/lib/study/gen/webtrial.ts`, `POST /api/lab/web-trial`. 결과 파일 `tmp/engine-data/study-gen/web-trials/wt_96d31412cca3.json`.

## 방법

| | 방법 | 보내는 것 |
|---|---|---|
| A | 글만 · 소제목 덩어리 | 소제목(h2·h3)마다 16덩어리, 덩어리 글 + 전체 소제목 목록 |
| B | 글+그림 · 소제목 덩어리 | A + 그 덩어리의 그림(1024px) |
| C | B + 글 전체 맥락 | B + 모든 호출 앞에 글 전체(맥락용, 카드는 자기 덩어리만) |
| D | 통째 한 번 | 글 전체 + 그림 31장을 호출 1번에 |

광고·관련 글 카드는 읽을 때 뺐고, 아이콘처럼 작은 그림과 첫 표지 그림은 보내지 않았다. 덩어리 안의 그림은 모두 보냈다(31장).

## 결과

|---|---|---|---|---|
| 카드 | 46 | 52 | 47 | 23 |
| 글에 있는 핵심 29개 중 | **28.5** | 26.5 | **28.5** | 21 |

| 걸린 시간 (카드 → 정리) | 22.6 + 25.2 = 47.8초 | 27.7 + 30.1 = 57.8초 | 24.7 + 24.7 = 49.4초 | 73.2 + 18.0 = 91.2초 |

| 출력 토큰 | 9.0천 | 9.9천 | 8.9천 | 4.6천 |

- **그림에만 있는 핵심 5개:**
  - 스레드 상태 전이(New →Started→ Runnable, →Waiting→ Blocked, →Resumed→, →Finished→ Terminated)
  - 메시지 전달과 공유 메모리 두 가지 IPC 방식
  - PCB 안에 TCB가 줄줄이 이어진 구조
  - 그림 속 스레드 스케줄러 세 방식
  - 멀티 스레드(메모리 하나 공유)와 멀티 프로세스(메모리 따로)
  - 글에는 상태 이름 4개나 "실제로는 더 복잡하다"만 있다.
- **글에 있는 핵심 29개:** 제가 글을 읽고 뽑은 기준 목록(정의, 메모리 4영역과 세부, 공유 범위, IPC, 병렬/동시성, 상태·전이, PCB, 전환 단계와 비용, TCB, 뮤텍스/세마포어, 경쟁 조건 등)이다. 부분만 다룬 것은 0.5로 셌다.
- **흐름:** 덩어리 방법(A·B·C) 모두 자료 전체 정리의 주제가 글 순서 그대로 나왔고, 원리 2개(자원 공유와 격리, 상태 저장·복원 또는 스케줄링)를 잡았다. C의 주제 6개는 글의 h2 6개와 정확히 같은 구조였다. A·B는 9개로 더 잘게 나눴다.
- **잡음:** 관련 글 홍보 문단과 참고 자료 목록에서는 어느 방법도 카드를 만들지 않았다. B·C에 "Stack·Heap 화살표 방향" 같은 그림 사소한 카드가 1장씩(보조) 있었다. "그림의 ○○"처럼 그림을 가리키는 제목이 B·C에 2~3장 있다.

## 읽은 것

1. **그림을 넣어야 그림에만 있는 지식이 들어온다.** 글만(A)은 0/5, 덩어리마다 그림(B)은 5/5. 그림 31장은 입력 약 1.5만 토큰(장당 약 470)이고, 시간은 거의 늘지 않았다.
2. **통째 한 번(D)은 느리고 빠뜨린다.** 출력이 한 줄로 나와 73초가 걸렸고, 카드가 절반(23장)이라 글의 핵심 8개 정도를 놓쳤다(전환 비용의 원인, 경쟁 조건, 스케줄링 알고리즘, 스레드가 나온 이유 등). PDF에서 본 것과 같다.
3. **글 전체 맥락(C)은 이 글에서는 품질 차이가 작고 입력이 3배다.**
   - 글의 핵심은 A·C가 같았다. 그림 핵심은 B보다 2개 적었다(한 번씩 돌린 결과라 이 정도 차이는 우연일 수 있다).
   - 이 글은 소제목이 촘촘해서 덩어리만으로도 흐름이 잘 살았다.
   - **캐시가 거의 안 걸렸다**(23만 중 2.2만). 16개를 동시에 보내면 첫 호출이 캐시를 만들기 전에 나머지가 출발해서다. 하나를 먼저 보내고 나머지를 보내면 캐시가 걸리지만, 그만큼(약 5초) 늦어진다.
4. **시간은 낮 측정의 약 두 배였다.** 오늘 새벽 출력 속도가 초당 55토큰으로, 어제 낮(117)의 절반이었다. 그래서 낮이면 B도 카드 약 12~14초에 정리까지 약 25~30초로 보인다(추정). 가장 늦은 덩어리는 글이 길고 그림 5장인 "컨텍스트 스위칭" 구역(출력 약 1천 토큰)이었다.

## 제안

- **기본은 B(소제목 덩어리 + 그 덩어리의 그림).** 그림 지식을 다 잡고, 비용은 글만보다 약 1.2배다.
- **글 전체 맥락(C)은 소제목이 없거나 드문 글에서만 다시 재 본다.** 그때는 캐시가 걸리도록 하나를 먼저 보낸다.
- **그림 고르기를 더 하면 잡음과 입력이 준다.** 작업 관리자 화면, 쇼핑몰 CPU 목록, 사진 같은 그림은 저화질로 한 번 보고 거르면 된다(PDF 쪽 의도 판정과 같은 방식).
- **실제 기능에서는 사용자의 브라우저가 본문을 읽는다.** 이번 실험은 서버가 글을 받아 같은 규칙(소제목·문단·목록·표·그림 순서, 관련 글·광고 제외)으로 읽었다.
  - 사용자 브라우저에서 보내는 길(다리 페이지)은 이 앱 내장 브라우저에서 막혔다. iframe이 막히고, 새 창 버튼은 클릭이 먹지 않았다.
  - 확장(B 담당)으로 보낼 때는 이 문제가 없다.
