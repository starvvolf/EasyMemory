## 1. 튜터는 코드를 어떻게 보나

### 튜터가 파일을 왜 안 읽나?
- 튜터가 아예 안 읽은 건 아니다. FPS 시뮬에서 파일을 6번 읽었다.
  - 저장했을 때 4번: 코드가 "이 파일을 읽고 확인해 달라"고 시킨다.
  - 오류가 났다고 했을 때 2번: 원인을 찾으려고 스스로 열었다.
- "됐다"고 하면 한 번도 안 읽었다. 이유는 두 가지로 본다.
  - 터미널 출력이 이미 맥락에 있어서, 결과만 보고 충분하다고 여겼다.
  - 지시가 "필요하면 read"로 튜터에게 맡겨져 있었다. 생각 강도도 low였다.
- "코드를 보여 주세요"라는 말은 우리 코드가 시킨 것이었다. 판정이 "근거 부족"이면 그렇게 넘기게 되어 있었다.
- 놓친 예: 응답에 넣는 값을 lock 밖에서 읽는 실수가 있었다. 출력이 맞게 나와서 튜터가 못 잡았다.

### low와 medium은 차이가 있나?
- 아마 있다. medium이면 "확인하고 말할까"를 더 따지니 도구를 더 부르는 편이다.
- 장담은 못 한다. 지시가 "필요하면 읽어라"인 동안은 medium도 안 읽을 수 있다. 대가로 매 답이 느려진다.
- → 생각 강도는 채팅마다 학습자가 고르게 했다. 기본은 low다.

### 매번 읽는 건 비효율적이지 않나? 열린 파일을 코드로 바로 보내면 뭐가 문제인가?
- 코드로 보내는 것 자체는 도구보다 빠르다.
- 다만 매 차례 열린 파일을 통째로 보내면 세 가지가 걸린다.
  1. 같은 코드가 대화에 계속 쌓인다.
  2. 열린 파일이 정작 고친 파일이 아닐 수 있다.
  3. 상관없는 질문에도 코드가 끼어 답이 산만해진다.
- 그래서 이렇게 정했다.
  - **언제:** 지난번에 보낸 뒤 바뀐 파일만 보낸다.
  - **무엇을:** 열린 파일과, 그 사이 저장된 다른 파일까지 보낸다.
  - **얼마나:** 150줄 이하는 통째로, 크면 바뀐 줄만 보낸다.
- → `lib/changes.ts`. 머리말은 `[지난번 뒤 바뀐 코드 — 파일, 저장됨 | 저장 안 함(실행하면 아직 예전 코드로 돌아요)]`이다.

### Ctrl+S를 안 해도 바뀐 걸 아나?
- 지금 보고 있는 파일 하나는 안다. 연결 확장이 키를 멈추고 1.2초 뒤 열린 파일의 현재 내용을 보낸다.
- 다른 탭에서 고치고 저장하지 않은 파일은 모른다.
- 실행은 디스크에 저장된 파일로 돈다. 그래서 "저장 안 함"을 따로 표시해, 저장 안 하고 실행해서 예전 결과가 나오는 일을 튜터가 짚게 했다.

### Codex · Claude Code · Cursor · OpenCode는 코드를 바로 보나, 불러서 보나?
- 대부분은 도구를 불러서 읽는다. 매 차례 자동으로 붙는 건 열린 파일 이름과 고른 줄 정도다.

| 도구 | 자동으로 붙는 것 | 파일 내용 |
|---|---|---|
| Claude Code (VS Code) | 고른 코드는 내용째, 열린 파일은 이름만 | 필요할 때 Read로 읽음. 이미 읽은 파일이 밖에서 바뀌면 바뀐 부분을 알려 줌 |
| Cursor | 열린 탭을 이름만 | 에이전트가 필요하면 읽음 |
| Codex (IDE) | 사용자가 직접 붙인 파일 · 선택 | 아니면 셸 명령으로 읽음 |
| OpenCode | `@파일`로 붙이면 내용째 | 아니면 read로 읽음 |

- → 우리는 Claude Code 쪽 방식을 따랐다. 바뀐 코드는 코드가 알려 주고, 그 밖에 필요한 건 튜터가 읽는다.

### `.class` 파일이 깨진 글자처럼 보이는데 VS Code 문제인가?
- 아니다. `.class`는 컴파일된 결과물(바이너리)이라 원래 사람이 읽는 글이 아니다. VS Code에서 열어도 똑같이 보인다.
- 고치려면 같은 이름의 `.java` 소스 파일을 열면 된다.

## 2. 실습 화면의 버튼

### 버튼 하나하나에 의미가 있나?
→ 이렇게 정리했다.
- 홈 버튼은 하나만 둔다.
- 도움 다이얼(스스로 · 같이 · 빨리 만들기)에 마우스를 올리면 설명이 뜬다. "빨리 만들기"를 고르면 튜터가 파일을 고치는 것도 허락된다.
- 모델과 생각 강도는 학습자가 고른다(GPT-6.1 terra · sol, GPT-6 luna / 생각 적게 · 보통 · 많이).
- [기록]은 개발자 모드(`?dev=1`)에서만 보인다.

### 탑다운 · 바텀업 질문은 빼도 문제없나?
- 문제없다. 튜터가 학습자의 말과 수준을 보고 계획을 짤 때 직접 고른다. 처음 해 보는 분야면 바텀업으로 간다.

### 튜터가 "다 했으면 이 버튼 눌러라"라고 하는 이유는?
- 11/5~6에는 튜터에게 버튼을 안내하라는 지시가 있었다.
- 11/8에 "버튼을 잘 다듬으면 사용자가 누르겠지"로 정하고 그 지시를 뺐다. 지금 지시는 "답에서 버튼을 누르라고 안내하지 않는다"이다.
- 기록을 찾아보면 그런 말은 11/5~6 대화에만 있다.

### 버튼 배치 (11/13)
- [이해했어요 → 적용하기] · [해 봤어요] · [다음으로]를 채팅창 위 [너무 쉬워요] · [너무 어려워요] 옆으로 옮겼다.
- 다이얼의 "도움"은 누르는 버튼이 아니라 제목으로 보이게 바꿨다(점 · 구분선 · 굵은 글씨).
- 실습 화면의 "배운 것 · 부족했던 점 · 끝낸 목표" 칸은 뺐다. 목표 정리는 기억 도서관 리뷰에서 본다.

## 3. 목표 흐름

### 선행은 뭐였나? 처음 설문 결과인가?
- 로드맵의 앞 단계도 아니고 설문도 아니다. 단기 목표마다 튜터가 붙이던 바탕 지식 목록 3~5개였다. 학습자가 "알아요 / 몰라요"를 표시할 수 있었다.
- 설문은 맨 처음 한 번, 무엇을 어느 수준으로 만들지 정하려고 묻는 것이다.

### 선행이 꼭 필요한가?
- 시뮬을 해 보니 목록은 꼬박꼬박 붙었는데, 학습자가 표시하거나 튜터가 확인한 적은 거의 없었다.
- 실제로 비어 있는 곳은 대화 · 판정 · 막힌 순간에서 드러났다.
- → **선행 시스템 전체를 뺐다(11/12).** 11/13에는 판정 · 부족함 원장 · 목표 정리 카드 · 학습 노트에 남아 있던 선행 칸도 뺐다.

### 터미널도 들어가나?
- 들어간다. 연결 확장이 학습자가 친 명령과 출력을 실습 서버로 보낸다.
- 지난 차례 이후 친 명령이 최대 5개까지 튜터 맥락에 붙는다. 그래서 "오류 떴어"라고만 해도 튜터가 실제 오류 문구를 본다.
- 같은 기록을 판정과 막힌 순간에도 쓴다.

### 현재 목표 · 완료 조건 · 이해 · 적용은 구체적으로 어떻게 도나?
- **완료 조건:** "이 목표를 끝냈다고 칠 수 있는 장면" 한 문장이다. 학습자가 직접 해 보고 확인할 수 있게 쓴다.
  - 예: "서버를 켠 상태에서 별도 클라이언트가 연결해 메시지를 보내고 응답을 확인한다."
- **① 이해:** 튜터가 설명한다. 설명의 예는 적용 과제와 다른 상황으로 든다. 이해했는지는 AI가 판정하지 않고, 학습자가 [이해했어요]를 누르면 코드가 바꾼다.
- **넘어갈 때:** [이해했어요]를 누르면 코드가 튜터에게 "완료 조건을 직접 해 볼 작은 과제 하나를 내라"고 넘긴다. 완성 코드는 주지 말고, 처음 쓰는 이름은 같이 알려 주라고 한다.
- **② 적용:** 학습자가 [해 봤어요]를 누르면 판정 AI가 비교해서 맞음 · 일부 · 틀림 · 근거 부족을 낸다.
  - **맞음:** 이때만 "적용 ✓"가 된다.
  - **일부 · 틀림:** 빠진 곳이 부족함 원장에 올라간다.
- **[다음으로]:** 언제든 누를 수 있다. 이해 · 적용을 다 안 했으면 "건너뜀"으로 남는다.
- 보충 단계도 ① → ②를 똑같이 거친다.

### 지도는 로드맵인가?
- 같은 것이다. 코드 안에서는 `map`, 화면에서는 "로드맵"이라고 부른다.

### [너무 어려워요]를 누르면 보충은 어떻게 진행되나?
1. 이유 6개 중에서 고르거나 직접 적는다. 안 골라도 된다.
2. [이걸로 도와줘요]를 누르면 코드가 기록한다. 막힌 순간 · 부족함 · 학습 기록을 남기고, 고른 이유마다 정해 둔 "채우는 법"을 붙여 튜터에게 넘긴다.
   - 예: "코드로 못 옮기겠어요" → 빈칸 한두 개짜리 코드
3. 튜터가 막힌 목표에 닿는 보충 단계 1~4개를 짠다. 이유만 보지 않고 대화 · 코드 · 터미널도 본다. 이때 원래 로드맵은 잠시 보관된다.
4. 보충 단계마다 이해 → 적용을 거친다.
5. 막힌 목표로 돌아와 한 걸음 나아가면 보충이 닫히고 원래 로드맵으로 돌아간다.

- 보충 중에 또 막히면 남은 보충을 더 쉽게 다시 짠다(2번째 보충).
- 3번째쯤 되면 튜터가 목표를 낮추거나 기초부터 깔자고 제안한다.
- → 버튼 이름을 [보충 로드맵 짜기]에서 [이걸로 도와줘요]로 바꿨다.

### 튜터가 낸 적용 과제의 질은 어떤가?
- 기록에 남은 과제 15개를 봤다.
  - **의미 있음 6개:** 결제 취소 추가, PATCH · DELETE 추가 등.
  - **작지만 쓸 만함 4개.**
  - **사실상 "다시 실행" 5개.**
- 까닭은 세 가지다.
  1. 완료 조건이 "실행하고 확인한다" 꼴이었다.
  2. 이해 단계에서 코드가 이미 완성됐다.
  3. 기대 출력을 과제에 그대로 적어 줬다.
- → [이해했어요] 지시에 두 가지를 더했다(지시문 승인): "코드가 이미 있으면 조건을 하나 바꾼 변형을 내고, 정답 코드나 기대 출력을 적지 않는다."

## 4. 판정과 튜터 맥락

### 완료 조건(판정)은 잘 동작하나?
- 실제 판정 25번 중 맞음 15번, 일부만 4번, 근거 부족 6번이었다.
- 맞음과 일부만은 대체로 적절했다.
- 근거 부족 6번 중 4번은 학습자가 했다고 말했는데, 판정이 코드를 못 본 경우였다. 판정이 [이해했어요] 뒤에 저장한 코드만 봤기 때문이다.
- → 학습자가 말이나 명령으로 해 본 게 있으면, 저장했거나 열린 파일의 지금 내용을 판정에 같이 넘긴다. 3개까지 넘긴다.

### 판정은 AI가 하나, 코드가 하나?
- 판정은 AI가 [해 봤어요]마다 1번 한다.
- 코드는 판정에 넘길 자료를 모으는 일만 한다. 대화, 저장본, 작업 폴더 파일, 터미널을 모아 붙인다.

### 매 차례 튜터에게 무엇이 들어가나?
- **고정(캐시):** 지시 · 튜터 규칙, 도구 목록, 실습 안내, 지난 차례들.
  - 11/13에 매번 같은 규칙(답에 반응하기 · 학습자가 물을 때 · 이름 알려 주기 등)을 차례 맥락에서 고정 지시로 옮겼다.
- **이번 차례:** 학습자 메모리, 학습 노트, 목표 · 로드맵 · 단계, 도움 다이얼, 복습에서 또 틀린 것, 터미널 명령, 바뀐 코드, 그리고 학습자 말이나 버튼 말.

### 도움 정도, 학습 노트, 다시 틀린 것은 뭔가?
- **도움 정도:** 다이얼이다(스스로 · 같이 · 빨리 만들기). 고른 칸의 규칙 한 줄만 붙는다.
  - 예: 같이 = "틀은 주고 핵심은 학습자가 채우게, 두 번 해도 안 되면 보여 준다"
- **학습 노트:** 지금 실습 하나가 아니라 모든 실습을 합친 요약이다. 아직 모르는 것, 이제 되는 것, 확인된 환경이 들어간다.
- **다시 틀린 것:** 예전 실습에서 틀렸던 것을 며칠 뒤 복습에서 다시 물었는데 또 틀린 것이다. 최대 3개 붙인다.

### AI 도구 중 "질문"은 뭔가?
- 학습자에게 보기를 골라 답하게 하는 도구다.
  - **ask_questions:** 맨 처음 무엇을 만들지 정하는 설문이다. 3~5개를 묻는다.
  - **보기 2~4개로 한 번 묻기:** 대화 중 갈래가 나뉠 때 쓴다.

## 5. 목표가 끝난 뒤 정리(리뷰)

### 실습이 끝나면 어떻게 정리하나?
- 목표마다 AI를 1번 부른다.
- **재료:** 코드가 모은다. 목표, 완료 조건, `[결과]` 한 줄, 그 목표 동안의 대화 · 저장한 코드의 바뀐 줄 · 터미널 · 막힌 순간 · 부족함 원장 · 학습자 메모리가 들어간다.
- **11/13부터 B의 "AI 학습 리뷰어 3차"를 실습 말로 바꿔 쓴다.**
  - JSON 대신 글로 받는다: 학습 총평 → 끝났을 때 상태 → 주제별 [핵심] / [작은] → 자잘하게 막힌 것 → 다시 확인할 것.
  - 원장 · 다시 확인 · 메모리 · 앱 기억에 필요한 것은 같은 글 끝의 `# 기록용`에 정해진 꼴로 받아 코드가 읽는다.
  - `[결과]` 줄은 코드가 센다: 마침/건너뜀, 판정 수, 너무 어려워요 · 보충, 다이얼, 한 말 수, 터미널(실패), 튜터가 고친 파일, 걸린 분.
- 하다가 나간 목표(손 놓고 15분)는 "진행 중"으로만 정리한다. 원장 · 메모리 · 앱 기억에는 넣지 않는다.

### 바꾼 리뷰의 내용은 어떤가? (C# 서버 실습 목표 3개로 확인)
- **좋은 점**
  - 학습자가 실제로 친 코드 · 오류 · 출력에서 출발한다.
  - 기록에 없는 건 "확인 안 됨"으로 깐깐하게 남긴다.
  - 판정 기록과 실행 출력을 구분한다.
  - 해설이 실제로 배울 만하고, 다시 확인 문항도 상황을 바꿔서 묻는다.
- **버그 하나:** 목표 기록의 끝 시각이 정리가 끝난 때(AI 약 1분 뒤)로 찍혀, 다음 목표 내용이 앞 목표 리뷰에 섞였다.
  - → 끝 시각은 정리를 부른 때로 찍고, 다시 정리할 때는 다음 목표 시작에서 자른다.
- **시간:** 목표당 50~60초로 예전 JSON과 비슷하다. 출력 길이가 비슷해서다.

### 본 앱에서 보이나?
- 보인다. 기억 탭 → 실습 → 그 실습을 열면 목표마다 리뷰가 나온다. 화면 부품은 알고리즘과 같은 `MdReviewView`다.
- 지금 새 리뷰로 다시 정리된 건 C# 실습뿐이다. 다른 실습은 예전 모양으로 보인다.

## 아직 정하지 않은 것
- 판정이 "근거 부족"일 때 튜터에게 넘기는 말: "보여 달라고 해 주세요" 대신 "파일을 먼저 읽고"로 바꿀지.
- 학습자가 원하는 설명 스타일(말투 · 탑다운 · 쉬운 예시 등)을 기억하게 할지.
- 목표 버튼(이해했어요 · 해 봤어요 · 다음으로 · 너무 쉬워요 · 너무 어려워요)을 더 합칠지.
- 실습을 시작할 때 AI가 먼저 말을 걸지.
- 예전 실습들도 새 리뷰로 다시 정리할지(목표마다 AI 1번).
