## Claude가 판단할 것

1. **다음 구현의 중심은 실험판 대화 방식으로 잡는 것을 권한다.** 사용자가 실제로 선호한 방식이며, 원하던 “자연스러운 챗봇 + 학습 조정 도구”와 구조가 더 가깝다. 기존 엔진의 검사·파일·사건·지식 기능을 필요한 도구로 연결하는 제안이다. 이번 보고서에서 기존 코스를 교체하지 않았다.
2. **기존의 상세 대화 규칙을 그대로 다시 붙이지 않는 것이 중요하다.** 검사 조건·권한·기록 출처는 코드와 도구 계약으로 유지하고, 말투·설명 순서·비유·확인 질문의 시점은 모델이 결정하도록 하는 방향이다. 기존 규칙 중 필요한 것은 실패를 관찰한 뒤 개별적으로 복원할 수 있다.
3. **“이해했는가”의 AI 판단과 “검사에 통과했는가”의 실행 사실을 끝까지 구분해야 한다.** 현재 실험판은 관찰만 갖고 있고 기존 코스의 검증된 학습 사건과 아직 연결되지 않았다.
4. **품질 우위·속도 우위·비용 우위는 별도 확인이 필요하다.** 지금의 사용자 체감은 중요한 관찰이지만 동일 질문·동일 파일·동일 학습 상태의 비교는 아니다. 이를 근거로 곧바로 “더 빨라졌다”, “더 싸다”, “더 잘 가르친다”는 수치를 만들 수 없다.

## 자세한 내용

### 1. 비교 범위와 확인 방법

2026-11-04 한국 시간의 현재 로컬 작업트리를 읽었다. “기존”은 lesson.ts를 거치는 코스 튜터이며, “실험판”은 agent-chat.ts와 agent-chat-policy.ts를 거치는 `/agent-chat.html`이다. 기존 코스 중 hello-api의 준비된 수업과 AI 생성 코스의 talkMemo도 구분했다.

현재 프롬프트 설정, 실제 모델 요청 JSON, usage.jsonl, 실험 대화의 메시지 역할·상태 변경 횟수를 확인했다. 인증·헤더·개인 대화 본문을 보고서에 옮기지 않았다. 실제 모델을 새로 호출하지 않았고, 이번에는 비교 대상 코드를 수정하거나 모델 품질 시험을 추가로 실행하지 않았다.

실험판 구현 소스 중 일부는 현재 로컬의 미커밋 파일이다. 따라서 현재 화면·소스를 비교한 보고서이며, HEAD만 다른 PC에서 읽으면 동일 구현이 모두 포함돼 있다고 가정하면 안 된다.

### 2. 가장 큰 변화: 진행을 결정하는 위치

기존 흐름은 다음과 같다.

```text
코스 계획서 → 현재 걸음·대기 상태 → 화면의 설명/문제/버튼
                              ↘ 질문이 오면 상태에 맞춰 튜터 호출
                              ↘ 검사·선택·다음 버튼으로 걸음 전환
```

실험판 흐름은 다음과 같다.

```text
학습자 메시지 + 앞 대화 + 현재 학습 상태 → 모델이 답과 다음 도움을 결정
                                           ↘ 필요할 때 자료/실행 도구
                                           ↘ 필요할 때 학습 조정 도구
                                              → 코드 검증·저장 → 상태 패널
```

기존에서는 AI가 자연스럽게 답해도 다음 진행 단위는 이미 plan.beats에 있다. 사용자 질문은 수업에서 잠깐 벗어난 대화로 기록하고 돌아오는 흐름과 연결된다. 실험판은 사용자 질문 자체를 현재 학습 활동으로 취급한다. “지금은 함수가 궁금하다”면 목표를 유지하면서 초점만 함수로 바꿀 수 있다.

이 차이가 사용자가 말한 “알아서 상황에 맞게 도와준다”는 느낌에 직접 연결될 가능성이 크다. 근거: [S2], [S3], [S4].

### 3. 고정 지시문의 변화: 덜 시키고 더 판단하게 함

기존 SYSTEM에는 자연스럽게 설명하라는 문장과 함께 상세 행동 지시가 들어 있다. 답변 길이, 첫 문장의 역할, 코드 이름의 표기, 파일·줄 링크, 도구 전 안내, 초보에게 끝에 붙일 행동, 힌트 3단계, 예측 답 보호, 완성 코드 공개 조건, 수업 순서 유지, 돌아가기 안내 조건 등이다.

이 규칙은 각각 원래 목적이 있다. 예측 문제의 답을 지키고, 학습자를 길 잃게 하지 않고, 대신 개발해 버리는 일을 막으려는 것이다. 다만 모델 입장에서는 질문에 답하는 일 외에 현재 걸음과 공개 수준, 화면 버튼, 문장 형식을 계속 맞춰야 한다.

실험판의 기본 지시문은 역할·자연스러운 대화·배경에 맞춘 설명·도구의 의미·관찰의 출처에 집중한다. “3~8문장/700자”, “한 질문에 힌트 한 단계”, “계획서 순서를 바꾸지 말 것”, “완성 코드는 특정 조건에서만” 같은 강제는 없다. “필요할 때 예시나 코드를 주고 설명 방식은 상황에 맞게 정하라”는 방향이다.

문자열 길이를 코드에서 읽으면 기존 기본 SYSTEM 2,157자, 실험판 기본 CHAT_SYSTEM 805자다. 이는 JavaScript 문자열 length로 센 값이며 토큰 수가 아니다. 길이 자체가 품질을 보장한다는 뜻도 아니다. 중요한 변화는 수업 진행과 표현 방식에 대한 강제 조건이 줄었다는 점이다.

실제 요청 기록에서도 기존 지시문은 추가 안내를 포함해 2,257자, 실험판은 805자였다. 조사 시점의 두 편집 설정은 각각 기본값과 같았다. 근거: [S1], [S4], [E1].

### 4. 질문에 따라 설명을 펼칠 여지가 커짐

가상의 예로 “REST API가 왜 필요하고 작은 예제로 보여 줄 수 있나요?”를 생각할 수 있다. 이는 관찰된 사용자 문장을 복사한 것이 아니라 동작 차이를 설명하기 위한 예다.

기존 튜터는 현재 예측 문제나 수정 과제의 답을 미리 공개하지 않아야 한다. 어느 걸음인지 확인하고, 완성 코드가 아닌 범위에서 설명하고, 보통 한 화면 안으로 답해야 한다. 학습자가 코드를 고쳐 달라고 하면 별도 [만들어 주세요] 동작으로 안내한다. “구조”나 “흐름” 같은 말은 TOUR_INTENT에 걸려 투어 모드로 바뀔 수도 있다.

실험판은 질문 의도에 맞춰 목적 설명 → 작은 코드 → 실행 방법을 한 답변에서 이어 갈 수 있다. 답의 길이나 코드 공개 여부를 별도 수업의 정답 보호 조건과 맞출 필요가 없다. 질문에서 “구조”라는 단어를 썼다는 이유로 투어 전용 도구 모드로 전환하지도 않는다.

따라서 “내 질문에 바로 충분히 답한다”는 체감이 좋아질 수 있다. 반면 정답을 직접 만들어 보게 하는 연습 장치를 제거한 효과도 있다. 설명 만족도와 실제 독립 수행 능력은 따로 확인해야 한다. 근거: [S1], [S2], [S4], [S5].

### 5. 맥락의 변화: 더 가벼워졌지만, 더 많이 아는 것은 아님

기존 askInner는 코스 전체 순서·이번 단계 목표·가르칠 개념·수정 과제·강사 메모·숨길 답을 고정 맥락으로 만든다. 매 차례에는 배경·내부 레벨·실패 횟수·힌트·검사 결과·고친 파일·VS Code 오류·현재/다음 걸음·화면 버튼·개념 상태·기초 기록·선택한 코드 등을 넣는다. 필요한 파일도 미리 붙인다.

실험판은 짧은 코스 안내와 목표·초점·보충 스택·최근 관찰·최근 학습자 메시지를 넣고, 자료와 파일은 필요하면 도구로 읽게 한다. parts.files는 비어 있다. 구체적인 코드 질문에 필요한 파일을 이미 안다고 가정할 수 없으며, 모델이 자료를 읽지 않고 추측하면 잘못된 답이 나올 수 있다.

### 7. 학습 상태의 의미와 코드가 보장하는 범위

기존 learner.ts는 예측·검사·도움 여부·자기 설명 같은 사건에서 new/learning/understood/weak를 계산하고 verified를 관리한다. AI가 남긴 관찰은 별도다. 전체 코스의 학습 근거를 계산하려는 모델이다.

실험판 상태에는 goal·focus·support·observations가 있다. observations는 모두 verified:false다. 모델은 실제 학습자 메시지 id와 그 메시지에 포함된 문구를 인용해야 이해·혼란·오개념 관찰을 남길 수 있다. 코드는 인용이 실제 메시지에 있는지를 검사하지만, 그 인용이 개념 이해를 입증하는지까지 의미적으로 채점하지 않는다.

보충 복귀는 현재 supportId와 보충을 연 뒤 받은 답변을 요구한다. 복귀하면 위 칸도 새 답변을 요구하도록 기준을 갱신해, 같은 답변으로 여러 칸을 연속 닫는 것을 막는다. 이것은 이전 검토에서 지적한 연속 닫힘 경로를 실험판에서는 막은 것이다. 기존 stuck.ts의 결함을 수정했다는 뜻은 아니다.

실험판이 모든 의미 판단을 코드로 옮긴 것은 아니다. 오히려 “어떤 도움이 필요한가”는 모델에 맡기고, 실제 근거·저장·동시성·상태 전환 계약을 코드가 담당하게 범위를 정했다. 근거: [S3], [S7], [S8].

### 8. 실제 대화에서 확인한 것과 아직 확인하지 못한 것

현재 실험 기록은 학습자 메시지 4개, 초기 안내를 포함한 assistant 메시지 5개, 도구 상태 기록 2개다. 두 상태 기록은 모두 초점 변경이었다. 보충 스택은 0개, 이해도 관찰도 0개다.

반면 이 기록만으로 학습자의 오개념을 적절히 찾아냈는지, 어려워하는 지점에서 아래 개념으로 내려갔는지, 확인 질문이 적절했는지, 원래 과제로 잘 복귀했는지는 평가할 수 없다. 자연스러운 설명 요청만 이어진 대화에서 관찰 도구를 쓰지 않은 것을 곧바로 결함이라고 할 수도 없다.

### 10. 기존 기능을 뺀 효과와 아직 연결하지 않은 것

기존 코스가 맡던 책임은 실험판보다 크다. 실제 실습 서버의 요청·검사, 직접 고침과 도움받음 구분, 예측·단계 완료, VS Code 선택 코드·오류·저장 이벤트, 앱 지식 동기화, 생성 코스 관문 등이 있다. 실험판은 이 책임을 다 이어받지 않았다.

현재 실험판에서 코드를 설명하거나 실행 방법을 알려 줄 수는 있어도, 사용자가 실제 프로젝트에서 그 코드를 실행해 통과했는지를 자동 검사하지 않는다. 파일을 고치는 도구도 없고, 현재 코스 단계 완료를 기록하지 않으며, 보충과 관찰을 앱 지식으로 보내지도 않는다. 코스 재시작은 새 대화·초기 상태·새 시작 코드 폴더를 만드는 기능이다.

따라서 실험판의 대화 만족도에는 강제 순서와 책임 범위를 줄인 효과가 함께 들어 있다. 이후 기존의 실행 확인과 기록 기능을 연결하면서도 현재의 자유로운 대화를 유지하는지가 제품 전환의 핵심이다.

특히 준비된 hello-api 수업은 1단계에 11개 걸음이 있다. AI 생성 코스는 이미 설명 부분을 talkMemo 대화 걸음으로 바꿨지만 그 뒤 예측·보내 보기·고치기·설명·정리 순서는 남아 있다. “기존은 전부 고정 대본, 새것만 대화”라고 단순화하는 것도 정확하지 않다. 근거: [S5], [S9], [S10].

### 11. 다음 구현에 대한 권고
