# PDF 자료 만들기 — AI 호출 시간·토큰·비용 분석 (11/11)

읽기만 했다. 저장소·앱·AI는 건드리지 않았다. 숫자는 모두 스크립트로 셌다(맨 끝 "다시 돌리기").
비용은 `src/lib/ai/prices.ts` 값으로 "API였다면"의 달러다. 앱은 ChatGPT 구독으로 부르므로 실제로 나가는 돈은 아니다.
시각은 한국 시간(KST)으로 적었다. 기록 파일 이름의 날짜는 UTC다.

## 한눈에

- **가장 중요한 사실: 자료를 만드는 AI 호출(줄기 계획·기억 채우기·학습 목표)은 `ai-calls/` 기록에 하나도 없다.** 엔진은 호출을 `study-gen/<id>/calls/N.json`에 따로 남기고(동기화 안 함), 강의 호출은 `assist-log.jsonl`에만 남긴다. 그래서 받은 기록 889건은 대부분 [문제 만들기]와 실험이다.
- 자료 만들기 시간은 실행 기록(state.json) 하나로만 볼 수 있었다: 50쪽 110초 = 전처리 9초 + 줄기 계획 53초 + 기억 채우기 44초 + 그림 자르기 4초. 토큰은 모른다.
- [문제 만들기](시험지 설계)는 14번 기록이 있다: 한 번에 35~74초, $0.07~0.27. 시간은 쪽 수에 거의 비례하지 않는다(14쪽과 52쪽이 비슷). **설계 호출 하나가 전체 시간의 34~74%(중앙 60%)** 다.
- 문제 만들기 비용의 50%는 문제 쓰기, 28%는 상황 확인이다. 같은 문제의 쓰기·확인·풀기가 같은 [기억]+[원문]을 세 번 보내고, 캐시는 거의 안 맞았다(입력 74만 토큰 중 캐시 8천).

- 예상 절감: 확인 $0.70 → $0.35, 문제 만들기 전체의 **-14%**. 시간: 이 기록에서 terra가 sol보다 빠르지 않아(초당 56 vs 58) 이득 없음. (설계 $0.37→$0.18, 쓰기 $1.27→$0.63도 같은 계산이지만, 쓰기·설계는 품질 위험이 커서 권하지 않음.)
- 품질 위험: 중간~높음. 다시 쓰기 19번 중 16번을 확인이 잡았다. terra가 덜 잡으면 함정 없는 문제·전제 틀린 문제가 나간다.
- 확인: 새로 만들 필요 없이, 기록된 확인 143건을 실험실 "이 호출만 다시"(현황 11/7)로 terra에 다시 보내 ok/problems가 sol과 같은지(특히 sol이 ok=false였던 것을 terra도 잡는지) 본다. 그다음 14·20쪽 실행 전후 다시 쓰기 수·내지 않은 문제 수 비교.

### 후보 5. 다시 쓰기를 기다리지 않고 통과한 문제부터 내기 (문제 만들기, 기다리는 시간)
- 무엇: recaller.ts:1804–1806은 모든 문제(다시 쓰기 포함)가 끝나야 publish한다. 통과한 문제를 먼저 내고, 다시 쓴 문제는 끝나는 대로 붙인다.
- 예상 절감: 다시 쓰기가 있던 실행에서 늘어난 시간 0~22초(표 2-2 마지막 칸). 토큰 0. 첫 문제까지의 시간은 "설계 + 가장 늦은 첫 검토"(설계 뒤 10~20초)로 줄어든다.
- 품질 위험: 없음(같은 문제). 화면에서 문제 수가 늦게 늘어나는 것만 다름.
- 확인: 14·20쪽으로 [문제 만들기] 누른 뒤 첫 문제가 보이는 시각·마지막 문제 시각을 전후 비교, 문제 목록이 같은지.

### 후보 6. 아주 작은 PDF(1~3쪽)는 줄기 계획과 채우기를 한 번에 (자료 만들기, 시간)
- 무엇: 쪽이 적으면 계획 → 채우기의 두 번 기다림이 시간 대부분이다(첫 글자 대기 2~3초씩 + 계획 출력). 기억이 몇 개뿐이면 한 호출이 영역·기억을 바로 채워 쓰게 한다(STEM_PLAN + STEM_FILL 규칙, 출력은 stemFillSchema + 영역).
- 예상 절감: 계획 호출 1번 몫(시간 기록 없음; 50쪽 계획 53초는 큰 자료 값이라 쓸 수 없음). 토큰: 쪽 글·그림을 두 번 보내던 것을 한 번으로.
- 품질 위험: 중간. 기억 나누기와 채우기를 한 호출이 하면 기억 이름·묶음이 흐트러질 수 있다(11/9 합치기 실험에서 "one" 한 번 방식은 77.8초로 오히려 길었다 — 큰 자료에서는 안 됨).
- 확인: 1·2·3·5쪽만. 전후 시작~끝 시간, 기억 수·쪽 덮음, 카드 블라인드 비교. 5쪽에서 나빠지면 기준을 3쪽 이하로.

(넣지 않은 것: 학습 목표 `rc-q-goals`를 문제 만들 때로 미루기 — 자료 만들기 시간엔 영향이 없고(채우기와 동시), 문제 만들 때 설계 앞에 30초가 더 붙는다. 사용자가 문제를 안 만드는 자료가 많다면 토큰 절감 후보가 된다.)

## 5. 기록으로 알 수 없는 것

- **자료 만들기 호출의 토큰·비용·호출별 시간**: `gen:` 호출이 ai-calls에 0건. 50쪽 실행 하나의 state.json 시간만 있다. 줄기 계획·빠진 쪽·채우기 묶음 하나하나의 ms·firstTextMs·토큰은 PC의 `RecallerData/study-gen/<id>/calls/*.json`에 있다(동기화 안 함). 이것을 올려 주면 1·2·3·5·10·14·20쪽 비교가 된다.
- **강의 v3(영역 한 흐름) 호출**: ai-calls 0건, 받은 데이터에 `lecture-areas.json`도 없다. 토큰은 `assist-log.jsonl`에만 있다.
- **11/11 낮의 호출**: 기록 파일은 UTC 11/9·11/10 두 개뿐이다. KST로는 11/9 21:22 ~ 11/11 02:29까지다. 11/11 02:29 KST 뒤(UTC 11/10 17:29 뒤)의 호출, 11/11 결정들(기억 카드 세 겹·idea·details, 모양 칸 강제 안 함, 강의 v3) 뒤의 자료 만들기·문제 만들기는 기록이 없다. 그래서 지금 지시문으로 만든 카드의 채우기 출력 길이는 모른다(details·idea가 늘어 채우기가 길어졌을 수 있음).
- **문제 만들기 기록의 자료가 "지금 지시문"으로 만든 자료인가**: 기록의 문제 만들기 14번은 11/10 새벽 실험(지시문을 바꿔 가며)이다. 앱에서 [문제 만들기]를 눌러 한 실행과 quiz-lab2 실험 실행은 기록에서 구분되지 않는다(같은 purpose).
- **쪽 수**: 기록에 나온 가장 큰 쪽 번호로 적었다(그래픽스 52, 반도체 52, 데드락 14). 자료 전체 쪽 수와 다를 수 있다. 1·2·3·5·10·20쪽 자료의 기록은 없다.
- **테스트 PDF로 돌린 기록**: 없다(11/11 준비만 됨).
- 내지 않은 문제(held) 수: 기록만으로는 셀 수 없다(코드 판정 결과는 실행 데이터에 있음).
