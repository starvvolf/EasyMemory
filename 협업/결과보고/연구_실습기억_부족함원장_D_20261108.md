## 한 줄 결론

예전 시스템은 부족함을 **찾고 알려 주는 데서 끝났다**. 앱 복습은 지식의 뜻만 묻고, 실습에서 잡힌 틀린 생각 · 틀린 코드는 화면에 보이기만 했다. 그래서 **부족함 원장**을 만들었다. 학습 중에 부족함 하나하나에 id를 붙여 찾기 → 채우기(보충) → 세션 안 확인 → 며칠 뒤 그 지점을 겨냥해 다시 확인 → 결과를 앱 기억에 넣는다. 큰 실습(Recaller `lib` 모듈 뜯어보기)으로 실제 AI로 한 바퀴 돌렸다. 찾기부터 앱 기억까지 끝까지 이어졌다.

## 3. 실습에서 학습자가 기억해야 할 것: 규정

Recaller의 뜻은 "**네가 뭘 모르는지 기억해서 다시 되새기게 한다**"다. 실습 한 번이 남기는 기억은 네 층이다.

1. **부족함(원장의 한 칸)**: 이게 중심이다. 학습자가 실제로 보인 틀림 · 모름 한 지점.
   - 지식 이름 · 여섯 칸(개념 · 원리 · 절차 · 규칙 · 방법 · 비교)
   - 무엇을 어떻게 잘못 알았나(`wrong`) · 바로 알 것(`right`)
   - 근거: 학습자 말 · 코드 덩어리 · 판정 결과
   - 드러난 곳(판정 · 막힘 · 목표 정리) · 학습자가 고른 원인(6가지)
   - 처방(무엇으로 채웠나) · 채운 근거(그 뒤 맞은 답)
   - 다시 확인 문항(그 지점을 이름 · 값만 바꿔 겨냥) · 다시 확인 기록과 다음 날짜
2. **배운 것**: 학습자가 직접 맞히거나 해낸 것만. 틀림 판정된 답은 근거가 못 된다(3번 수정).
3. **세션 노트**: 학습 한 번 = 제목(장기 목표) · 태그(나온 지식 이름) · 목표마다 요약과 거친 과정 · 부족함과 그 뒤. 사용자가 말한 "그 세션에서 무엇을 배웠는지 정리"가 이것이다.
4. **학습자 메모리**: 여러 세션에 걸친 경향(예: "실행 순서를 거꾸로 읽는 경향"). 부족함이 여러 목표에서 반복될 때 생긴다(이미 있음, `lib/memory.ts`).

### 왜 "다시 확인"까지가 필수인가

- 바로잡은 오류는 되돌아온다. Butler · Fazio · Marsh(2011)에서 즉시 다시 물으면 오류의 86%를 고쳤지만, 일주일 뒤에는 56%만 고쳐져 있었다. 확신이 높았던 오류일수록 다시 나왔다. 권고는 간격을 둔 인출 연습이다.
- 같은 문제를 되풀이하면 그 자리 정답률은 오르지만(71% vs 64%), 새 문제로 옮겨 가는 힘은 **바뀐 문제**가 키웠다(arXiv 2405.09655, 대학원 강좌 32명 · 지식 단위 78개).
  → 그래서 재확인 문항은 같은 지점을 겨냥하되 이름 · 값을 바꾸게 했다.
- 프로그래밍 학습 곡선 연구는 지식 단위마다 작은 연습 기회가 많아야 학습이 보인다고 했다(Demirtaş 외, EDM 2024).
  → 부족함마다 짧은 문항 하나를 여러 번(1 → 3 → 7 → 16 → 35일) 묻는다.

## 4. 지금 앱이 담는 방식과 부족한 점 (코드 확인)

| 앱(지식 저장소)이 가진 것 | 다시 묻기에 쓰이나 |
|---|---|
| 뜻(`body`) · 카드 앞면 질문(`ask`, 지식 하나에 하나) | 쓰임. 복습 문제(플래시카드 · 객관식 · OX · 빈칸)는 뜻으로만 만든다(`questions.ts`, AI 없음) |
| 사건(물어봄 · 틀림 · 힌트 · 맞힘 · 메모) · 상태 · 복습 상자 | 상태 · 날짜만. 사건 글(무엇을 틀렸나)은 안 씀 |
| 틀렸던 코드(`mistakes`, 최근 3개) | **안 씀**. 지식 창에 보이기만 |
| 예시(`example`) · 출처 | 안 씀 |
| 실습 출처 묶음(`code:project:`) · 주제 폴더 · 계산된 태그 | 보기용. "학습 세션" 단위는 없음 |

부족한 점:
1. **다시 확인이 부족함을 겨냥하지 않는다.** 실습에서 "+=가 기존 값을 먼저 읽는 걸 몰랐다"가 잡혀도, 앱은 "딕셔너리 키 확인"의 뜻 카드만 묻는다. 학습자는 뜻은 외워 맞히고, 같은 코드 실수는 다시 한다.
2. **채웠는지 모른다.** 세션 안에서 보충하고 맞혔는지가 기록되지 않아, "알려 준 것"과 "채운 것"이 구분되지 않는다.
3. **실습 결과가 실습으로 돌아오지 않는다.** 다음 실습의 튜터는 예전에 다시 틀린 것을 모른다.
4. **세션 단위가 없다.** 학습 한 번에서 무엇을 배우고 무엇이 비었는지 한 장으로 볼 곳이 없다.
5. 이름 매칭이 글자 기준이라, 정리마다 이름이 흔들리면 같은 지식이 여럿 생긴다(1장 5번).

## 5. 개선판: 무엇을 만들었나

```
학습 중                                   목표 끝                        며칠 뒤
[해 봤어요] 일부만/틀림 ──┐
[너무 어려워요] + 이유 ───┼→ 부족함 열림 ─→ 보충 로드맵 = 처방 ─→ 그 단위 판정 맞음 = 세션에서 채움
                         │      (id)        (채우는 중)                   │
목표 정리가 새로 찾은 것 ─┘                                               ▼
                                   목표 정리: 원장 id를 잇고 이름 · 바로 알 것 · 재확인 문항
                                                                          │
         ┌────────────── 실습 첫 화면 [다시 확인 n개] · 앱 복습의 "다시 확인" 카드 ◀──┘
         ▼
   맞음 → 간격 늘림(1·3·7·16·35일) · 앱 "앎"      틀림 → 다시 열림 · 1일 뒤 · 앱 "몰랐음"
                                                  · 다음 실습 튜터 맥락에 "또 틀린 것"
```

### "이게 부족하면 이거" 매칭 (코드 표 `lib/gaps.ts CAUSE_PLAN`)

학습자가 [너무 어려워요]에서 고른 원인마다 채우는 법과 다시 확인하는 꼴을 정해 두었다. 보충 로드맵(튜터)과 재확인 문항(목표 정리)이 같은 표를 본다.

| 원인(학습자가 고름) | 채우는 법(보충) | 다시 확인하는 꼴 |
|---|---|---|
| 무엇을 하라는 건지 모름 | 과제를 작은 할 일로 쪼개고 완료 조건을 예로 | 비슷한 과제에서 무엇을 해야 끝인지 자기 말로 |
| 개념 · 용어를 모름 | 그 말의 뜻을 작은 예 하나로 먼저 | 그 개념이 들어간 짧은 코드 · 상황의 결과 예측 |
| 코드(문법)로 못 옮김 | 빈칸 한두 개짜리 코드로 옮기기 | 한두 줄 직접 쓰기 · 고치기 |
| 순서를 모름 | 단계를 순서대로 나눠 하나씩 | 단계 순서 말하기 · 코드가 지나가는 순서 따라가기 |
| 오류 · 결과가 다름 | 실제로 돌려 오류 · 값을 보고 원인 찾기 | 비슷한 코드의 오류 · 출력 예측과 이유 |
| 앞에서 배운 게 기억 안 남 | 먼저 떠올리게 하고 짧게 다시 | 힌트 없이 떠올려 설명 |
| (판정에서 드러남, 원인 모름) | 튜터가 소크라테스식으로 짚음 | 틀렸던 그 지점을 이름 · 값만 바꿔 다시 |

실측: "순서 · 용어를 모름"을 고르자 보충 첫 단계가 용어를 작은 예로(함수를 넘겨 나중에 실행), 다음이 순서 따라가기로 짜였다. 재확인 문항은 실행 순서를 다시 따라가게 하는 꼴이 나왔다.

### 바뀐 지시문 (사용자 확인 필요)

규칙 "지시문 함부로 바꾸지 마"가 있어서 바꾼 것을 모두 적는다.

- [너무 어려워요] 때 튜터에게 가는 글에 "이유별로 채우는 방법: …" 한 줄
- 다시 확인 채점(`RECHECK_SYSTEM`, 새로): correct · partial · incorrect · unclear, 같은 오해가 다시 보이면 same_mistake
