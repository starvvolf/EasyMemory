# 연구 1: 대용량 PDF(수십 쪽)의 속도와 비용 (C 스레드, 2026-10-28)

목표: 수십 쪽 PDF를 기본 엔진(recaller)으로 만들 때 더 빠르고 덜 쓰게 하는 방법. 전처리·모델 사용·파이프라인 모두 후보.
이 문서는 **측정과 제안까지**다. 엔진 코드는 아직 고치지 않았다(사용자가 고른 것만 고친다).

## 0. 측정 방법

- 실제 호출: 3D 뷰잉 4쪽(`3D뷰잉_좌표계_4쪽.pdf`)을 3002번 엔진 실험 서버에서 recaller로 2번(30회·18회). 호출 기록(`calls/*.json`)의 시간·토큰을 단계별로 평균했다.
- 가짜 모델(비용 0): 3D Viewing 44쪽, 반도체 07주차 47쪽, Geometric Transformations 32쪽을 3002번에서 돌려 전처리 결과(쪽마다 읽는 길)·구역 수·호출 상한을 봤다. 같은 흐름을 클라우드에서 44쪽 가상 자료로 다시 돌려 오류를 재현했다.
- 쪽 글자는 `pdftotext`로 따로 세어 중복·빈 쪽을 봤다.
- 비용의 뜻: 지금 공급자는 ChatGPT 계정이라 돈이 아니라 **계정 사용량**이다. 사용량은 대략 호출 수와 입력·출력 토큰에 비례한다. API 키로 바꾸면 그대로 돈이 된다.

## 1. 지금 구조와 실측 숫자

### 단계별 평균 (실제 호출 3회 실행, 70회)

| 단계 | 쪽·카드당 | 평균 시간 | 입력 토큰(캐시) | 출력 토큰 |
|---|---|---|---|---|
| 그림 쪽 읽기(transcribe, 쪽 이미지 1600px) | 이미지로 읽는 쪽마다 1 | 8.8초 | 2,138 (0) | 312 |
| 정리(rc-organize) | 쪽마다 1 (+재시도) | 11.1초 | 3,490 (1,132) | 376 |
| 기본 문제(rc-author) | **카드마다 1** (+재시도 약 15%) | 8.1초 | 2,709 (1,290) | 225 |
| 따로 풀기(rc-check) | **문제마다 1** (플래시카드 제외) | 4.4초 | 841 (0) | 52 |
| 연결·심화·풀이·오답 확인 | 심화 1묶음에 4 | 8~25초 | 1~4천 | 250~930 |

- 4쪽: 카드 7~8장, 첫 문제 26초, 기본 문제 끝 48초, 심화까지 92초, 호출 30회.
- 쪽당 약 **6~7회 호출, 입력 약 1.3만 토큰**(읽기 1 + 정리 1 + 카드 1.9장 × (출제 1.15 + 따로 풀기 1)).
- 기본 문제 출제 호출은 지시문+출제기준(약 2,100자)을 카드마다 다시 보낸다. 캐시가 절반쯤만 맞는다(1,290/2,709).

### 44쪽으로 늘리면 (3D Viewing 실제 쪽 구성 기준 추정)

- 전처리(코드)는 **1.7초**로 문제없다.
- 그런데 **44쪽 중 42쪽이 모델 이미지 읽기로 간다**(글자 층 2, 그림만 잘라 23, 쪽 전체 19). 수식 글꼴이 5자만 있어도 쪽 전체를 이미지로 보내는 규칙(`prep.ts` `routePage`) 때문이다. 반도체 47쪽은 31쪽이 글자 60자 미만(그림 슬라이드)이다.
- 추정: 호출 약 **280회**(읽기 42 + 나머지 약 235), 입력 약 **60만 토큰**, 출력 약 6만 토큰.
- 시간: 구역 2개씩 동시에 돌고(`PARALLEL = 2`), 1쪽짜리 구역도 자리 하나를 차지한다. 44쪽은 구역 13개(1~8쪽). 대략 8~10분으로 추정한다(실측 아님).

### 큰 자료에서 실제로 막히는 것 (가짜 모델 실측)

1. **호출 상한에서 멈춘다.** 한 번 시작에 쓸 수 있는 호출은 `max(60, 구역 수 × 4 + 10)`(그림 쪽 읽기 제외)이다. 44쪽은 62회에서 "호출 수를 다 썼어요"로 멈췄다. 실제로는 235회가 필요하니 **"다시 시작"을 3~4번 눌러야 끝난다.**
2. **멈출 때 처리 안 된 오류가 난다.** 상한에 걸리는 순간, 정리 응답이 흐르는 동안 이미 시작한 카드 출제(`authorOne`)의 실패가 아무도 받지 않는 오류(unhandledRejection)로 터진다. 클라우드에서 12번 중 2번 재현했고, 위치는 `recaller.ts` 555줄 → `runner.ts` 442줄이다. 3002번 서버 로그에 같은 오류가 5개 찍힌 직후 서버가 응답하지 않게 됐다. 그 오류 때문에 꺼졌는지는 서버 창을 봐야 확정된다. **같은 코드가 3000번에서도 돈다.**
3. **가짜 모델 읽기가 쪽 읽기 캐시에 남는다.** 같은 PDF의 다음 실제 실행이 그걸 원문으로 쓴다(앞 보고에서 22회 낭비).

## 2. 방법 후보

효과는 44쪽 기준 추정이다. "실측 필요"는 품질이 떨어지는지 직접 돌려 봐야 한다는 뜻이다.

### A. 막힘부터 (작고 확실)

| # | 방법 | 효과 | 위험 |
|---|---|---|---|
| A1 | 호출 상한을 쪽 수에 맞춤(예: `쪽 × 8 + 20`), 화면에 예상 호출 수를 미리 보여 줌 | 44쪽이 한 번에 끝남 | 상한의 원래 목적(폭주 방지)이 약해짐 → 쪽 수 기반이라 여전히 묶임 |
| A2 | 출제 실패를 정리 호출이 끝난 뒤 한곳에서 받기(시작한 출제 약속을 항상 기다림) | 처리 안 된 오류 제거 | 없음 |
| A3 | 가짜 모델일 때 읽기 캐시에 쓰지 않음 | 실험 오염 방지 | 없음 |

### B. 전처리 (코드, 호출 0)

| # | 방법 | 효과 | 위험 |
|---|---|---|---|
| B1 | **수식 글꼴 기준 완화**: 쪽 전체가 아니라 깨진 글꼴만 따로 본다. 깨진 글자가 없는 수학 글꼴(𝑃, 𝑧 → NFKC로 이미 고침)은 글자 층을 쓰고, 깨진 줄·도식만 잘라 보냄 | 3D Viewing에서 쪽 전체 이미지 19쪽 중 상당수를 그림 잘라 읽기·글자 층으로 → 읽기 입력 토큰·시간 감소 | 수식이 글자 층에서 틀린 쪽을 놓침 → 깨진 글자 검출을 글꼴별로 해야 함(`P!`, `y"#$%`는 ToUnicode 없는 글꼴) |
| B2 | 이미지 해상도 1600px → 1024px(읽기 단계만) | 이미지 입력 토큰 약 절반 | 작은 첨자·식 오독. 4쪽으로 1600 vs 1024 비교 필요(약 8회) |
| B3 | 내용이 없는 쪽 건너뛰기: 표지·목차·"Q&A"·참고문헌, 앞 쪽에 덧붙이기만 한 애니메이션 쪽 | 자료마다 다름. 이번 3개 자료는 0~2쪽뿐(효과 작음) | 목차를 지식으로 오판하지 않게 이미 정리 단계가 거름 |
| B4 | 쪽 읽기 캐시를 **PDF 쪽 단위**로 계속 활용(이미 있음) + 미리 읽기: 자료를 올리자마자 그림 쪽만 먼저 읽어 둠 | 같은 PDF 재생성·범위 변경이 공짜 | 안 쓰는 쪽도 읽게 됨 → C1과 같이 써야 함 |

### C. 파이프라인

| # | 방법 | 효과 | 위험 |
|---|---|---|---|
| C1 | **읽는 만큼만 만든다(창 방식)**: 읽는 쪽 + 앞으로 N쪽(예: 6쪽)만 만들고, 읽는 위치가 다가오면 다음 묶음을 만든다. "만들면서 바로 읽기"(DECISIONS 10-19)의 연장 | 학습자가 실제로 읽은 쪽만큼만 쓴다. 44쪽 중 오늘 15쪽 읽으면 비용 약 1/3. 첫 문제 시간은 그대로 | 자료 전체 개념 목록(A1 과제)이나 심화 묶음은 전체를 봐야 함 → 개념 목록만 전체 1회로 |
| C2 | **카드 묶음 출제**: 쪽 하나의 카드 1~3장을 한 호출로(지금은 카드마다 1회) | 출제 호출 97 → 약 44, 지시문 반복 입력 절반 | 첫 문제가 몇 초 늦어질 수 있음(흐름 출제로 보완 가능). 품질 실측 필요 |
| C3 | **따로 풀기 묶음**: 쪽의 문제를 한 호출로 풂, 또는 원문 그대로인 빈칸·단답은 코드 검사만 | 확인 호출 90 → 약 44 | 한 문제가 다른 문제의 답을 흘릴 수 있음(묶음 안 교차 힌트) |
| C4 | **읽기+정리 합치기**: 이미지로 읽는 쪽은 한 호출이 옮겨 쓰기와 카드를 같이 냄 | 호출 42회·쪽당 약 9초 감소 | 인용 검사는 옮긴 글을 기준으로 해야 함(지금도 옮긴 글로 검사) |
| C5 | **동시 실행을 쪽 단위로**: 구역 2개 제한 → 쪽 4~6개 제한 | 1쪽 구역이 자리를 낭비하지 않음, 벽시계 시간 단축 | ChatGPT 계정의 동시 요청 한도에 걸릴 수 있음 → 4부터 |

### D. 모델 사용

| # | 방법 | 효과 | 위험 |
|---|---|---|---|
| D1 | 프롬프트 캐시 맞추기: 고정 지시문·출제기준을 맨 앞에, 자료마다 같은 앞부분을 공유 | 캐시 비율 50% → 80% 이상이면 입력 비용 감소(공급자가 캐시 입력을 싸게 셀 때) | ChatGPT 계정에서 캐시가 사용량에 얼마나 반영되는지 불명 |
| D2 | 단계별 모델 낮추기: 따로 풀기는 지금 sol·low, 심화 풀이는 sol·high. 더 가벼운 모델(luna)로 따로 풀기 비교 | 따로 풀기 비용·시간 감소 | 10/24 기록에 luna가 수식을 빠뜨린 적 있음 → 실측 필요 |
| D3 | API 키 공급자의 일괄 처리(Batch, 보통 반값·24시간 안) | 미리 만드는 자료는 비용 절반 | ChatGPT 계정 방식에는 없음. 즉시 보는 흐름과 안 맞음 → 밤사이 미리 만들기에만 |

## 3. 추천 묶음

1. **먼저 A1·A2·A3** (작고 확실, 호출 0). 44쪽이 멈추지 않고 끝나야 나머지를 잴 수 있다.
2. **그다음 C1 창 방식 + C2 카드 묶음 출제 + C5 쪽 단위 동시 실행.** 비용은 "읽은 쪽 수"에 비례하게, 호출 수는 쪽당 약 6.5 → 약 4로 줄어든다. 44쪽 전체를 만든다고 해도 약 280회 → 약 190회로 추정한다.
3. **B1·B2는 4~8쪽으로 품질 비교 후** 넣는다(그림 읽기가 지금 품질의 바탕이라 조심).

실측 계획(사용자가 고르면): 44쪽 중 8쪽 범위로 지금 방식 / C2+C3 방식을 같은 쪽에서 비교한다. 품질은 문제 수·보류 수·따로 풀기 불일치·눈으로 본 오류로 본다. **예상 호출 약 40~50회**(남은 허락 10회로는 모자람).

## 4. 확인 못 한 것

- 44쪽 실제 호출 실행(시간·토큰은 4쪽 실측에서 늘린 추정).
- 3002번 서버가 응답하지 않게 된 원인(처리 안 된 오류인지, 메모리인지). 서버 창 출력을 봐야 한다.
- ChatGPT 계정에서 캐시 입력이 사용량에 어떻게 계산되는지.
