# 연구 2: 평문·코드·교양 자료의 Recall 설계 (C 스레드, 2026-10-28)

목표: PDF 강의 말고 ① 평문(예: 주식 블로그 글), ② 코드 공부 지식, ③ 교양 공부를 플래시카드·객관식·OX 등으로 어떻게 떠올리게 할지.
이 문서는 **조사와 설계 제안**이다. 코드는 고치지 않았다. 웹 글은 B 영역, 코드는 A 영역이라 구현은 해당 스레드와 사용자 결정이 필요하다.

## 0. 지금 Recaller는 어떻게 하나 (코드 확인)

| 자료 | 지식으로 뽑는 것 | 떠올리기 문제 |
|---|---|---|
| PDF(recaller 엔진) | 카드 9종류(용어·사실·목록·조건·절차·공식·비교·개념·패턴), 실수 후보, 받음/냄 | 카드마다 AI가 형식을 골라 1문제, 따로 풀어 확인. 심화는 계산 사슬 |
| 웹 글(`knowledge-ai.ts` 지식 잡기) | 용어(term)·원리(idea) 4~12개 + 글의 주장 1개(근거 포함) + 고리. 시세처럼 시간이 지나면 의미 없는 숫자는 뽑지 않음 | 지식창고 복습(`knowledge/questions.ts`, AI 없음): 이름 → 뜻 플래시카드, 다른 지식의 뜻을 오답으로 쓰는 객관식, 뜻을 바꿔치기한 OX, 고리 빈칸. 주장은 "주장 확인"으로 한 번 씀 |
| 코드 | 문제 이름만 지식으로 들어옴(뜻이 비어 있음, CURRENT_STATUS) | 문제를 다시 풂. 힌트·틀린 제출이 지식 기록으로 감 |

결론:
- 웹 글과 코드는 **모든 지식이 같은 4가지 문제 틀**(이름↔뜻)로만 복습된다. 자료의 성격(주장인지 사실인지, 코드인지)을 문제가 모른다.
- 웹 글의 "주장"은 지식이 아니라 글 한 편의 속성이라 복습에 안 나온다.

## 1. 근거 (학습 연구·다른 제품)

조사 출처는 끝의 목록. 수치나 결론은 출처가 말한 범위만 적었다.

**학습 연구**

- **문제 형식**
  - 시험 보듯 떠올리기가 다시 읽기보다 오래 남는다. 새로운 추론 문제에도 옮겨 간다(Butler 2010, 산문 지문).
  - 사실 문제만 풀면 사실만 늘고, 사고 문제를 풀어야 사고 문제가 는다. 섞으면 둘 다 는다(Agarwal 2019).
  - 직접 떠올리게 하는 것(생성)이 고르기보다 낫다(생성 효과 메타분석, Bertsch 2007).
- **객관식의 위험**
  - 그럴듯한 오답을 나중에 사실로 기억하는 일이 생긴다(Roediger & Marsh 2005; Marsh 2007).
  - 바로 피드백을 주면 줄어든다(Butler & Roediger 2008).
- **되풀이하면 참처럼 느껴진다**(Fazio 외 2015, 진실 착각).
  - "글쓴이의 의견"을 사실처럼 OX로 계속 보여 주면, 맞든 틀리든 참으로 느끼게 훈련된다.
  - 그래서 Nielsen은 논문 내용을 "논문이 이렇게 말한다"로 외우라고 한다.
- **좋은 질문 쓰는 법**
  - Matuschak: 하나만 묻고, 정확하고, 매번 같은 답이 나오고, 답할 수 있고, 힘이 드는 질문.
  - 개념은 다섯 방향으로 묻는다: 속성, 비슷한 것과 차이, 부분과 전체, 원인과 결과, 의미.
  - 빈칸은 앞뒤 글이 답을 흘려서 이해가 덜 생긴다.
  - 적용 문제는 매번 값을 바꿔야 한다. 그대로 되풀이하면 1~2번 만에 외운 답이 된다(Execute Program 사례).
  - SuperMemo 20규칙: 이해한 뒤 외우기, 목록 통째로 외우지 않기, 출처 달기, 날짜 달기(낡는 지식 표시).
- **프로그래밍**
  - 코드를 읽고 결과를 따라가는 힘이 쓰는 힘보다 먼저다(Lister 외 2004, 556명).
  - 줄 순서 맞추기(Parsons)는 같은 학습 효과에 더 빨리 끝난다(Ericson).
  - 예측 → 실행 → 살펴보기 → 고치기 → 만들기 순서(PRIMM).

**다른 제품**

- Readwise Mastery: 밑줄을 손으로 질문·빈칸으로 바꿔 복습한다.
- RemNote: AI 카드를 만들되 사람이 고르게 한다.
- NotebookLM: 자료 안에서만 플래시카드·퀴즈를 만들고, 날짜 간격 복습은 없다.
- Execute Program: 실행되는 코드 예제만으로 복습한다.
- LeetCode 복습 도구들: 문제 단위로 1·3·7·14·30일.
- **확인한 제품 중 글의 "주장·의견"과 "사실"을 나눠 다루는 곳은 없었다** → Recaller가 메울 빈자리 후보.
- 한국 앱(유니브 등)의 이 부분은 확인하지 못했다.

## 2. 공통 설계 원칙 (세 자료 모두)

1. **지식 하나에 질문 2~3개, 방향을 바꿔 가며.**
   - 같은 문장을 매 상자마다 되풀이하지 않는다.
   - 지금 `questionsFor`는 이름→뜻 한 방향뿐이다.
2. **상태에 따라 형식을 올린다.** 지금 상태(만남·몰랐음·앎·졸업)와 상자에 그대로 맞춘다.

   | 상태 | 형식 | 이유 |
   |---|---|---|
   | 만남(처음) | 객관식·OX + 즉시 설명 | 부담이 작다. 오답 기억 위험은 설명으로 줄인다 |
   | 몰랐음 | 단서 주고 떠올리기(단답·빈칸) | 생성 효과 |
   | 앎 | 단서 없이 떠올리기 + "왜?" 한 줄 | 정교화 질문 효과는 배경지식이 있을 때 크다 |
   | 졸업 직전 | 새 사례에 적용(매번 다른 값·사례) | 외운 답이 되지 않게 |

3. **출처 없이 풀 수 있게 쓴다.** "이 글에서" 대신 대상과 맥락을 문제에 적는다.
4. **지식에 종류 표시를 붙인다:** 사실 / 정의 / 주장(누구의) / 예측 / 수치(기준 날짜). 종류에 따라 쓸 수 없는 형식이 있다(아래).
5. **낡는 지식**(시세·실적·순위)은 기준 날짜를 달고 졸업하지 않게 하거나, 일정 기간 뒤 복습에서 뺀다. 숫자 자체보다 "어떻게 계산·해석하나"를 묻는다.

## 3. 자료별 설계

### ① 평문 — 예: 주식 블로그 글

**지식 단위:** 주장 카드 = {주장, 누구의 주장인지, 근거 1~3개, 조건·반론, 기준 날짜}. 그리고 지금처럼 용어(정의)와 원리.

| 쓸 것 | 예 |
|---|---|
| 누구 말인지 밝힌 주장 질문 | "글쓴이는 반도체 업황 회복의 근거로 무엇을 들었나?" (단답·자기 채점) |
| 논증 구조 | "이 결론(배당주 비중 확대)을 받친 근거 2가지는?" / 근거 하나를 주고 결론 고르기(객관식) |
| 용어 | 질문형 플래시카드("PER이 낮다는 것은 무엇을 뜻하나?"), 같은 글·폴더의 비슷한 지표를 오답으로 |
| 적용 | 새 회사 숫자를 주고 "이 지표로 보면?"(매번 다른 숫자, 코드가 만들 수 있음) |
| 비판 | "이 추론이 틀릴 수 있는 경우는?"(앎 이후, AI 채점 또는 자기 채점) |

**피할 것:**
- 의견을 사실처럼 묻는 OX("삼성전자는 저평가다 → O").
- 의견으로 만든 그럴듯한 오답.
- 글 문장을 그대로 비운 빈칸.
- 시세·분기 숫자를 날짜 없이 외우게 하기.

**지금 코드와 차이:**
- 지식 잡기가 이미 주장·근거를 뽑지만 복습 대상이 아니다.
- 지식에 "주장/사실" 표시가 없다.
- OX가 의견에도 그대로 나간다.

### ② 코드 공부 지식

**지식 단위:**
- 개념·문법 + 최소 예제
- 패턴 + 언제 쓰나(조건)
- 버그 교훈(증상 → 원인 → 고침)
- 푼 문제 = {핵심 아이디어, 접근, 복잡도}

| 쓸 것 | 예 | 채점 |
|---|---|---|
| 출력 예측·따라가기 | 짧은 코드 + 입력 → 출력은? 값은 매번 바꿈 | **코드를 실제로 돌려 정답을 만든다**(이미 4개 언어 실행기 있음) → 정답이 확실 |
| 빈 줄 채우기 / 줄 순서 맞추기 | 내가 맞힌 풀이의 줄을 섞어 순서 맞추기 | 실행해서 확인 |
| 버그 찾기 | 내 틀린 제출과 맞은 제출의 차이 → "이 코드가 틀리는 입력은?" | 실행 |
| 언제 쓰나 구별 | "N ≤ 10^5, 최단 거리, 간선 가중치 1 → BFS/DFS/다익스트라?" 비슷한 패턴을 섞어서 | 객관식 |
| 복잡도 | 단답 + "왜" 한 줄 | 단답 |
| 문제 다시 풀기 | 앞 상자(10분·1·3일)는 핵심 아이디어 떠올리기, **뒤 상자(16·35일)만 전체 다시 풀기** | 실행 채점 |

**피할 것:**
- 코드 통째로 외우기.
- 다시 안 쓸 API 이름 맞히기.
- 같은 출력 예측 문제를 같은 값으로 되풀이하기.

**지금 코드와 차이:**
- 코드 지식은 이름만 들어와 뜻이 비어 있다.
- 복습이 "다시 풀기" 하나라 짧은 상자에서도 무겁다.
- 힌트·틀린 제출 기록(이번 풀이)은 이미 있다 → 버그 교훈 카드의 재료가 된다.

### ③ 교양(역사·철학·사회·예술)

**지식 단위:**
- 사건 = {원인, 결과, 의의}
- 사상가의 논증 = {전제, 결론, 반론}
- 개념 = {정의, 예, 대비}
- 해석 = {누구의 해석인지}

| 쓸 것 | 예 |
|---|---|
| 인과 | "왜 X가 Y로 이어졌나?"(단답 → 앎 이후 서술) |
| 비교 | "홉스와 로크의 자연 상태는 어떻게 다른가?"(비교 표의 칸을 묻는 객관식부터) |
| 누구의 해석 | "베버에 따르면 …" |
| 사례 적용 | 새 사례 → "어떤 개념의 예인가?" |
| 날짜 | 맥락 속 기준점으로만("프랑스 혁명 직전의 재정 위기는 어느 왕 때?") |

**피할 것:**
- 연도↔사건 목록 외우기.
- 서로 다른 해석을 "틀린 보기"로 쓰는 객관식.
- 예/아니오만 묻기.

**참고:** 개념 지도는 복습 화면(전체 보기)으로 쓰는 게 낫다. 공부 활동 자체로는 떠올리기가 더 낫다(Karpicke & Blunt 2011).

## 4. PDF 엔진과 같이 쓰기

- recaller 카드 9종류가 이미 비슷한 모양이다(개념 = 주장·이유·한계, 비교 = 대상×기준, 절차 = 단계).
- 평문·교양은 **카드 종류에 "주장(누구의)"·"사건(원인·결과)"을 더하면** PDF와 같은 정리 → 변환 → 따로 풀기 흐름을 그대로 탈 수 있다. 정리 지시문과 출제기준(`출제기준/변환.md`) 절만 늘어난다.
- 코드는 실행기로 정답을 만들 수 있어 다른 길이 맞다: AI가 문제 틀을 쓰고, 정답은 코드를 돌려 만든다. 심화 문제에서 계산기가 값을 내는 방식과 같은 생각이다.
- 지식 저장소 쪽(B): 지식에 종류 표시(사실/정의/주장/예측/수치+날짜)와 "낡음" 처리가 필요하다. 복습 문제 생성(`questions.ts`)이 종류에 따라 형식을 거르면 된다(예: 주장 → OX 금지, 질문은 "누가 …라고 했나").

## 5. 정할 것 (사용자)

1. 웹 글의 주장을 지식(복습 대상)으로 넣을지. 넣는다면 "누구의 주장" 형식으로만 물을지.
2. 낡는 숫자: 아예 안 뽑기(지금) / 날짜를 달고 졸업 없이 / 기간 뒤 자동으로 빼기.
3. 코드 복습의 짧은 상자를 "다시 풀기" 대신 가벼운 문제(출력 예측·핵심 아이디어)로 바꿀지.
4. 상태에 따라 형식을 올리는 표(2장)를 지식창고 복습에 적용할지(B 영역).
5. 시험 순서: 작은 시험(호출 몇십 회)으로 블로그 글 2개·코드 문제 2개·교양 글 1개에 위 형식을 만들어 보고, 사람이 보고 고르는 방식을 제안한다.
