# 유니브 AI는 요약 → 퀴즈 → 플래시카드 품질을 어떻게 올렸나 (2026-10-31, Claude)

근거: 유니브 웹의 공개 화면 코드(JS 번들 398개 파일)에서 요청 형식·옵션·스트림 이벤트를 읽었고, 저장된 결과 데이터(그래픽스 03 44쪽, 데드락 14쪽)를 원문 PDF와 맞춰 봤다. **프롬프트와 서버 코드는 볼 수 없다.** 아래 "추정"은 그 한계 안의 판단이다. 실측 시간은 `실측_유니브대비_속도품질_Claude_20261031.md`.

## 0. 한 줄 요약

유니브의 품질은 특별한 파이프라인보다 **① PDF 파일을 통째로 추론 모델에 넣고 ② 결과 형식을 학습용 칸(쉬운 설명·힌트·보기별 해설·원문 인용+쪽)으로 꽉 채우게 하고 ③ 학습자가 고를 손잡이를 주는 것**에서 나온다. Recaller는 ①을 일부러 하지 않고(쪽마다 나눠 동시에 읽어 빠르다), 근거 검사는 이미 더 엄격하다. 따라잡을 곳은 ②와 ③이다.

## 2. 요약 (가장 앞선 부분)

**보내는 것**: `pdfUrl`, `language`, `includeEasyExplanation`(기본 켬), `detailLevel`, `summaryStyle`, `customPrompt`, `pageRanges`. 호출 1번, 스트리밍.

**결과에서 보이는 기법**
- 소제목마다 본문 + "쉬운 설명"(비유) + 한 줄 정리. 끝에 "핵심 정리".
- 문장 끝마다 쪽 표시. 데드락 2~14쪽 전부(50번), 그래픽스 44쪽 중 43쪽.
- 표(평행 vs 원근 투영), 수식(행렬)까지 본문에 재구성.
- 첫 글자 약 10초: 문서 전체를 본 한 번의 호출이 처음부터 흘러나오니 "지도가 다 될 때까지" 기다리지 않는다.

**추정되는 비결**: 문서 전체를 한 번에 본 모델이 흐름(파이프라인 순서)을 잡아 소제목을 나눈다. "쉬운 설명" 칸을 형식으로 강제한다.

**Recaller와 차이**: Recaller는 쪽 카드 → 자료 전체 정리(바뀐 것만, 44쪽 약 20초) 순서라 첫 화면이 지도·문제다. 읽을 수 있는 "한 편의 정리 글"이 없다.

## 3. 퀴즈

**보내는 것**: `pdfUrl`/`pageRanges`, `numQuestions`, `difficulty`, `questionTypes`, `customPrompt`, `reasoningMode: "deep"`(화면 문구 "문제를 한 번 더 검토"), `variantSeeds`(변형 문제), `existingQuestionsArray`(더 만들 때 중복 피하기), `conversationHistory`(AI 튜터 대화를 반영), `examDelivery`. SSE로 문항이 하나씩 온다.

**문항 형식**(저장 데이터): `question, options, correctAnswer, answerText, hint, optionExplanations(보기마다), explanation, sourceQuote, sources[{page, quote}]`.

**근거 검사(그래픽스 오늘 퀴즈, 인용 17개를 원문 PDF 글자 층과 대조)**
- 17개 모두 **적힌 쪽이 맞다**.
- 11개는 글자 그대로 있다. 5개는 단어는 전부 있고 아래첨자(`z_far`)·줄바꿈·따옴표만 다르다. 1개(19쪽 수식)는 단어 63%만 맞다(그림·수식을 읽어 옮긴 것으로 보임).
- 즉 인용은 모델이 "원문을 옮겨 적은 것"이고, 서버의 `insufficient_source`/`sources_skipped`로 보아 근거 없는 문항을 거르는 단계가 있는 것으로 추정한다. 글자 그대로 일치까지는 요구하지 않는다.

**계산 문항**: 기본 설정에서는 개념 확인 위주. 10/18 그래픽스 퀴즈처럼 거의 전부 수치 계산이 된 건 `customPrompt`(한 줄 요청)를 넣었을 때로 보인다. 다단계 계산은 "요청하면 하는" 기능이다.

**Recaller와 차이**: Recaller는 인용을 글자 그대로 검사하고 따로 풀기 검사도 있어 근거 엄격성은 앞선다. 없는 것은 힌트·보기별 해설, 학습자 손잡이(유형·난이도·문항 수·집중 영역·쪽 범위·한 줄 요청), "더 만들기" 중복 방지, 문항 단위 스트리밍.

## 4. 플래시카드

**보내는 것**: `pdfUrl`/`pageRanges`, `numCards`, `customPrompt`, `bypassSharedCache`, `conversationHistory`. 기본 Gemini.

**기법**
- 응답 JSON을 글자 단위로 읽으며 `"flashcards":[` 안의 `{...}`가 닫히는 순간 카드 하나를 화면에 붙인다(완성 전에 보여 주기).
- 카드 형식 `type`(예: `term_…` 계열), `front`(질문형), `back`, `sourceQuote`. 앞면이 "용어?"가 아니라 "평행 투영은 투영선의 방향과 치수 표현에서 어떤 특징이 있는가?"처럼 **특징을 묻는 질문**이다.
- "알고 있어요/모르겠어요"는 브라우저에만 저장, 날짜 간격 복습은 없다.

**Recaller와 차이**: 복습 일정은 Recaller가 앞선다. 카드 앞면을 질문형으로, 카드마다 원문 인용을 붙이는 것, 만들어지는 대로 보여 주는 것은 없다.

## 5. Recaller에 옮길 방법 (제안, 순서 = 요약 > 퀴즈 > 카드)

| # | 할 일 | 어디 | 효과 | 비용 |
|---|---|---|---|---|
| S1 | **정리 글 한 편**: 쪽 카드가 모이는 대로 소제목별 본문 + `쉬운 설명` + 한 줄 정리 + 쪽 표시를 스트리밍으로 쓴다. 원 PDF 대신 이미 만든 쪽 카드(인용·쪽 포함)를 입력으로 | C, 공부 화면 | 유니브 요약과 같은 읽을거리, 쪽 표시를 코드로 검사 가능 | 호출 1회 추가 |
| S2 | 정리 글의 쪽 표시는 그 문단이 쓴 카드의 쪽만 허용(코드 검사) | C | 유니브보다 엄격한 근거 | 0 |
| Q1 | 문항 형식에 `hint`, `optionExplanations` 추가. 오답 보기마다 "왜 틀렸나"를 원문 근거로 | C (`schemas.ts`·`prompts.ts`) | 문항당 학습량 증가 | 출력 토큰 증가 |
| Q2 | 출제 손잡이: 유형·난이도·문항 수·쪽 범위·한 줄 요청을 엔진 입력으로 | C + 공부 화면 | A2(방향 지시 반영)와 같은 일 | 0 |
| Q3 | "더 만들기"에 기존 문항 목록을 넘겨 중복 금지 | C | | 0 |
| Q4 | "꼼꼼히" 선택 시에만 따로 풀기 검사를 한 번 더(지금 검사를 손잡이로) | C | 유니브 deep과 같은 선택권 | 선택 시 호출 증가 |
| Q5 | 인용 일치 검사에서 아래첨자·줄바꿈·따옴표를 같은 것으로 보기(지금은 글자 그대로라 수식 쪽 문항이 많이 떨어질 수 있음) | C (`containsQuote`) | 보류 문항 감소 | 0 |
| F1 | 카드 앞면을 "특징·이유·차이"를 묻는 질문형으로, 카드마다 인용+쪽 | C → B | 카드 품질(B4) | 0 |
| F2 | 카드·문항을 JSON이 닫히는 대로 하나씩 화면에 붙이기 | 공부 화면 | 체감 속도 | 0 |

**하지 않기를 권하는 것**: PDF 통째로 한 번에 넣기. 10/30 연구대로 44쪽 한 번이면 출력만 약 165초이고, Recaller의 쪽별 동시 처리가 첫 문제 11초를 만든다. 유니브의 요약 첫 글자 10초는 S1(카드를 입력으로 한 스트리밍 정리)로 따라갈 수 있다.

## 5-1. 쓰는 모델 (추가 확인)

| 기능 | 확인된 것 | 근거 |
|---|---|---|
| 퀴즈 | **OpenAI `gpt-6-luna`**. 데드락·그래픽스 오늘 퀴즈 둘 다 | 저장된 퀴즈의 `paperGeneration: {provider: "openai", model: "gpt-6-luna", requestedCount: 10, actualCount: 10/11}`. 주소 이름은 `generateQuizWithGemini`인데 실제는 OpenAI |
| AI 튜터 | 빠름 = `gemini-3.1-flash-lite`, 깊게 = `gemini-3.8-flash` | 튜터 모드 메뉴 코드 |
| 요약·개념·카드 | 저장 데이터에 모델 기록 없음 | 요약 생각(`thought`) 이벤트가 있어 추론 모델로 추정 |
| 바꾸기 규칙 | 파일마다 기본 Gemini, 그 파일에서 Gemini가 답을 못 주면 `noGeminiReturn` 표시를 남기고 이후 OpenAI로. 서버에도 `fallback_notice`(다른 모델로 넘김)가 있다 | `providerFlag` 코드 |

즉 문항은 OpenAI 상위 모델, 대화는 Gemini 가벼운 모델로 나눠 쓴다. Recaller도 출제(정확성 중요)와 설명·대화(속도 중요)의 모델·추론 강도를 따로 정하는 것이 맞다.

## 5-2. 같은 방식으로 우리가 해 보면 (데드락 14쪽, terra·low, 1회)

PDF 통째 입력 + 유니브식 요약 지시로 한 번 돌렸다. 원 보고: `실측_PDF통째요약_terra_20261031.md`.

| | 유니브 | Recaller 실험 (gpt-6.1-terra·low) |
|---|---|---|
| 첫 글자 | 약 7~10초 | 7.1초 |
| 완성 | 약 50~57초 | 53.1초 |
| 입력 / 출력 토큰 | 모름 | 13,640 / 2,536 (생각 0) |
| 글자 수 | 약 5,200자 | 4,244자 |
| 쪽 표시 | 50개, 2~14쪽 전부(13쪽) | 62개, 12쪽(14쪽 빠짐) |
| 소제목 / 쉬운 설명 | 3 + 핵심 정리 / 8개 | 6 + 핵심 정리 / 6개 |

- **속도는 같다.** PDF 통째 입력이 느리다는 걱정은 이 크기에서는 맞지 않았다. 입력 1.4만 토큰에도 첫 글자 7초.
- 출력 속도가 약 55토큰/초로, 쪽 카드 호출 평균(117)의 절반이다. 한 번 잰 값이라 원인은 모른다.
- **품질 차이는 "쉬운 설명"이다.** 우리 쪽은 비유가 아니라 본문을 쉽게 다시 말한 수준이었다. 지시에 "일상 비유 하나 + 비유가 맞지 않는 점 한 줄"(유니브 요약에 있는 형태)을 넣는 것이 다음 시도다.
- 결론: S1(정리 글 스트리밍)은 PDF 통째 입력으로도, 쪽 카드 입력으로도 시간상 문제없다. 통째 입력은 쪽 카드를 기다리지 않아 첫 글자가 빠르고, 쪽 카드 입력은 근거 검사를 코드로 하기 쉽다. 둘 다 써서 품질을 비교할 만하다.

### 모델·추론 강도 4가지 (각 1회, 같은 PDF·지시)

| | terra low | terra medium | sol low | sol medium | 유니브 |
|---|---|---|---|---|---|
| 첫 글자 / 완성 | 7.1 / 53.1초 | 4.4 / 48.3초 | 5.5 / 119.7초 | 7.5 / 114.6초 | 7~10 / 50~57초 |
| 출력 토큰 (생각) | 2,536 (0) | 2,421 (0) | 3,716 (0) | 3,640 (62) | - |
| 글자 수 | 4,244 | 4,088 | 6,528 | 6,243 | 약 5,200 |
| 서로 다른 쪽 | 12 | 12 | 13 | 13 | 13 |
| 소제목 / 쉬운 설명 | 6 / 6 | 6 / 6 | 9 / 9 | 7 / 7 | 3 / 8 |

- terra는 low와 medium이 사실상 같다(생각 토큰 0). 이 작업에 terra의 추론 강도는 손잡이가 아니다.
- sol은 1.5배 길게 쓰고 13쪽을 다 걸며, 쉬운 설명이 비유에 더 가깝다. 대신 출력이 느려(약 33토큰/초) 완성이 약 2분으로 유니브의 2배다.
- 유니브는 시간은 terra, 쪽 범위는 sol 수준이다. 품질 기준으로는 sol, 시간 기준으로는 terra.
- 권고: 스트리밍이면 첫 글자는 넷 다 4~8초라 읽기 시작은 같다. **정리 글은 sol low로 스트리밍**하고(완성 2분은 읽는 속도보다 빠름), 쉬운 설명 지시만 다듬는다. 완성까지 1분이 꼭 필요하면 terra + 비유 지시 강화를 시도한다.

### 입력 방식 3가지 (데드락 14쪽, 각 1회)

| 입력 | terra low 첫 글자/완성 | sol low 첫 글자/완성 | 입력 토큰 | 강점 | 약점 |
|---|---|---|---|---|---|
| PDF 통째 | 7.1 / 53.1초 | 5.5 / 119.7초 | 13,640 | - | 12~13쪽만, 그림 판정 일부 빠짐 |
| 쪽 이미지 14장만 | 3.8 / 52.1초 | 3.9 / 119.4초 | 13,196 | 그림 읽기 최고, 14쪽 전부 | terra가 표를 안 만듦 |
| **우리 전처리 한 번에** | **1.9 / 51.0초** | **2.7 / 94.0초** | **5,070** | 가장 빠름, 입력 63% 적음, 표·수식 최고 | p.12 그림이 `layer`로 분류돼 빠짐 |

- PDF 통째 입력은 어느 쪽으로도 이점이 없었다.
- 우리 전처리가 속도·비용·표·수식에서 앞서고, 약점은 그림 쪽 분류 하나다. 원인은 `prep.ts` 쪽 분류(p.12처럼 글자가 충분하고 그림이 있는 쪽을 글자 층만으로 보냄).
- 권고: **정리 글 = 우리 전처리 입력을 한 번에 + sol low 스트리밍.** 보완 두 가지 중 하나를 같은 조건으로 재서 고른다. (가) 그림이 있는 `layer` 쪽에 잘라낸 그림을 붙인다(분류 규칙 수정). (나) 모든 쪽에 low detail 쪽 이미지(쪽당 약 85토큰, 14쪽 약 1.2천)를 덧붙여 배치를 보게 한다. 쉬운 설명은 "일상 비유 1개 + 비유가 안 맞는 점 1줄"로 지시를 바꾼다.

### 입력 차이를 돈으로 (추정)

가격은 `src/lib/api-usage.ts`의 표(2026-08-17, gpt-5.6 기준, 100만 토큰당 sol 입력 $5·출력 $30, terra 입력 $2.5·출력 $15)를 6.x 모델에 그대로 적용했다. 6.x 실제 단가는 표에 없다. 앱은 ChatGPT 구독으로 부르므로 실제로는 돈이 아니라 **사용량 한도**를 쓴다. 환율 1달러 = 1,400원으로 잡았다.

| 데드락 14쪽, 1회 | 입력 토큰 | 입력 비용 | 출력 비용 | 합계 |
|---|---|---|---|---|
| sol low · PDF 통째 | 13,640 | $0.068 | $0.111 | **$0.180 (약 250원)** |
| sol low · 이미지만 | 13,196 | $0.066 | $0.115 | $0.181 (약 250원) |
| sol low · 우리 전처리 | 5,070 | $0.025 | $0.091 | **$0.116 (약 160원)** |
| terra low · PDF 통째 | 13,640 | $0.034 | $0.038 | $0.072 (약 100원) |
| terra low · 우리 전처리 | 5,070 | $0.013 | $0.039 | $0.052 (약 73원) |

- 입력만 보면 전처리가 PDF 통째보다 8,570토큰 적다. sol로 $0.043(약 60원), terra로 $0.021(약 30원) 싸다.
- 44쪽은 같은 비율(전처리 = 통째의 약 37%)이면 통째 약 4.3만 vs 전처리 약 1.6만 토큰으로, sol 기준 1회 약 $0.135(약 190원) 차이로 추정한다.
