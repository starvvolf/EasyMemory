# Study Forge 자료 구조 이해 진단

## 1. 진단 목적

이 문서는 현재 production pipeline의 `Analyze → Plan → Prepare` 결과만으로 모델이 자료의 계층과 관계를 얼마나 잘 이해하는지 진단한다. Cards와 Critic의 표현 품질은 평가하지 않는다.

평가 대상은 다음 두 baseline이다.

- OPIc: `eval/local/study-forge-baseline-1-2026-08-10T06-52-35-568Z.json`
  - 아직 canonical run으로 import되지 않은 legacy browser export다.
  - 원자료: `1.pdf`
- Deadlock: `eval/runs/operating-system-deadlock/20260810T152136Z__whole-document-core-soft-budget__baseline__r01/`
  - 원자료: `lecture8.pdf`

관계 복원에는 각 baseline의 Analyze, Plan, Prepare/LearningUnits만 사용했다. `docs/LEARNING_PRINCIPLES.md`, `docs/references/OPIC_PERSON_DESCRIPTION.md`, `docs/references/OPERATING_SYSTEM_DEADLOCK.md`는 누락과 경계 판단을 위한 비교 기준으로만 사용했다.

이 문서에서 관계 표시는 다음 의미를 갖는다.

- `[상위/하위]`: 주제 또는 영역의 계층
- `[구성요소]`: 상위 대상을 구성하는 부분
- `[비교]`: 구별해서 이해해야 하는 대안이나 상태
- `[선행/의존]`: 앞 개념이나 사건이 뒤 대상을 이해하는 데 필요함
- `[조건/결과]`: 조건에 따라 판정이나 결과가 달라짐
- `[예시]`: 핵심 지식을 설명하거나 적용하는 사례
- `[기타]`: 답변 순서 등 위 유형으로 충분히 표현되지 않는 관계

## 2. OPIc 암묵 구조

### 2.1 Analyze와 Plan이 이해한 전체 자료

```text
OPIc 인물 묘사 자료
├─ 답변 전략 [상위/하위]
│  ├─ 3인칭 단수 수일치 [구성요소]
│  ├─ 배경 → 구체 설명 → 계기 → 생각의 답변 흐름 [기타: 순서]
│  └─ about/that 뒤 핵심어 집중 [구성요소]
├─ 7개 만능 패턴 [상위/하위, 선택된 학습 영역]
├─ 학교·이웃·배우·건강 완성 스크립트 [예시]
└─ 쉐도잉 목적과 반복 방법 [상위/하위: 학습 절차]
```

Analyze는 자료를 답변 전략, 만능 패턴, 주제별 완성 스크립트, 쉐도잉 방법으로 구분했다. Plan도 이 네 역할을 그대로 별도 group으로 만들고 `patterns`를 추천했다. 선택 지시에는 패턴을 포함하고 전략 설명, 완성 스크립트, 쉐도잉 지침을 제외한다고 명시되어 있다.

이는 모델이 문서의 물리적 구획만 나눈 것이 아니라 다음 역할 차이를 이해했다는 근거다.

- 답변 전략: 답변을 조직하는 상위 지침
- 패턴: 실제로 인출할 재사용 가능한 표현
- 완성 스크립트: 패턴이 적용된 예시
- 쉐도잉: 표현 자체가 아니라 학습 절차

### 2.2 Prepare가 이해한 7개 패턴

```text
인물 묘사 답변 [상위]
├─ pattern-1 인물과 이름 소개 [구성요소, 시작]
├─ pattern-2 관계·정체와 나이 [구성요소]
├─ pattern-3 외모 묘사 [구성요소]
├─ pattern-4 좋아하는 이유 [구성요소]
├─ pattern-5 처음 알게 된 계기 [구성요소]
│  └─ pattern-6 이후 관계 변화 [선행/의존: Since then]
└─ pattern-7 최종 생각·평가 [구성요소, 마무리]
```

Prepare의 `detectedGoal`과 `keyTopics`는 reference의 일곱 필수 학습 기능과 일치한다. `recommendedStrategy`는 일곱 패턴의 배열이 하나의 답변 구조이며, 개별 패턴 학습 후 같은 인물을 기준으로 연속 발화하는 관계까지 설명한다.

각 패턴은 `pattern-1`부터 `pattern-7`까지 하나의 독립 LearningUnit으로 생성되었다. 각 LU에는 고정 표현, 변수 자리, 일반화된 표현, 발화 의도와 원문 근거가 있다. 완성 예문의 `Tom`, `21`, 영화 취향 등은 `variableSlots.example`이나 `sourceText`에만 남고 핵심 `generalizedForm`으로 승격되지 않았다.

### 2.3 관계 보존 상태

- 패턴 5와 6의 선행 관계는 `Since then`과 LU intent/rationale에 보존된다.
- 패턴 1부터 7까지의 답변 순서는 `recommendedStrategy`에 보존된다.
- 성별에 따른 `his/her`, `him/her`, `he/she` 일관성은 공통 적용 규칙으로 인식되어 있다.
- 패턴 2가 관계·정체와 나이를 함께 다루는 것은 reference도 하나의 학습 기능으로 정의하므로 부적절한 병합으로 보지 않는다.
- 패턴 3의 `be + 외모 설명`과 예시의 `have + 신체 특징`은 하나의 외모 설명 확장으로 처리되어 reference의 현재 기준과 충돌하지 않는다.

## 3. OPIc 문제점

OPIc에서는 구조 추론의 실질적인 실패를 찾기 어렵다. 주요 한계는 이해한 관계를 명시적인 구조 데이터로 표현하지 않는 점이다.

1. `pattern-1`부터 `pattern-7`까지가 평면 배열이다. 상위 대상인 `인물 묘사 답변`과 순서 관계는 `recommendedStrategy` 문장에만 있다.
2. `pattern-5 → pattern-6` 의존 관계는 자연어에는 있으나 기계적으로 추적할 relation이 없다.
3. `organizedMaterial.title`이 첫 LU의 제목인 `인물과 이름 소개`로 설정되어 전체 7개 패턴을 포괄하는 제목이 아니다.
4. 답변 흐름은 reference에서 권장·보조 단위이므로 별도 LU가 없는 것은 실패가 아니다. 다만 모델이 이미 파악한 전체 흐름을 metadata로 보존하면 이후 누적 발화나 구조 회상에 활용할 수 있다.

완성 스크립트나 쉐도잉이 핵심 패턴 LU로 섞이지 않았고, 예시에서 공통 패턴을 추상화했으므로 현재 OPIc 구조 이해는 충분하다.

**분류: A. 구조 이해 자체는 충분하고, 현재 문제는 구조를 명시적으로 표현하지 않는 것에 가깝다.**

## 4. Deadlock 암묵 구조

### 4.1 Analyze와 Plan이 이해한 전체 구조

```text
Deadlock
├─ 개념과 발생 조건 [상위/하위]
│  ├─ 데드락 정의 [구성요소]
│  ├─ 세마포어 역순 획득 [예시]
│  └─ 네 필요조건이 동시에 성립 [조건/결과]
│     ├─ 상호 배제 [구성요소]
│     ├─ 점유와 대기 [구성요소]
│     ├─ 비선점 [구성요소]
│     └─ 순환 대기 [구성요소]
├─ 자원 할당 그래프 [상위/하위]
│  ├─ 프로세스·자원 정점 [구성요소]
│  ├─ 요청·할당 간선 [구성요소]
│  └─ 사이클 판정 [조건/결과]
│     ├─ 사이클 없음 → 데드락 없음
│     └─ 사이클 있음
│        ├─ 단일 인스턴스 → 데드락
│        └─ 다중 인스턴스 → 데드락 가능성
└─ 처리 전략 [상위/하위, 비교]
   ├─ 예방 [조건/결과: 필요조건 하나 이상 제거]
   │  ├─ 상호 배제 제거의 한계
   │  ├─ 점유와 대기 → 실행 전 일괄 할당
   │  ├─ 비선점 → 보유 자원 반납·재시작
   │  └─ 순환 대기 → 자원 전순서·증가 순서 요청
   ├─ 회피 [선행/의존: 사전 정보와 안전 상태 판단]
   │  ├─ 안전 상태 정의
   │  ├─ 안전 상태와 불안전 상태 [비교]
   │  │  ├─ 안전 → 데드락 없음
   │  │  └─ 불안전 → 데드락 가능성, 데드락 확정 아님
   │  ├─ 클레임 → 요청 → 할당 → 클레임 [기타: 상태 전이]
   │  ├─ 단일 인스턴스 요청 승인 [조건/결과: 할당 후 사이클]
   │  └─ 다중 인스턴스 → Banker 알고리즘 [조건/결과]
   └─ 탐지 및 복구 [기타: 사후 처리]
      ├─ 데드락 진입 허용 → 주기적 탐지 [선행/의존]
      └─ 탐지된 데드락 → 복구 [선행/의존]
         ├─ 모든 교착 프로세스 종료
         ├─ 사이클 제거까지 하나씩 종료
         └─ 자원 선점
```

Analyze의 outline과 Plan의 `wholeDocumentCorePlan.areas`는 이 큰 구조를 거의 그대로 표현한다. 특히 Plan은 다음 관계를 명시한다.

- 네 조건은 데드락 판별과 처리 전략의 기반이다.
- 예방 정책은 각 필요조건을 실제 제어 규칙으로 변환한다.
- 사이클은 자원 인스턴스 수와 함께 해석한다.
- 회피는 사전 정보로 안전 상태를 유지한다.
- 탐지 및 복구는 데드락 진입을 허용한 뒤 대응한다.

Prepare의 `recommendedStrategy`도 네 조건의 동시성, 간선 방향 → 사이클 → 인스턴스 수의 판정 순서, 필요조건과 예방 정책 연결, 안전/불안전의 비대칭을 정확히 설명한다. 따라서 상위 구조에 대한 추론 자체는 상당히 강하다.

### 4.2 LearningUnit으로 보존된 핵심 관계

- `LU03~LU06`은 네 필요조건을 각각 분리하고 `LU07`이 동시 성립 관계를 보존한다.
- `LU10`은 사이클 부재 규칙, `LU11`은 사이클 존재 시 인스턴스 수에 따른 조건부 판정을 보존한다.
- `LU12`는 예방·회피·탐지 및 복구를 비교 관계로 유지한다.
- `LU13~LU17`은 예방의 공통 원리와 조건별 정책을 분리한다.
- `LU18~LU20`은 회피의 할당 판단, 안전 상태 정의, unsafe와 deadlock의 비동일성을 분리한다.
- `LU21~LU24`는 클레임 간선, 간선 전이, 단일 인스턴스 판정, 다중 인스턴스 알고리즘 범위를 구분한다.
- `LU25~LU26`은 탐지와 복구를 별도 단위로 나눈다.

중대한 개념 관계도 올바르다. `unsafe state = deadlock`으로 만들지 않았고, 사이클이 항상 데드락이라고 일반화하지 않았으며, 요청·할당 간선 방향도 보존했다.

## 5. Deadlock 문제점

### 5.1 상위 구조의 평탄화

Plan에는 다섯 개 핵심 area와 area별 설명·학습 가치·범위가 있지만 Prepare의 26개 LU에는 `parentAreaId`나 관계 edge가 없다. `organizedMaterial.sections`도 각 LU를 한 줄씩 나열하며 전체 제목은 첫 LU에서 가져온 `데드락의 정의`다.

그 결과 다음 관계는 LU의 intent/rationale를 다시 읽어야만 복원할 수 있다.

- `LU03~LU06`이 `LU07`의 네 하위 조건이라는 관계
- `LU15`, `LU16`, `LU17`이 각각 `LU04`, `LU05`, `LU06`을 깨는 예방 정책이라는 관계
- `LU18~LU24`가 모두 회피라는 하나의 정책 아래 있다는 관계
- `LU25 탐지 → LU26 복구`라는 선행 관계

이는 주로 구조 표현의 손실이지만, 이후 단계가 관계를 안정적으로 사용하기 어렵게 만든다.

### 5.2 LearningUnit 경계의 국소 문제

#### 예시의 독립 LU 승격

`LU02`는 세마포어 역순 획득 사례를 `knowledgeType: example`인 독립 LU로 만든다. Plan의 exclusion은 세마포어 코드 자체를 독립 암기하지 않고 순환 대기 원리의 맥락으로 활용한다고 명시한다. Prepare의 rationale도 코드 문법이 아니라 발생 원리가 대상이라고 설명하지만, 실제 구조에서는 예시가 독립 LU가 되었다.

이는 모델이 예시의 역할을 모른다기보다, 알고 있는 역할을 LU 포함 여부에 끝까지 적용하지 못한 사례다.

#### 탐지 LU의 과도한 범위

`LU25`는 다음을 한 단위에 담는다.

- 데드락 진입 허용
- 주기적 사이클 탐지
- 단일 인스턴스에서 사이클과 데드락의 관계
- 다중 인스턴스에서는 더 복잡한 알고리즘이 필요함

이 내용들은 탐지 정책의 범위라는 공통 목적은 있지만, 정책의 개입 시점과 판정 경계라는 두 인출 행동이 함께 들어 있다. 반드시 실패라고 할 정도는 아니지만 한 LU의 범위가 넓다.

#### 복구 LU의 과도한 병합

`LU26`은 모든 프로세스 종료, 하나씩 종료, 자원 선점을 한 LU로 합친다. 기존 reference는 프로세스 종료와 자원 선점을 서로 다른 필수 LU로 구분한다. 둘은 모두 사이클 제거라는 상위 목표를 공유하지만 조치 대상과 방식이 달라 독립 인출이 가능하다.

이 병합은 1:N 카드 변환으로 보완될 수 있으나, LearningUnit 자체의 하나의 명확한 학습 의도 원칙에는 다소 넓다.

### 5.3 중복과 누락

- `LU12`의 전략 비교와 `LU13`의 예방 원리는 범위가 겹쳐 보이지만, 하나는 세 정책 비교이고 다른 하나는 예방의 내부 원리이므로 중복으로 보지 않는다.
- `LU10`과 `LU11`은 하나의 전체 사이클 판정 규칙을 둘로 나눴지만 각각 독립적으로 완결된 조건을 다루므로 의미 없는 분할은 아니다.
- 정의, 네 조건, 그래프, 예방, 회피, 안전 상태, 탐지와 복구의 큰 영역 누락은 없다.
- 특정 그래프의 프로세스 번호와 배치가 핵심 LU로 승격되지 않았고, 요약 페이지도 중복 LU로 추가되지 않았다.

**분류: B. 구조 이해는 대체로 되지만, LearningUnit 경계를 정하고 평면 목록으로 옮길 때 관계 일부가 손실된다.**

|---|---|---|---|---|
| OPIc | 네 역할군, 7개 패턴, 답변 순서와 패턴 5→6 관계를 정확히 이해 | 상위 답변 구조와 순서가 자연어에만 있음 | 7개 핵심 기능이 적절히 분리됨 | A |
| Deadlock | 큰 영역, 조건부 판정, 전략 비교와 의존 관계를 정확히 이해 | Plan의 area와 relation이 Prepare에서 평탄화됨 | 예시 LU 승격, 탐지·복구 단위의 국소 과병합 | B |

두 사례 모두 `C`로 볼 근거는 없다. 별도 Structure stage가 없어도 Analyze와 Plan에서 필요한 구조를 이미 상당 부분 추론한다. 문제는 그 구조가 Prepare의 LearningUnit schema와 OrganizedMaterial에 일관되게 전달되지 않는다는 점이다.

## 7. 현재 결론

### OPIc

현재 구조 이해는 충분하다. 역할 구분, 패턴 추상화, 일곱 발화 기능, 답변 순서가 모두 보존된다. 부족한 것은 명시적인 parent/relation 표현이다.

### Deadlock

현재 구조 이해는 대체로 충분하다. 특히 네 조건의 동시성, 사이클과 인스턴스 수, unsafe와 deadlock의 차이, 예방·회피·탐지 및 복구의 정책 차이를 정확히 파악한다. 다만 Plan에서 이해한 계층이 Prepare에서 평탄화되고 일부 LU 경계가 넓거나 예시 역할이 끝까지 적용되지 않는다.

따라서 현재 증거만으로 별도 Structure stage를 추가하는 것은 과하다. 먼저 Analyze/Plan이 이미 만든 구조를 Prepare가 보존하도록 하는 것이 우선이다.

## 8. 다음 최소 변경 제안

다음 한 가지 변경을 우선 검증한다.

> Prepare가 LearningUnit을 만들 때 Plan의 area 구조를 직접 참조하고, 각 LU에 최소 구조 metadata를 보존한다.

개념적으로 필요한 최소 정보는 다음 정도다.

- `parentAreaId`: 어느 Plan area의 하위 학습 단위인지
- `relations`: artifact에 실제로 근거가 있는 경우에만 `prerequisite`, `component_of`, `prevents_condition`, `condition_result`, `example_of`, `followed_by` 같은 관계와 대상 LU ID

이 변경은 새 Structure stage를 만들지 않고도 OPIc의 답변 흐름과 Deadlock의 조건·전략 연결을 명시적으로 유지할 수 있다. 동시에 Prepare가 예시를 독립 LU로 승격하거나 서로 다른 복구 방법을 과도하게 합칠 때, 상위 area의 학습 의도와 관계를 기준으로 경계를 다시 확인하게 할 수 있다.

아직 production schema나 prompt를 변경하지 않는다. 실제 변경 전에는 현재 두 baseline을 기준으로 parent/relation 보존 여부와 LU 경계 개선을 비교할 수 있는 실험을 먼저 설계한다.
