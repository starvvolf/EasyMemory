# 상황 재현 복습 설계안 (A, 2026-11-13)

> 상태: **제안**이에요. 사용자가 고르면 DECISIONS에 올리고 만들어요.
> 출처: 사용자 11/13. "사용자가 풀이한 컨텍스트를 보고 똑같이 / 비슷하게 / 응용해서 풀어야 하는 상황을 만들어 주는 거야. 문제를 통으로 새로 주는 게 아니라 **떠올리지 못한 생각 검증 단위로**. 문법이 틀렸으면 그 문법 쓰는 상황을 컴팩트하게. 자료를 어떻게 담을지 모를 수도, 자료를 구현하는 방법을 모를 수도, 알고리즘을 모를 수도, 알고리즘 구현을 모를 수도… 이걸 실습까지 적용. 단위에 따라 형식이 달라도 좋아(작은 코드창, codium…)."
> 짝 문서: `상황재현_복습_아이디어.md`(처음 생각), `가상학습자_설계.md`(이걸 시험할 NPC), `모르는것_층_설계.md`(층).

## 한 줄

풀이 기록에서 **"그때 떠올리지 못한 생각" 하나하나**를 뽑고, 생각마다 **그 생각만 다시 꺼내게 하는 작은 장면**을 만들어요. 장면의 모양은 생각의 종류에 맞추고, 맞았는지는 **코드를 실제로 돌려서** 정해요.

## 낱말

| 낱말 | 뜻 |
|---|---|
| **빈틈** | 그때 떠올리지 못한 생각 하나. 복습의 단위예요. (예: "정렬 기준 두 개를 튜플로 준다") |
| **알맹이** | 그 생각이 담긴 가장 작은 코드 조각(3~8줄)과 한 문장. 장면을 만드는 재료예요. |
| **장면** | 빈틈 하나를 확인하는 작은 과제 하나. 30초~10분. |
| **형식** | 장면의 모양. 한 줄 쓰기, 빈칸, 결과 맞히기, 고치기 … (아래 3번) |
| **거리** | 원래 상황과 얼마나 다른가. **똑같이 / 비슷하게 / 응용** |
| **함정 테스트** | 그 빈틈이 그대로면 반드시 틀리는 테스트. 장면이 진짜 그 생각을 확인하는지 보증해요. |

## 전체 흐름

```
[풀이 · 실습이 끝남]
   └ ① 빈틈 뽑기 (AI 1번, 리뷰와 같은 재료)      → 빈틈 목록 + 알맹이 + 그때 코드 위치
[복습 날이 됨]  (기억 저장소가 날짜를 정함)
   └ ② 장면 고르기 (코드)   종류 × 크기 × 거리 → 형식
   └ ③ 장면 만들기          똑같이 = AI 0번 / 비슷하게 · 응용 = AI 1번(작게) 또는 은행에서 꺼냄
   └ ④ 장면 검사 (코드)     모범 답은 통과 · 그때 실수는 함정 테스트에서 틀려야 함
[학습자가 풂]
   └ ⑤ 채점 (코드 실행)     함정 테스트 통과 = 그 생각을 꺼냄
   └ ⑥ 반영 (코드)          앎/몰랐음 · 다음 날짜 · 다음 거리 · 다음 크기
```

## 1. 빈틈: 무엇을 뽑나

### 빈틈의 종류 (떠올리지 못한 생각의 종류)

사용자가 말한 네 가지를 기준으로 늘렸어요. 층은 `모르는것_층_설계`의 층이에요.

| 종류 | 떠올리지 못한 것 | 층 | 알고리즘 예 | 실습 예 (FPS · 결제) |
|---|---|---|---|---|
| **문법** | 어떻게 쓰나 | 1 | `sorted(key=lambda p: (p[1], p[0]))`, `sys.stdin.readline` | C# `lock (obj) { }`, `async/await` |
| **자료 담기** | 무엇을 어떤 모양에 담나 | 2 | 연결 정보를 인접 리스트에, 방문을 배열에 | 체력을 어디에 두나, 결제 상태를 enum으로 |
| **자료 구현** | 그 모양을 코드로 만들고 쓰는 법 | 2→4 | 인접 리스트 채우기, 2차원 배열 초기화, 큐에서 꺼내기 | 딕셔너리로 플레이어 표 만들기, 큐로 메시지 쌓기 |
| **한 줄 읽기** | 이 줄 뒤 값이 어떻게 되나 | 3 | `q.pop(0)` 뒤 `q`, 자리와 값 혼동 | `Interlocked.Decrement` 뒤 값, `UPDATE`가 0줄일 때 |
| **알고리즘 고르기** | 이 문제에 왜 이 방법인가 | 6 | "퍼져 나감 → BFS", N이 커서 이중 반복은 안 됨 | 이 상황에 lock? 조건부 갱신? 멱등 키? |
| **알고리즘 원리** | 왜 이렇게 돌면 되나 | 5 | 방문 표시를 넣을 때 해야 하는 이유 | 동시에 오면 왜 둘 다 통과되나 |
| **알고리즘 구현** | 아는 방법을 코드로 잇기 | 4 | BFS 뼈대의 순서(꺼냄 → 이웃 → 표시 → 넣음) | 확인 → 빼기 → 저장을 한 잠금 안에 어떤 순서로 |
| **경계 · 예외** | 빠뜨린 경우 | 함정 | 빈 입력, 같은 값, 범위 끝 | 체력이 0 아래로, 연결 끊김, 중복 요청 |
| **문제 · 과제 읽기** | 조건을 잘못 읽음 | — | "y 먼저, 같으면 x"를 거꾸로 | 완료 조건을 다르게 이해 |
| **실행 · 도구** | 돌리고 입력 넣고 환경 맞추기 | 실행 | 입력 형식, 빠른 입력 | `dotnet run --project`, 포트 사용 중, 빌드 오류 |
| **오류 읽기** | 오류 · 로그에서 원인 찾기 | 3 / 실행 | 인덱스 오류가 난 줄에서 원인 | 스택 트레이스, 서버/클라 로그 맞춰 보기 |

### 빈틈 하나의 모양

```jsonc
{
  "id": "gap_a1f3", "branch": "algo",            // algo | project
  "kind": "문법", "layer": 1, "size": "small",    // small | mid | big
  "title": "정렬 기준 두 개를 튜플로 주기",
  "missed": "y로 먼저, 같으면 x로 정렬하려면 key에 (y, x) 튜플을 준다",   // 떠올렸어야 할 생각 한 문장
  "wrong":  "sort를 두 번 하면 된다고 생각함 (x로 먼저, y로 다시)",        // 그때 생각 (있으면)
  "state": "모름",                                 // 모름 | 잘못 앎 | 애매
  "kernel": { "lang": "python", "code": "pts.sort(key=lambda p: (p[1], p[0]))", "needs": ["pts: (x, y) 튜플의 리스트"] },
  "evidence": [                                    // 그때 장면을 가리키는 주소 (원문은 기록에 있음)
    { "type": "submission", "id": "sub_17", "lines": [4, 6], "verdict": "WA" },
    { "type": "talk", "id": "talk_33", "quote": "정렬 두번하면 안됨?" }
  ],
  "origin": { "problemId": "cp_boj_11651", "sheetId": "…" },
  "topic": "syntax.py.sort-key",                   // 같은 빈틈 합치기 · 은행 열쇠
  "ladder": { "distance": "near", "passes": 0, "fails": 0 }
}
```

- **크기**는 기록의 숫자로 코드가 정해요 (AI가 낸 값은 참고만).

| 크기 | 알고리즘 신호 | 실습 신호 |
|---|---|---|
| small | 한 번 틀리고 혼자 고침, 또는 한 번 물어봄 | 한 번 묻고 바로 적용 |
| mid | 같은 이유로 두 번 이상 틀림, 힌트 · 도움 1~2칸 | 같은 명령을 여러 번 다시 돌림, 판정 한 번 실패 |
| big | 도움 3~4칸 · 뼈대 사용 · 튜터가 코드를 줌 · 포기 · 질문 3번 이상 | 보충 단계로 내려감, 판정 여러 번 실패, 튜터가 코드를 줌 |

- **같은 빈틈 합치기**: `topic`이 같으면 한 빈틈으로 합치고 증거만 늘려요. 문법 하나를 세 문제에서 틀렸으면 빈틈은 하나, 크기는 한 단계 올라가요.

### 어떻게 뽑나

- **알고리즘**: 풀이가 끝나면 지금도 리뷰를 쓰려고 재료를 한 덩어리로 모아요(`reviewUser`: 대화 · 제출 코드 · 판정). **같은 재료로 AI를 한 번 더** 불러서 빈틈 목록(JSON)만 받아요. 앞부분이 리뷰 호출과 같아서 캐시를 타요. 출력은 빈틈마다 몇 줄이라 짧아요.
- **실습**: 빈틈이 이미 구조로 남아 있어요(`Gap`: 개념 · 틀린 생각 → 맞는 생각 · 틀린 코드 덩어리 · 막힌 이유). 목표 정리 호출의 출력에 `kind`와 `kernel` 두 칸만 더해요.
- **코드가 하는 일**: 증거 주소가 진짜 있는지(그 제출, 그 줄), 알맹이 코드가 **실제로 돌아가는지**(실행해서 확인), 크기 계산, 합치기.
- 오타 · 실수는 빈틈으로 안 뽑아요: "같은 판정 안에서 바로 고쳤고, 물은 적 없고, 한 글자 차이"면 코드가 걸러요.

## 2. 거리: 똑같이 / 비슷하게 / 응용

| 거리 | 무엇이 같고 다른가 | 만들기 | 언제 |
|---|---|---|---|
| **똑같이** | 그때 내 코드 · 그때 틀린 입력 그대로 | **AI 0번.** 기록에서 잘라 옴 | 큰 빈틈의 첫 복습, 비슷하게에서 또 틀렸을 때 |
| **비슷하게** | 같은 생각, 값 · 이름 · 작은 이야기만 바뀜 | AI 1번 또는 은행 | 보통의 첫 복습 |
| **응용** | 같은 생각이 **다른 겉모습 · 다른 문맥**에 숨어 있음. 무슨 빈틈인지 미리 말해 주지 않음 | AI 1번 | 비슷하게를 통과한 뒤 |

- **응용을 통과해야 "앎"**이에요. 똑같이 · 비슷하게만 맞히면 "그 문제를 기억하는 것"일 수 있어요.
- 사다리: 통과하면 한 칸 멀리(똑같이 → 비슷하게 → 응용), 틀리면 한 칸 가까이.
- 화면에서도 달라요. 똑같이 · 비슷하게는 "11651에서 이런 일이 있었어요"를 먼저 보여 주고, 응용은 **풀고 난 뒤에** "이건 11651에서 막혔던 그 생각이었어요"를 보여 줘요.

## 3. 형식: 장면의 모양

모든 형식은 **코드가 채점할 수 있게** 골랐어요. 말로 답하는 형식(12번)만 예외예요.

### 공통 형식 (알고리즘 · 실습 둘 다)

| # | 형식 | 학습자가 하는 일 | 화면 | 채점 | 걸리는 시간 |
|---|---|---|---|---|---|
| 1 | **한 줄 쓰기** | 주어진 변수에서 한두 줄을 써서 원하는 결과 만들기 | 작은 코드창 (위: 준비된 코드 · 가운데: 내가 쓸 줄 · 아래: 실행 결과) | 실행해서 숨은 입력 2~3개의 출력 비교 | 30초~1분 |
| 2 | **빈칸 채우기** | 뼈대 코드의 빈칸 1~3곳 채우기 | 작은 코드창 | 실행 + 숨은 테스트 | 1~2분 |
| 3 | **결과 맞히기** | 짧은 코드와 입력을 보고 출력이나 변수 값 쓰기 | 인라인 카드 | 실제로 돌린 값과 비교 | 30초~1분 |
| 4 | **틀린 곳 고치기** | 6~20줄 코드와 틀린 입력 하나를 보고 고치기 | 작은 코드창 | 함정 테스트 + 기본 테스트 | 2~4분 |
| 5 | **고르기** | 장면 2~3개마다 무엇을 쓸지 / 어떤 모양에 담을지 고르기 | 인라인 카드 | 정답 고정 | 30초~1분 |
| 6 | **순서 맞추기** | 섞인 줄 4~8개를 순서와 들여쓰기로 맞추기 | 끌어 놓기 카드 | 맞춘 코드를 실행 | 1~2분 |
| 7 | **작은 함수 쓰기** | 함수 하나(10~25줄)를 직접 쓰기. 입출력 틀은 주어짐 | 작은 코드창 (실행 · 제출) | 숨은 테스트 | 5~10분 |
| 8 | **반례 만들기** | 틀린 코드를 보고 **이 코드가 틀리는 입력**을 직접 쓰기 | 인라인 카드 + 입력 칸 | 그 입력에서 틀린 코드와 모범 코드의 출력이 다르면 통과 | 1~3분 |
| 9 | **담기 그리기** | 주어진 입력을 내가 고른 모양에 담으면 어떻게 되는지 값으로 쓰기 (예: `linked`의 내용) | 인라인 카드 | 실제로 만든 값과 비교 | 1~2분 |
| 10 | **변형 문제** | 같은 함정이 있는 짧은 새 문제를 통으로 풀기 | 알고리즘 문제 화면 | 숨은 테스트 (지금 문제 만들기 장치) | 10~20분 |
| 11 | **오류 읽기** | 오류 문구 · 로그를 보고 원인 줄이나 먼저 볼 곳 고르기 | 인라인 카드 | 정답 고정 | 30초~1분 |
| 12 | **왜인지 한 줄** | 이유를 한두 문장으로 쓰기 (다른 형식을 통과한 뒤 덧붙이는 선택 질문) | 글 칸 | AI 1번 (지금 실습 "다시 확인" 채점 그대로) | 30초 |

### 실습 전용 형식

| # | 형식 | 학습자가 하는 일 | 화면 | 채점 |
|---|---|---|---|---|
| 13 | **어디에 넣을까** | 코드에서 잠금 · 트랜잭션 · `await` · 검사를 넣을 줄 범위 고르기 | 코드 보기 카드 (줄 고르기) | 코드가 그 자리에 넣고 실행 · 검사 |
| 14 | **시간 순서 표** | 두 스레드(요청)의 걸음을 보고 ① 최종 값 맞히기 ② 값이 어긋나는 순서 만들기 | 표 카드 (걸음 끌어 놓기) | 코드가 그 순서대로 흉내 내어 계산 — **매번 같은 결과** |
| 15 | **명령 · 설정 한 줄** | 터미널 명령이나 설정 한 줄 쓰기 | 작은 터미널 칸 | 작은 예제 폴더에서 실제 실행 (안 되는 환경이면 모양 비교) |
| 16 | **작은 재현 프로젝트** | 파일 1~3개(80줄 안쪽) 프로젝트에서 같은 종류의 문제를 고치고 실행 | **앱 안 편집기(VSCodium)** + 따로 만든 작업 폴더 | 검사 스크립트 (실행 출력 확인) |
| 17 | **원래 자리로** | 내 실습 프로젝트의 그 시점 파일에서 다시 고치기 (똑같이) | 앱 안 편집기, 그 시점 저장본을 복사한 폴더 | 그 목표의 검사 그대로 |

- 지금 있는 복습은 이 표 안으로 들어와요. PS의 "내 실수 다시 보기 · 알아보기 · 설계"는 5번, "출력 예측"은 3번, 실습 "다시 확인"은 12번이에요. 없애지 않고 형식의 하나로 써요.
- 14번(시간 순서 표)은 동시성을 **AI 없이, 매번 똑같이** 채점하려고 넣었어요. 진짜 스레드를 돌리면 버그가 날 때도 안 날 때도 있어서 채점이 흔들려요.

## 4. 고르기: 종류 × 크기 × 거리 → 형식 (코드, 표 한 장)

첫 칸이 기본이고, 재료가 없으면 다음 칸으로 가요.

| 종류 | small | mid | big |
|---|---|---|---|
| 문법 | 1 한 줄 쓰기 | 1 한 줄 쓰기 ×2 (다른 상황) | 2 빈칸 → 뒤에 7 작은 함수 안에서 |
| 자료 담기 | 5 고르기 | 9 담기 그리기 | 9 → 뒤에 7 (담는 부분만 쓰기) |
| 자료 구현 | 1 한 줄 쓰기 | 2 빈칸 채우기 | 7 작은 함수 쓰기 |
| 한 줄 읽기 | 3 결과 맞히기 | 3 ×2 (값 바꿔서) | 3 → 4 틀린 곳 고치기 |
| 알고리즘 고르기 | 5 고르기 | 5 (비슷한 장면 셋을 구별) | 5 → 뒤에 10 변형 문제 |
| 알고리즘 원리 | 3 결과 맞히기 (단계별 상태) | 8 반례 만들기 | 8 → 4 |
| 알고리즘 구현 | 2 빈칸 채우기 | 6 순서 맞추기 | 7 작은 함수 쓰기 |
| 경계 · 예외 | 8 반례 만들기 | 4 틀린 곳 고치기 | 4 → 뒤에 10 |
| 문제 · 과제 읽기 | 5 고르기 (조건 읽고 예제 답 고르기) | 3 결과 맞히기 | — |
| 실행 · 도구 | 15 명령 한 줄 / 1 | 11 오류 읽기 | 16 작은 재현 프로젝트 |
| 오류 읽기 | 11 | 11 → 4 | 4 |
| (실습) 순서 · 동시성 | 14 시간 순서 표 ① | 14 ② → 13 어디에 넣을까 | 13 → 뒤에 16 작은 재현 프로젝트 |

- **거리로 바뀌는 것**: "똑같이"면 형식은 4번(알고리즘) · 17번(실습)으로 고정이에요(그때 내 코드를 고치기). "응용"이면 같은 형식을 쓰되 겉모습을 바꾸고, 작은 것 여러 개가 통과된 뒤에는 **섞어서**(여러 빈틈을 한 작은 함수에) 물어요.
- **아래층부터**: 같은 풀이에서 나온 빈틈은 층이 낮은 것부터 내요. 문법 빈틈이 한 번 통과되기 전에는 그 문법이 필요한 위층 장면(7 · 10 · 16)을 미뤄요. 위층 장면에서 또 문법에 걸리면 확인하려던 생각을 못 보기 때문이에요.
- **하루 분량**: 오늘 탭에 "확인 N개 · 약 M분"으로 보여 줘요. 기본 10분까지, 넘는 건 다음 날로.

## 5. 장면 만들기

### 똑같이: AI 없음

- 알고리즘: 그때 틀린 제출 코드를 가져오고, 빈틈의 줄 범위를 표시해요. 틀린 입력은 원래 문제의 테스트 중 **그 코드가 틀리는 가장 작은 것**을 코드가 찾아요(지금 있는 반례 찾기). 채점은 원래 문제 테스트 그대로예요.
- 실습: 그 시점 저장본(`Save`)을 새 폴더에 복사하고, 그 목표의 검사를 그대로 써요.

### 비슷하게 · 응용: AI 1번 (작게), 또는 은행

- **은행**: 문법 · 자료 구현처럼 **사람과 상관없는 장면**은 `topic`(예: `syntax.py.sort-key`)별로 한 번 만들어 두고 모두가 다시 써요. 같은 항목에 장면 3~5개가 쌓이면 더 안 만들어요. 문법 빈틈은 대부분 AI 0번이 돼요.
- **새로 만들기**: AI에게 주는 것은 빈틈(생각 한 문장 · 그때 생각 · 알맹이) + 형식 명세 + 거리예요. 받는 것은 그 형식의 JSON이에요.

```jsonc
// 형식 1 "한 줄 쓰기" 장면의 예
{
  "format": "write-line", "lang": "python", "distance": "near",
  "story": "학생 (이름, 점수) 목록이 있어요. 점수가 높은 순서로, 점수가 같으면 이름 가나다순으로 정렬해요.",
  "before": "students = [(\"민수\", 80), (\"지아\", 95), (\"가람\", 80)]",
  "ask": "students를 정렬하는 한 줄을 써 보세요.",
  "after": "print(students)",
  "reference": "students.sort(key=lambda s: (-s[1], s[0]))",
  "tests": [ { "before": "…", "trap": true }, { "before": "…", "trap": false } ],   // 숨은 입력들
  "wrongLike": "students.sort(key=lambda s: s[0]); students.sort(key=lambda s: s[1])",  // 그때 실수를 이 장면에 옮긴 것
  "explain": "기준이 여러 개면 key에 튜플을 줘요. 앞 칸이 같을 때만 뒤 칸을 봐요."
}
```

- 호출은 장면 하나에 입력 약 1.5천 · 출력 약 5백 토큰이에요. **복습 차례가 온 장면만, 다음 한 칸만** 만들어요(미리 다 만들지 않음).

### 검사: 장면이 진짜 그 생각을 확인하나 (코드)

1. **모범 답이 통과**: `reference`를 넣어 실행 → 모든 테스트 통과.
2. **그때 실수가 걸림**: `wrongLike`를 넣어 실행 → **함정 테스트에서 틀려야** 해요. 안 틀리면 이 장면은 그 빈틈을 확인하지 못하는 장면이에요.
3. **그냥은 안 풀림**: 아무것도 안 쓴 상태(빈칸 그대로)가 통과되면 안 돼요.
4. **결과 맞히기 · 담기 그리기**: 정답은 AI가 쓴 값이 아니라 **실제로 돌려서 나온 값**을 써요.
5. **고르기**: 보기가 3개 이상, 정답 하나, 보기 길이 · 모양이 비슷한지(모양으로 찍히지 않게) 코드가 봐요.
6. 실패하면 한 번 다시 만들고, 또 실패하면 **은행 → 똑같이** 순서로 물러나요. 검사를 통과하지 못한 장면은 학습자에게 안 보여요.

## 6. 채점과 반영

- **통과**: 함정 테스트를 포함해 모두 통과.
- **같은 실수**: 함정 테스트에서 틀림 → 그 빈틈은 아직 "몰랐음". 맞는 생각과 알맹이를 보여 주고, 그때 내 코드와 나란히 볼 수 있게 해요. [튜터와 다시 보기]를 누르면 이 장면과 빈틈을 들고 튜터가 열려요.
- **다른 실수**: 함정은 통과했는데 기본 테스트에서 틀림 → 이 빈틈의 기록은 안 깎아요. 한 번 더 고칠 기회를 주고, 그래도 틀리면 그 실수를 **새 작은 빈틈 후보**로 남겨요.
- **힌트 보고 통과**: [힌트]를 열었으면 "도움받고 넘어감 = 아직 몰랐음"으로 쳐요(리뷰 기준과 같음). 날짜만 조금 늦춰요.

| 결과 | 거리 | 크기 | 다음 날짜 |
|---|---|---|---|
| 통과 | 한 칸 멀리 | 한 칸 작게 (big → mid → small) | 기억 저장소 규칙대로 늘어남 |
| 응용 통과 | — | — | **앎**으로 바뀜. 이후엔 가끔 섞어서만 물음 |
| 같은 실수 | 한 칸 가까이 | 한 칸 크게 | 1~2일 뒤 |
| 두 번 연속 같은 실수 | 똑같이 | big | 다음 날 + 튜터와 다시 보기 권함 |

- 빈틈은 기억 저장소의 항목으로 남아요. 복습 날짜 · 앎/몰랐음은 지금 규칙 그대로 코드가 정해요. 알고리즘 빈틈은 그 패턴의 기억에, 실습 빈틈은 지금의 실습 기억 카드에 이어져요.

## 7. 화면

- **오늘 탭**: "알고리즘 · 확인 3개 · 약 4분", "실습 · 확인 2개 · 약 6분". 누르면 장면이 하나씩 나와요.
- **장면 카드의 틀** (형식이 달라도 같음)
  1. 위: 거리에 따라 "그때 이런 일이 있었어요"(똑같이 · 비슷하게) 또는 아무 말 없음(응용)
  2. 가운데: 형식별 몸통 (인라인 카드 / 작은 코드창 / 편집기 열기 버튼)
  3. 아래: [실행] [제출] [힌트] [모르겠어요]
  4. 답한 뒤: 결과 · 맞는 생각 한 문장 · 알맹이 코드 · [그때 내 코드 보기] · [튜터와 다시 보기]
- **세 가지 판**
  - **인라인 카드**: 3 · 5 · 6 · 8 · 9 · 11 · 13 · 14. 화면 이동 없음.
  - **작은 코드창**: 1 · 2 · 4 · 7 · 15. 알고리즘 화면의 편집기를 작게 쓴 것. 실행은 지금 채점기(파이썬 · 자바스크립트 · C++ · C# 네 언어).
  - **편집기 전체**: 10은 알고리즘 문제 화면, 16 · 17은 앱 안 편집기(VSCodium, 4103)에 따로 만든 폴더(`<데이터>/scenes/<id>/`)를 열어요. 원래 실습 폴더는 건드리지 않아요.
- **기억 탭**: 풀이 노트 · 실습 정리 안에 "이 풀이에서 나온 빈틈"과 빈틈마다 지금 상태(똑같이 ✓ · 비슷하게 ✓ · 응용 ─)를 보여 줘요.

- 각 단계는 **가상 학습자**로 시험해요: 그 빈틈을 안 배운 NPC는 장면에서 또 걸려야 하고, 배운 NPC는 통과해야 해요. 뽑은 빈틈은 NPC의 정답지와 비교해요.

## 어려운 곳 · 한계

1. **빈틈 뽑기의 정확도**: 틀린 제출 다섯 번이 이유 하나일 수도, 한 번에 두 가지일 수도 있어요. → 1단계에서 실제 기록으로 먼저 확인하고, 빈틈 카드에 [이건 아는 거였어요]를 둬서 사용자가 지울 수 있게 해요.
2. **응용 장면의 질**: 겉모습을 바꾸다 함정이 빠질 수 있어요. → 함정 테스트 검사(5번)가 막지만, "너무 어려워진 응용"은 못 막아요. 걸린 시간이 예상의 3배를 넘으면 그 장면을 표시해 두고 다음에는 안 써요.
3. **알맹이를 못 떼는 빈틈**: "문제 이해" · "알고리즘 고르기"는 코드 조각이 아니에요. → 5 · 3 형식(고르기 · 결과 맞히기)만 쓰고, 재료는 지금 있는 문제 요약 · 접근 목록을 써요.
4. **실습의 실행 환경**: 채점기가 도는 언어는 네 가지(파이썬 · 자바스크립트 · C++ · C#)예요. 다른 스택(자바 · SQL 등)의 빈틈은 실행 형식 대신 3 · 5 · 11 · 12 · 14로만 확인해요.
5. **동시성**: 진짜 스레드로는 매번 재현되지 않아요. → 작은 것은 14(시간 순서 표)로, 16(작은 재현 프로젝트)은 어긋남이 늘 나도록 읽기와 쓰기 사이에 일부러 쉼을 넣은 코드로 만들어요.
6. **검사 통과 ≠ 좋은 장면**: 문장이 어색하거나 이야기가 억지일 수 있어요. → 처음에는 만든 장면을 사용자가 몇 개 직접 보고 지시문을 고쳐요.

2. **빈틈 종류 11가지**가 맞는지(합치거나 더할 것).
3. **"앎"의 기준**: 응용 한 번 통과로 볼지, 두 번으로 볼지. (권장: 한 번. 대신 이후에도 가끔 섞어서 물음)
