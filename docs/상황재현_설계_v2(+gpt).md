## 한 줄

풀이 기록에서 **"그때 떠올리지 못한 생각" 하나하나**를 뽑고, 생각마다 **그 생각만 다시 꺼내게 하는 작은 장면**을 만들어요. 장면 길이는 확인할 것의 무게에 맞추고, 맞았는지는 **코드를 실제로 돌려서** 정하고, 왜 틀렸는지는 **증거가 있을 때만** 적어요.

## 낱말

| 낱말 | 뜻 |
|---|---|
| **빈틈** | 그때 떠올리지 못한 생각 하나. 복습의 단위예요. |
| **확인할 것** | 이 빈틈에서 볼 것이 **능력**(어떤 방법으로든 해내면 됨)인지 **표현**(바로 그 문법 · 그 도구를 쓸 수 있어야 함)인지. |
| **알맹이** | 그 생각이 담긴 가장 작은 코드 조각(3~8줄)과 한 문장. |
| **장면** | 빈틈 하나를 확인하는 작은 과제 하나. |
| **형식** | 장면의 모양. 한 줄 쓰기, 빈칸, 결과 맞히기, 고치기 … |
| **거리** | 원래 상황과 얼마나 다른가. 똑같이 / 비슷하게 / 응용 |
| **범위** | 장면의 길이(한 줄 · 조각 · 함수 · 프로젝트). **빈틈의 종류가 정해요.** |
| **세기** | 얼마나 빨리, 몇 번, 어느 거리부터 다시 묻나. **얼마나 막혔는지가 정해요.** |
| **기본 입력 / 가르는 입력** | 맞는 생각과 그때 생각이 같은 답을 내는 입력 / **서로 다른 답을 내는 입력**. |
| **오답 모양** | 그때 생각대로 풀었을 때 가르는 입력들에서 나오는 출력들. "같은 실수"의 지문이에요. |

## 전체 흐름

```
[풀이 · 실습이 끝남]
   └ ① 빈틈 뽑기 (AI 1번)   → 빈틈 + 확인할 것 + 알맹이 + 그때 코드 위치
       └ 코드 검사: 그때 생각이 정말 틀렸나(실행) · 증거 주소가 있나 · 알맹이가 돌아가나
[복습 날이 됨]
   └ ② 장면 고르기 (코드)   종류 → 범위 → 형식,  막힌 정도 → 세기(간격 · 횟수 · 거리)
   └ ③ 장면 만들기          똑같이 = AI 0번 / 비슷하게 · 응용 = AI 1번 또는 은행
   └ ④ 장면 검사 (코드)     모범 답 통과 · 다른 맞는 방법도 통과 · 그때 생각은 가르는 입력에서 틀림
[학습자가 풂]
   └ ⑤ 채점 (코드 실행)     통과 / 같은 실수(오답 모양 일치) / 다른 실수 / 원인 미확정
   └ ⑥ 반영 (코드)          앎/몰랐음 · 다음 날짜 · 다음 거리. 장면 길이는 안 바뀜
```

## 1. 빈틈: 무엇을 뽑나

### 빈틈의 종류

사용자가 말한 네 가지를 기준으로 늘렸어요. 층은 `모르는것_층_설계`의 층이에요.

| 종류 | 떠올리지 못한 것 | 층 | 알고리즘 예 | 실습 예 (FPS · 결제) |
|---|---|---|---|---|
| **문법** | 어떻게 쓰나 | 1 | `sorted(key=lambda p: (p[1], p[0]))`, `sys.stdin.readline` | C# `lock (obj) { }`, `async/await` |
| **자료 담기** | 무엇을 어떤 모양에 담나 | 2 | 연결 정보를 인접 리스트에, 방문을 배열에 | 체력을 어디에 두나, 결제 상태를 enum으로 |
| **자료 구현** | 그 모양을 코드로 만들고 쓰는 법 | 2→4 | 인접 리스트 채우기, 2차원 배열 초기화, 큐에서 꺼내기 | 딕셔너리로 플레이어 표 만들기, 큐로 메시지 쌓기 |
| **한 줄 읽기** | 이 줄 뒤 값이 어떻게 되나 | 3 | `q.pop(0)` 뒤 `q`, 자리와 값 혼동 | `Interlocked.Decrement` 뒤 값, `UPDATE`가 0줄일 때 |
| **알고리즘 고르기** | 이 문제에 왜 이 방법인가 | 6 | "퍼져 나감 → BFS", N이 커서 이중 반복은 안 됨 | 이 상황에 lock? 조건부 갱신? 멱등 키? |
| **알고리즘 원리** | 왜 이렇게 돌면 되나 | 5 | 방문 표시를 넣을 때 해야 하는 이유 | 동시에 오면 왜 둘 다 통과되나 |
| **알고리즘 구현** | 아는 방법을 코드로 잇기 | 4 | BFS 뼈대의 순서(꺼냄 → 이웃 → 표시 → 넣음) | 확인 → 빼기 → 저장을 한 잠금 안에 어떤 순서로 |
| **경계 · 예외** | 빠뜨린 경우 | 함정 | 빈 입력, 같은 값, 범위 끝 | 체력이 0 아래로, 연결 끊김, 중복 요청 |
| **문제 · 과제 읽기** | 조건을 잘못 읽음 | — | "y 먼저, 같으면 x"를 거꾸로 | 완료 조건을 다르게 이해 |
| **실행 · 도구** | 돌리고 입력 넣고 환경 맞추기 | 실행 | 입력 형식, 빠른 입력 | `dotnet run --project`, 포트 사용 중, 빌드 오류 |
| **오류 읽기** | 오류 · 로그에서 원인 찾기 | 3 / 실행 | 인덱스 오류가 난 줄에서 원인 | 스택 트레이스, 서버/클라 로그 맞춰 보기 |

### 빈틈 하나의 모양

```jsonc
{
  "id": "gap_a1f3", "branch": "algo",
  "kind": "문제 · 과제 읽기", "layer": null,
  "title": "정렬 우선순위를 거꾸로 잡음",
  "target": "ability",                              // ability(능력) | form(표현)
  "missed": "y가 먼저, y가 같을 때만 x를 본다",          // 떠올렸어야 할 생각
  "wrong":  "x로 먼저 줄 세우고, 같을 때 y를 봤다",       // 그때 생각 (있으면)
  "wrongVerified": true,                            // 코드가 확인: 그때 생각대로 풀면 원래 문제에서 실제로 틀림
  "state": "잘못 앎",
  "kernel": { "lang": "python", "code": "pts.sort(key=lambda p: (p[1], p[0]))", "needs": ["pts: (x, y) 튜플의 리스트"] },
  "evidence": [ { "type": "submission", "id": "sub_17", "lines": [4, 6], "verdict": "WA" } ],
  "origin": { "problemId": "cp_boj_11651" },
  "topic": "read.sort-priority",
  "scope": "piece",                                 // line | piece | function | project — 종류가 정함
```

### 확인할 것: 능력인가, 표현인가

- **기본은 능력**이에요. "우선순위가 있는 정렬을 해낼 수 있나"를 보는 장면에서는 튜플 key든, 두 번 정렬이든, 비교 함수든 **맞게 해내면 통과**예요. 채점이 출력 비교라서 저절로 그렇게 돼요.
- **표현**으로 잡는 건 기록에 **그 표현 자체를 못 쓴 증거**가 있을 때만이에요.
  - "key에 두 개 어떻게 넣어?"처럼 그 문법을 물었다
  - 그 문법을 쓰려다 문법 오류가 났다
  - 튜터가 그 문법을 알려 줘서 붙여 넣고 넘어갔다
- 표현을 확인하는 장면은 **형식이 그 표현을 쓰게 만들어야** 해요. 출력만 봐서는 다른 방법으로 돌아갈 수 있기 때문이에요.
  - 빈칸을 그 자리에만 둠: `pts.sort(key=lambda p: ______)`
  - 또는 한 줄 쓰기 + 구조 검사(코드가 "sort 한 번, key에 튜플"인지 봄)
- 표현 빈틈은 대개 한 줄짜리예요. 능력은 되는데 그 표현만 모르는 것이니, **급하지 않은 것으로** 다뤄요(세기 낮음).

### 범위와 세기 (v1의 "크기"를 둘로 나눔)

**범위 = 장면 길이. 빈틈의 종류가 정해요.** 확인하는 데 필요한 만큼만이에요.

| 범위 | 무엇 | 해당 종류 |
|---|---|---|
| **한 줄** (30초~1분) | 한두 줄 쓰기, 값 하나 맞히기, 고르기 | 문법, 한 줄 읽기, 실행 · 도구, 문제 읽기, 오류 읽기, 자료 담기(고르기) |
| **조각** (1~4분) | 빈칸 1~3곳, 순서 맞추기, 6~20줄 고치기, 반례 쓰기, 담기 그리기 | 자료 담기, 자료 구현, 알고리즘 원리, 경계 · 예외, 알고리즘 구현(뼈대) |
| **함수** (5~10분) | 함수 하나를 직접 쓰기 | 알고리즘 구현(혼자 못 쓴 경우), 자료 구현(혼자 못 쓴 경우) |
| **문제 · 프로젝트** (10분~) | 변형 문제, 작은 재현 프로젝트 | 알고리즘 고르기의 **응용 확인**, 실습의 순서 · 동시성 **응용 확인** |

- 종류 안에서 범위가 둘일 때(예: 알고리즘 구현이 조각 또는 함수)는 **무엇을 못 했는지**로 골라요. 한 군데 순서만 틀렸으면 조각, 튜터가 코드를 통째로 줘서 넘어갔으면 함수예요. 빈칸 채우기로는 "혼자 쓸 수 있나"를 확인하지 못하기 때문이에요.
- **틀린 횟수는 범위를 키우지 않아요.** 문법을 세 번 틀려도 한 줄이에요.

**세기 = 얼마나 빨리 · 몇 번 · 어느 거리부터. 얼마나 막혔는지가 정해요.**

| 세기 | 기록 신호 | 달라지는 것 |
|---|---|---|
| 1 | 한 번 틀리고 혼자 고침, 한 번 물어봄 | 보통 간격, 비슷하게부터, 장면 1개 |
| 2 | 같은 이유로 여러 번 틀림, 힌트 · 도움 1~2칸, 같은 빈틈이 다른 문제에서 또 나옴 | 간격 짧게, 비슷하게부터, **다른 상황으로 2개** |
| 3 | 도움 3~4칸 · 뼈대 · 튜터가 코드를 줌 · 포기 · 보충 단계 | 다음 날, **똑같이부터**, 통과해도 한 번 더 |

- 같은 빈틈(`topic`)이 여러 문제에서 나오면 하나로 합치고 **세기만** 올려요.

### 어떻게 뽑나

- **알고리즘**: 풀이가 끝나면 리뷰와 같은 재료(`reviewUser`: 대화 · 제출 코드 · 판정)로 AI를 한 번 더 불러 빈틈 목록(JSON)만 받아요. 앞부분이 리뷰 호출과 같아서 캐시를 타요.
- **실습**: 이미 구조로 남아 있는 빈틈(`Gap`)에 종류 · 확인할 것 · 알맹이 칸을 더해요.
- **코드가 하는 검사**
  1. 증거 주소가 진짜 있나(그 제출, 그 줄).
  2. 알맹이 코드가 실제로 돌아가나.
  3. **그때 생각이 정말 틀렸나**: `wrong`을 코드로 옮긴 것(AI가 같이 냄)을 원래 문제 테스트로 돌려요. **통과하면 빈틈이 아니에요**("다른 맞는 방법"). 11651의 "두 번 정렬"이 여기서 걸러져요. 표현 빈틈이면 3번 대신 표현 증거(질문 · 문법 오류)가 기록에 있는지 봐요.
  4. 범위(종류 표) · 세기(신호 표) 계산, 합치기.
  5. 오타 · 실수 거르기: 같은 판정 안에서 바로 고쳤고, 물은 적 없고, 한 글자 차이면 빈틈으로 안 뽑아요.
- 3번을 확인할 수 없는 빈틈(생각만 있고 코드로 옮길 수 없음)은 `wrongVerified: false`로 남겨요. 이런 빈틈의 장면은 "같은 실수"를 판정하지 않고 통과 / 미확정만 내요.

## 2. 거리: 똑같이 / 비슷하게 / 응용

| 거리 | 무엇이 같고 다른가 | 만들기 | 언제 |
|---|---|---|---|
| **똑같이** | 그때 내 코드 · 그때 틀린 입력 그대로 | **AI 0번.** 기록에서 잘라 옴 | 세기 3인 빈틈의 첫 복습, 비슷하게에서 또 틀렸을 때 |
| **비슷하게** | 같은 생각, 값 · 이름 · 작은 이야기만 바뀜 | AI 1번 또는 은행 | 보통의 첫 복습 |
| **응용** | 같은 생각이 **다른 겉모습 · 다른 문맥**에 숨어 있음. 무슨 빈틈인지 미리 말해 주지 않음 | AI 1번 | 비슷하게를 통과한 뒤 |

- **응용을 통과해야 "앎"**이에요. 똑같이 · 비슷하게만 맞히면 "그 문제를 기억하는 것"일 수 있어요.
- 사다리: 통과하면 한 칸 멀리(똑같이 → 비슷하게 → 응용), 틀리면 한 칸 가까이.
- 화면에서도 달라요. 똑같이 · 비슷하게는 "11651에서 이런 일이 있었어요"를 먼저 보여 주고, 응용은 **풀고 난 뒤에** "이건 11651에서 막혔던 그 생각이었어요"를 보여 줘요.

## 3. 형식: 장면의 모양

모든 형식은 **코드가 채점할 수 있게** 골랐어요. 말로 답하는 형식(12번)만 예외예요.

### 공통 형식 (알고리즘 · 실습 둘 다)

| # | 형식 | 학습자가 하는 일 | 화면 | 채점 | 걸리는 시간 |
|---|---|---|---|---|---|
| 1 | **한 줄 쓰기** | 주어진 변수에서 한두 줄을 써서 원하는 결과 만들기 | 작은 코드창 (위: 준비된 코드 · 가운데: 내가 쓸 줄 · 아래: 실행 결과) | 실행해서 숨은 입력 2~3개의 출력 비교 | 30초~1분 |
| 2 | **빈칸 채우기** | 뼈대 코드의 빈칸 1~3곳 채우기 | 작은 코드창 | 실행 + 숨은 테스트 | 1~2분 |
| 3 | **결과 맞히기** | 짧은 코드와 입력을 보고 출력이나 변수 값 쓰기 | 인라인 카드 | 실제로 돌린 값과 비교 | 30초~1분 |
| 4 | **틀린 곳 고치기** | 6~20줄 코드와 틀린 입력 하나를 보고 고치기 | 작은 코드창 | 함정 테스트 + 기본 테스트 | 2~4분 |
| 5 | **고르기** | 장면 2~3개마다 무엇을 쓸지 / 어떤 모양에 담을지 고르기 | 인라인 카드 | 정답 고정 | 30초~1분 |
| 6 | **순서 맞추기** | 섞인 줄 4~8개를 순서와 들여쓰기로 맞추기 | 끌어 놓기 카드 | 맞춘 코드를 실행 | 1~2분 |
| 7 | **작은 함수 쓰기** | 함수 하나(10~25줄)를 직접 쓰기. 입출력 틀은 주어짐 | 작은 코드창 (실행 · 제출) | 숨은 테스트 | 5~10분 |
| 8 | **반례 만들기** | 틀린 코드를 보고 **이 코드가 틀리는 입력**을 직접 쓰기 | 인라인 카드 + 입력 칸 | 그 입력에서 틀린 코드와 모범 코드의 출력이 다르면 통과 | 1~3분 |
| 9 | **담기 그리기** | 주어진 입력을 내가 고른 모양에 담으면 어떻게 되는지 값으로 쓰기 (예: `linked`의 내용) | 인라인 카드 | 실제로 만든 값과 비교 | 1~2분 |
| 10 | **변형 문제** | 같은 함정이 있는 짧은 새 문제를 통으로 풀기 | 알고리즘 문제 화면 | 숨은 테스트 (지금 문제 만들기 장치) | 10~20분 |
| 11 | **오류 읽기** | 오류 문구 · 로그를 보고 원인 줄이나 먼저 볼 곳 고르기 | 인라인 카드 | 정답 고정 | 30초~1분 |
| 12 | **왜인지 한 줄** | 이유를 한두 문장으로 쓰기 (다른 형식을 통과한 뒤 덧붙이는 선택 질문) | 글 칸 | AI 1번 (지금 실습 "다시 확인" 채점 그대로) | 30초 |

### 실습 전용 형식

| # | 형식 | 학습자가 하는 일 | 화면 | 채점 |
|---|---|---|---|---|
| 13 | **어디에 넣을까** | 코드에서 잠금 · 트랜잭션 · `await` · 검사를 넣을 줄 범위 고르기 | 코드 보기 카드 (줄 고르기) | 코드가 그 자리에 넣고 실행 · 검사 |
| 14 | **시간 순서 표** | 두 스레드(요청)의 걸음을 보고 ① 최종 값 맞히기 ② 값이 어긋나는 순서 만들기 | 표 카드 (걸음 끌어 놓기) | 코드가 그 순서대로 흉내 내어 계산 — **매번 같은 결과** |
| 15 | **명령 · 설정 한 줄** | 터미널 명령이나 설정 한 줄 쓰기 | 작은 터미널 칸 | 작은 예제 폴더에서 실제 실행 (안 되는 환경이면 모양 비교) |
| 16 | **작은 재현 프로젝트** | 파일 1~3개(80줄 안쪽) 프로젝트에서 같은 종류의 문제를 고치고 실행 | **앱 안 편집기(VSCodium)** + 따로 만든 작업 폴더 | 검사 스크립트 (실행 출력 확인) |
| 17 | **원래 자리로** | 내 실습 프로젝트의 그 시점 파일에서 다시 고치기 (똑같이) | 앱 안 편집기, 그 시점 저장본을 복사한 폴더 | 그 목표의 검사 그대로 |

- 지금 있는 복습은 이 표 안으로 들어와요. PS의 "내 실수 다시 보기 · 알아보기 · 설계"는 5번, "출력 예측"은 3번, 실습 "다시 확인"은 12번이에요. 없애지 않고 형식의 하나로 써요.
- 14번(시간 순서 표)은 동시성을 **AI 없이, 매번 똑같이** 채점하려고 넣었어요. 진짜 스레드를 돌리면 버그가 날 때도 안 날 때도 있어서 채점이 흔들려요.

- (v2) 형식 1 · 2로 **표현**을 확인할 때는 빈칸 위치나 구조 검사로 그 표현을 쓰게 만들어요. **능력**을 확인할 때는 맞는 방법을 모두 통과시켜요.
- (v2) 형식 4 · 8(고치기 · 반례 만들기)은 그 빈틈이 **출력을 틀리게 만들 때만** 쓸 수 있어요. 느려지기만 하거나 같은 일을 여러 번 하는 빈틈은 형식 3에서 "이 줄이 몇 번 실행되나"처럼 **횟수를 묻는 결과 맞히기**로 확인해요(값은 실제로 세어서 정답으로 써요).

## 4. 고르기: 종류 → 범위 → 형식 (코드, 표 한 장)

장면 길이는 종류가 정한 범위 안에서만 골라요. 세기는 표에 안 들어가요(간격 · 횟수 · 거리만 바꿔요).

| 종류 | 범위 | 형식 (앞이 기본, 재료가 없으면 다음) |
|---|---|---|
| 문법 (표현) | 한 줄 | 1 한 줄 쓰기 (+구조 검사) · 2 빈칸 한 곳 |
| 자료 담기 | 한 줄 / 조각 | 5 고르기 · 9 담기 그리기 |
| 자료 구현 | 조각 / 함수 | 2 빈칸 채우기 · 1 한 줄 쓰기 / (혼자 못 썼으면) 7 작은 함수 — 담는 부분만 |
| 한 줄 읽기 | 한 줄 | 3 결과 맞히기 |
| 알고리즘 고르기 | 한 줄 (응용 확인만 문제) | 5 고르기 (비슷한 장면 셋을 구별) → 응용 확인에서 10 변형 문제 |
| 알고리즘 원리 | 조각 | 3 결과 맞히기(단계별 상태 · 횟수) · 8 반례 만들기(출력이 달라질 때만) |
| 알고리즘 구현 | 조각 / 함수 | 6 순서 맞추기 · 2 빈칸 / (혼자 못 썼으면) 7 작은 함수 |
| 경계 · 예외 | 조각 | 8 반례 만들기 · 4 틀린 곳 고치기 |
| 문제 · 과제 읽기 | 한 줄 | 5 고르기(조건을 읽고 맞는 출력 고르기) · 3 결과 맞히기 |
| 실행 · 도구 | 한 줄 | 15 명령 한 줄 · 1 · 11 오류 읽기 |
| 오류 읽기 | 한 줄 / 조각 | 11 · 4 |
| (실습) 순서 · 동시성 | 조각 (응용 확인만 프로젝트) | 14 시간 순서 표 · 13 어디에 넣을까 → 응용 확인에서 16 작은 재현 프로젝트 |

- **똑같이**는 그때 내 코드를 쓰지만 범위는 지켜요. 한 줄 범위의 빈틈이면 그때 코드에서 **그 줄 근처만** 잘라 보여 주고 그 줄을 다시 쓰게 해요. 조각 이상이면 4번(알고리즘) · 17번(실습)이에요.
- **응용**은 같은 범위에서 겉모습을 바꿔요. 한 줄 범위의 빈틈 여러 개가 통과된 뒤에는 **하나의 작은 함수에 섞어서** 물을 수 있어요(각 빈틈의 길이를 키우는 게 아니라, 여러 개를 한 번에 확인하는 거예요).
- **아래층부터**: 같은 풀이에서 나온 빈틈은 층이 낮은 것부터 내요. 문법 빈틈이 한 번 통과되기 전에는 그 문법이 필요한 함수 · 문제 범위 장면을 미뤄요.
- **하루 분량**: 오늘 탭에 "확인 N개 · 약 M분". 기본 10분까지, 넘는 건 다음 날로.

## 5. 장면 만들기

### 똑같이: AI 없음

- 알고리즘: 그때 틀린 제출 코드와 빈틈의 줄 범위를 가져와요. 틀린 입력은 원래 문제 테스트 중 **그 코드가 틀리는 가장 작은 것**을 코드가 찾아요. 채점은 원래 문제 테스트예요.
- 실습: 그 시점 저장본(`Save`)을 새 폴더에 복사하고, 그 목표의 검사를 그대로 써요.

### 비슷하게 · 응용: AI 1번 (작게), 또는 은행

- **은행**: 문법 · 자료 구현처럼 사람과 상관없는 장면은 `topic`별로 한 번 만들어 두고 다시 써요.
- **새로 만들기**: 빈틈(생각 · 그때 생각 · 확인할 것 · 알맹이) + 형식 명세 + 거리를 주고, 그 형식의 JSON을 받아요.

```jsonc
// 형식 5가 아니라 형식 1(능력 확인)로 만든 예: "우선순위가 있는 정렬"
{
  "format": "write-line", "lang": "python", "distance": "near", "target": "ability",
  "story": "학생 (이름, 점수) 목록이 있어요. 점수가 높은 순서로, 점수가 같으면 이름 가나다순으로 정렬해요.",
  "before": "students = [(\"민수\", 80), (\"지아\", 95), (\"가람\", 80)]",
  "ask": "students를 정렬하는 코드를 써 보세요. (한 줄이 아니어도 돼요)",
  "after": "print(students)",
  "reference": "students.sort(key=lambda s: (-s[1], s[0]))",
  "alsoRight": [ "students.sort(key=lambda s: s[0]); students.sort(key=lambda s: s[1], reverse=True)" ],  // 다른 맞는 방법 — 통과해야 함
  "wrongs": [                                                   // 예상한 틀린 생각들 (그때 생각이 첫째)
    { "id": "mine",  "what": "우선순위를 거꾸로 (이름 먼저, 같으면 점수)", "code": "students.sort(key=lambda s: (s[0], -s[1]))" },
    { "id": "other", "what": "점수 방향을 안 뒤집음",                   "code": "students.sort(key=lambda s: (s[1], s[0]))" }
  ],
  "inputs": [
    { "role": "basic", "before": "…점수 · 이름이 모두 다르고 이미 순서대로…" },   // 맞는 생각도 틀린 생각도 같은 답
    { "role": "split", "before": "…점수가 같은 사람이 있음…", "splits": ["mine", "other"] },
    { "role": "split", "before": "…이름 순서와 점수 순서가 반대…", "splits": ["mine"] }
  ],
  "explain": "먼저 볼 기준이 앞이에요. 앞 기준이 같을 때만 뒤 기준을 봐요."
}
```

- 정답과 오답 모양은 **AI가 쓴 값이 아니라 코드가 돌려서** 만들어요: `reference`의 출력이 정답, 각 `wrongs`의 출력이 그 생각의 오답 모양이에요.

### 검사: 장면이 진짜 그 생각을 확인하나 (코드)

1. **모범 답이 통과**: `reference`가 모든 입력에서 정답.
2. **다른 맞는 방법도 통과** (능력 확인일 때): `alsoRight`가 모두 통과해야 해요. 떨어지면 장면이 한 가지 표현만 강요하는 거예요. 원래 문제에서 학습자가 **결국 맞힌 방법**을 이 장면에 옮긴 것도 여기 넣어요.
3. **그때 생각은 틀림**: `wrongs[mine]`이 가르는 입력에서 틀려야 해요. 안 틀리면 이 장면은 그 빈틈을 확인하지 못해요.
4. **가르는 입력이 정말 가르나**: 틀린 생각들의 오답 모양이 **서로, 그리고 정답과 달라야** 해요. 두 틀린 생각이 모든 입력에서 같은 출력을 내면 둘을 구별할 수 없으니, 그 둘은 하나의 "원인 묶음"으로만 판정해요.
5. **기본 입력은 모두가 맞힘**: 기본 입력에서는 틀린 생각들도 정답을 내야 해요(그래야 "기본은 맞고 가르는 입력만 틀림"이 뜻을 가져요).
6. **그냥은 안 풀림**: 아무것도 안 쓴 상태가 통과되면 안 돼요.
7. 결과 맞히기 · 담기 그리기의 정답은 실제로 돌린 값. 고르기는 보기 수 · 길이 · 모양 검사.
8. 실패하면 한 번 다시 만들고, 또 실패하면 은행 → 똑같이로 물러나요. 검사를 통과하지 못한 장면은 안 보여요.

## 6. 채점과 반영

### 판정 넷

| 판정 | 조건 | 뜻 |
|---|---|---|
| **통과** | 모든 입력에서 정답 | 그 생각을 꺼냄 |
| **같은 실수** | 기본 입력은 맞고, 가르는 입력들의 출력이 **그때 생각의 오답 모양과 일치** | 그때 그 생각이 그대로 남아 있음 |
| **다른 실수** | 출력이 **다른 틀린 생각**(`wrongs`의 다른 것)의 오답 모양과 일치 | 이 빈틈이 아니라 다른 것. 그 생각을 새 빈틈 후보로 |
| **원인 미확정** | 틀렸는데 어느 모양과도 안 맞음, 기본 입력부터 틀림, 실행 오류, `wrongVerified: false` | 틀린 건 맞지만 **왜인지는 모름** |

- 고르기 형식은 보기마다 "이 보기를 고르면 어떤 생각"이 붙어 있어서, 고른 보기로 판정해요.
- 결과 맞히기는 쓴 값이 그때 생각대로 계산한 값과 같으면 같은 실수, 아니면 미확정이에요.
- **힌트를 보고 통과**하면 "도움받고 넘어감 = 아직 몰랐음"으로 쳐요(리뷰 기준과 같음).
- **"모르겠어요"**를 누르면 몰랐음이에요(원인은 "떠올리지 못함"으로 적어요).

### 반영

| 판정 | 앎/몰랐음 | 다음 날짜 | 거리 | 장면 길이 |
|---|---|---|---|---|
| 통과 | 그대로 진행 | 규칙대로 늘어남 | 한 칸 멀리 | 그대로 |
| 응용 통과 | **앎** | 길게. 이후엔 가끔 섞어서만 | — | 그대로 |
| 같은 실수 | 몰랐음, 세기 +1 | 1~2일 뒤 | 한 칸 가까이 | **그대로** |
| 같은 실수 두 번 연속 | 몰랐음 | 다음 날 | 똑같이 | 그대로. [튜터와 다시 보기]를 권함 |
| 다른 실수 | 이 빈틈은 **기록 안 깎음** | 한 번 더 기회, 며칠 뒤 다시 | 그대로 | 그대로 |
| 원인 미확정 | 몰랐음으로 치되 **"원인 미확정"으로 남김**. 세기는 안 올림 | 2~3일 뒤 | 그대로 | 그대로. 두 번 연속이면 **똑같이**로 가서 그때 코드로 확인 |

- 틀린 뒤에는 맞는 생각 한 문장과 알맹이, [그때 내 코드 보기], [튜터와 다시 보기]를 보여 줘요. 미확정일 때는 "어디서 달라졌는지"(내 출력과 정답이 처음 갈린 입력)를 같이 보여 줘요.
- 원인 미확정이 쌓이는 빈틈은 **빈틈 뽑기가 틀렸을 수 있다**는 신호예요. 그런 빈틈은 표시해 두고 사람이(또는 튜터 대화에서) 다시 잡아요.
- 빈틈은 기억 저장소의 항목으로 남고, 복습 날짜 · 앎/몰랐음은 지금 규칙대로 코드가 정해요.

## 8. 예시

### 알고리즘: 11651 좌표 정렬하기 2 (y 먼저, 같으면 x)

먼저 **빈틈이 아닌 것**: "x로 정렬한 뒤 y로 정렬"은 맞는 풀이예요(정렬이 순서를 지켜 줘서). 뽑기 검사 3번이 이걸 걸러요.

| 기록에 이런 증거가 있으면 | 빈틈 | 확인할 것 · 범위 | 장면 |
|---|---|---|---|
| y 먼저 → x 나중으로 두 번 정렬해서 틀림 / (x, y) 튜플로 정렬해서 틀림 | 우선순위를 거꾸로 잡음 | 능력 · 한 줄 | **한 줄 쓰기**: 학생을 점수 높은 순, 같으면 이름순. 튜플 key도, 두 번 정렬도 맞으면 통과. 가르는 입력: 점수가 같은 사람이 있는 것 / 이름 순서와 점수 순서가 반대인 것 |
| "key에 두 개 어떻게 넣어?"라고 물었거나, 튜터가 준 `key=lambda p: (p[1], p[0])`를 붙여 넣음 | 기준 두 개를 튜플로 주는 표현 | 표현 · 한 줄 · 세기 낮음 | **빈칸 한 곳**: `words.sort(key=lambda w: ______)` (길이순, 같으면 가나다순) |
| 조건 문장을 반대로 읽고 처음부터 x 기준으로 풂 | 문제 조건 읽기 | 능력 · 한 줄 | **고르기**: 조건 문장과 점 4개를 보고 맞는 출력 고르기 (보기마다 "어느 기준을 먼저 봤나"가 붙음) |
| 입력을 느리게 받아 시간 초과 | 빠른 입력 | 표현 · 한 줄 | **한 줄 쓰기**: N줄을 `sys.stdin.readline`으로 읽기 (은행) |

## 어려운 곳 · 한계

1. **빈틈 뽑기의 정확도**: 뽑기 검사 3번이 "틀리지 않은 생각"은 걸러 주지만, "틀렸지만 원인은 다른 것"은 못 걸러요. → 원인 미확정이 쌓이는 빈틈을 다시 보는 장치(6번)와, 빈틈 카드의 [이건 아는 거였어요].
2. **오답 모양이 우연히 맞을 수 있어요.** 가르는 입력이 하나면 특히 그래요. → 같은 실수 판정에는 가르는 입력 둘 이상을 요구하고, 모자라면 미확정으로 내요.
3. **틀린 생각을 다 예상할 수 없어요.** `wrongs`에 없는 생각으로 틀리면 미확정이에요. 미확정 답안이 쌓이면 그걸 보고 그 주제의 `wrongs`를 늘려요(은행에 같이 저장).
4. **표현 확인은 구조 검사가 필요해요.** 언어마다 "이 표현을 썼나"를 보는 규칙을 따로 써야 하고, 문법 항목마다 하나씩이라 손이 가요. → 빈칸 형식(위치로 강제)을 먼저 쓰고, 구조 검사는 자주 나오는 항목만.
5. **출력으로 안 드러나는 빈틈**(느림 · 중복)은 횟수 맞히기로만 확인돼요. 직접 고쳐 보는 장면은 그 빈틈이 채점에서 드러난 기록이 있을 때만 만들 수 있어요.
6. 응용 장면의 질, 알맹이를 못 떼는 빈틈, 실습의 실행 환경(네 언어), 동시성, "검사 통과 ≠ 좋은 장면"은 v1과 같아요.
