## 1. 제품 방향과 사용자 결정

개인 학습자료를 실제로 기억하고 사용할 수 있는 반복학습 문제로 바꾸는 도구다. 사용자는 보통 자료를 직접 가져오며 PC·폰·태블릿에서 공부하려 한다.

- 학교 자료: 원문의 세부 내용과 표현을 함부로 생략하지 않는다. 원문 보존과 모든 문장을 문제로 만드는 것은 다르다.
- 영어 표현: 한국어 의미를 보고 완성된 영어 문장을 떠올리는 방식도 지원한다. 요청하지 않은 빈칸 힌트를 붙이지 않는다.
- 코딩: Python·C#·Java, VS Code와 기존 Codex 확장을 활용하는 방향이다. 전용 편집기를 크게 만드는 것보다 복붙 부담과 공부 기록 부담을 줄이는 것이 중요하다.
- 학습 기억: 익힌 내용·부족한 점을 기록하고 설명과 다음 학습에 활용한다. 설명을 읽었다는 이유만으로 숙달했다고 기록하지 않는다.
- 정리·제안은 사용자가 원할 때 받는 방향이다. 자동 갱신의 세부 주기와 실제 동작은 해당 구현을 확인한다.
- 장기적으로 내부 PDF 보기, 원문 위 강조, 학습 흔적과 분야별 기억을 연결한다. 이번 인수인계는 이 기능들을 새로 구현하라는 요청이 아니다.

## 2. 생성엔진과 문제작성 실험

논의한 책임 구분은 다음과 같다. 실제 호출 순서와 입출력은 **선택한 코드 버전에서 다시 확인**한다.

| 단계 | 책임 |
| --- | --- |
| Analyze | 원문을 세세한 목차형 구조로 파악하고 페이지·하위 항목과 연결 |
| 사용자 선택 | 학습할 범위와 목적 지정 |
| Plan | 선택 범위와 목적에 맞춰 학습목표·핵심 범위·후순위와 이유 결정 |
| Learning Design | 목표별 지식 단위와 무엇을 답하게 할지 설계 |
| Authoring | 실제 질문·정답과 텍스트·빈칸·보기·기호·그림 배치 작성 |
| 학습 루프 | 풀이 또는 인출 → 채점·자기평가 → 기록 → 복습 |

현재 실험은 기존 생성엔진의 내용 설계를 활용하면서, 문제의 형식은 AI가 편집 요소를 조합해 만들게 하는 것이다. 고정 유형별 화면만 주는 방식이 아니라 문서 편집기 같은 틀을 제공한다. 답안과 채점 연결은 안정적으로 유지해야 한다.

- 객관식·빈칸·OX·플래시카드·순서·구조 표현 등 다양한 유형과 그래프 문제를 실험했다. 사용자는 여러 유형을 대체로 표현할 수 있다고 평가했다. 모든 자료에서 품질이 입증된 것은 아니다.
- 현대적이고 둥근 화면과 Pretendard 시안에 긍정적인 피드백이 있었다. 과한 장식은 원하지 않는다.
- 최신 실험 코드에는 Learning Design → Authoring 연결과 단계별 결과 보존 커밋이 있다. 실제 제품 학습 화면까지 통합 완료했다고 해석하지 않는다.
- **MCP 실험 → 결과 검수 → API 실험** 순서다. 인수인계만으로 유료 생성 테스트를 새로 실행하지 않는다.
- MCP는 에이전트가 도구를 단계적으로 사용하는 경로, API는 앱이 모델을 직접 호출하는 경로다. 사용자 결정상 API의 구조화 JSON 출력에 MCP 자연어용 후처리를 그대로 적용하지 않는다.
- 출력 형식 검사 통과와 문제 품질 검수는 다르다. 실제 화면, 정답의 유일성, 학습목표, 원문 충실성을 따로 본다.

출제 근거와 검수표: [시험 출제 방법론 조사](../research/EXAM_ITEM_DESIGN_RESEARCH.md). 이 문서는 조사·제안이며 전부 구현되어 있다는 뜻이 아니다.

## 4. 지금 이어서 할 일

1. **기획**: 이 문서와 출제 방법론을 읽으면 이어서 논의할 수 있다. 가장 최근에는 경쟁 제품 비교, 특히 유니브 AI의 자료 → 요약 → 문제·암기 흐름을 살펴봤다. 사용자는 우리 방향과 유사하다고 보았다.
2. **비교 조사**: 이용 규모와 검색 관심도는 비교군 선정 근거로 보되 생성 품질 순위와 섞지 않는다. 유니브 AI도 비교군에 포함한다. 전체 조사·실제 화면 검토 기록은 아직 이 브랜치에 없다. 상세 수치나 품질 결론을 재구성해서 사실처럼 쓰지 않는다.
3. **문제작성 개발**: 위 실험 커밋과 필요한 결과물을 먼저 이전하고 실행을 확인한다. 이 브랜치만 보고 이미 합쳐졌다고 판단하거나 과거 엔진에서 변경을 시작하지 않는다.
4. **외부 공유**: 교수님에게 공유하는 것은 사용자가 자료를 완성한 뒤 직접 한다. 제품 차별점은 아직 확정해서 쓰지 않는다.

## 5. 두 컴퓨터의 협업 규칙

- 기획 담당은 의사결정과 검수, 프로덕션 구현은 별도 담당이 맡는다. 작업 전에 책임·수정 파일·완료 기준을 기록한다.
- 같은 파일을 두 담당이 동시에 수정하지 않는다. 공용 타입·설정은 한 담당만 맡는다. 겹치면 순차 진행한다.
- 시작할 때 `git status`와 브랜치·커밋을 확인한다. 사용자의 미완료 변경을 되돌리거나 전체를 한꺼번에 커밋하지 않는다.
- 끝날 때 커밋·원격 업로드 여부·검증 결과·남은 일을 남긴다. 완료했다고 보고한 작업도 검증 범위를 함께 쓴다.
- 예약 감시를 새로 만들지 않는다. 담당 작업에 보고를 요청해 기획 담당이 결과를 확인한다.
- GitHub는 코드·문서를 전달한다. 기존 대화 기억, 실행 중 에이전트, 로그인, API 키, 로컬 데이터까지 이전하지는 않는다.

```text
담당 / 목적:
브랜치 / 시작 커밋:
수정 파일:
완료 기준:
완료 커밋 / GitHub 업로드 여부:
검증한 것 / 확인하지 못한 것:
남은 일 / 다음 담당:
```

## 6. 노트북에서 시작

저장소 접근 권한이 있는 환경에서:

```sh
git clone --branch codex/laptop-handoff https://github.com/starvvolf/EasyMemory.git
cd EasyMemory
```

이미 받은 저장소라면 현재 변경을 확인한 뒤 원격 브랜치를 받아 별도 작업 공간에서 연다. 강제 초기화하지 않는다.

코드 작업 전 `AGENTS.md`, `docs/PLANNING_RULES.md`를 읽고, 생성·학습 변경이라면 `docs/GENERATION_ENGINE_BOUNDARY.md`도 읽는다. 문서와 최신 대화 결정이 다르면 시점을 확인한다. 개발 실행에는 해당 버전의 Node.js·의존성·환경 설정이 필요하며 설치 성공은 아직 노트북에서 검증하지 않았다.

API 키와 로그인은 노트북에서 별도 설정한다. `.env`나 인증 파일을 GitHub에 올리지 않는다. 브라우저 학습 데이터, 원본 PDF, `.study-forge-data`도 Git clone만으로 옮겨지지 않는다. 필요한 데이터만 별도 이전한다.

ChatGPT 앱이 저장소를 읽을 수 있는지는 연결 상태에 달려 있다. 접근이 안 되면 이 문서와 필요한 참고 문서를 직접 제공한다. GitHub 업로드만으로 앱이 자동으로 기억한다고 가정하지 않는다.
