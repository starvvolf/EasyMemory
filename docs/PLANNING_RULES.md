# Planning Rules

## 기본 태도

이 프로젝트의 사용자는 개발 전문 용어에 익숙하지 않다.
기획과 설계 논의에서는 구현자끼리 쓰는 용어보다
"무엇을 왜 하는지"를 먼저 설명한다.

목표는 복잡해 보이는 설계를 만드는 것이 아니라
사용자가 다음 결정을 쉽게 내릴 수 있게 만드는 것이다.

## 가장 중요한 원칙

1. 문제를 먼저 정의한다.
2. 현재 제품이 할 수 있는 것과 없는 것을 구분한다.
3. 가장 작은 변경으로 문제를 해결할 수 있는지 먼저 본다.
4. 필요성이 확인되지 않은 구조, 계층, 추상화는 추가하지 않는다.
5. 미래 확장 가능성만을 이유로 현재 구조를 복잡하게 만들지 않는다.
6. 새로운 개념을 만들기 전에 기존 개념으로 설명 가능한지 확인한다.

## 과설계 금지

다음 행동을 기본적으로 피한다.

- 아직 필요하지 않은 시스템을 미리 구현하기
- 하나의 기능을 위해 여러 추상 계층 만들기
- 이름만 다른 비슷한 개념을 계속 추가하기
- 모든 가능성을 하나의 범용 시스템으로 해결하려 하기
- "확장성", "유연성", "엔터프라이즈급" 같은 이유만으로 복잡성을 추가하기
- 사용자가 요청하지 않은 리팩터링을 함께 진행하기

필요하면 먼저 단순한 버전을 제안한다.

예:

나쁜 방향:
LearningCapabilityResolver
→ ActivityStrategyRegistry
→ ActivityProvider
→ ActivityExecutionAdapter

좋은 방향:
각 학습 단위에
"현재 지원 가능 여부"
"추천 활동"
두 값을 붙인다.

복잡성이 실제로 필요해진 뒤에 구조를 확장한다.

## 용어 사용 규칙

전문 용어는 필요한 경우에만 사용한다.

전문 용어를 처음 사용할 때는 반드시 쉬운 한국어 설명을 붙인다.

예:

- Artifact(실험 결과 파일)
- Freeze(앞 단계 결과를 고정)
- Activity Design(어떤 방식으로 훈련할지 결정하는 단계)

단순한 개념에 새로운 영어 이름을 붙이지 않는다.

가능하면 사용자가 이미 쓰고 있는 표현을 그대로 사용한다.

## 기획할 때의 사고 순서

새 기능이나 구조를 제안하기 전에 다음 순서로 생각한다.

1. 지금 문제가 정확히 무엇인가?
2. 현재 시스템은 어떻게 동작하는가?
3. 실제로 부족한 부분은 어디인가?
4. 기존 구조를 조금 수정해서 해결 가능한가?
5. 새 개념이 정말 필요한가?
6. 지금 구현해야 하는 최소 범위는 어디까지인가?

## 제안 형식

기획안을 설명할 때 가능하면 다음 순서를 사용한다.

현재:
지금 시스템이 어떻게 동작하는지.

문제:
왜 현재 방식이 부족한지.

변경:
무엇을 바꾸면 되는지.

예시:
실제 데이터가 어떻게 달라지는지.

지금 안 하는 것:
이번 단계에서 일부러 구현하지 않는 것.

## 사용자와 의사결정

여러 선택지가 있을 경우
처음부터 하나를 임의로 구현하지 않는다.

중요한 설계 선택이면 다음처럼 설명한다.

A안:
장점 / 단점

B안:
장점 / 단점

추천:
왜 이쪽이 현재 단계에 더 맞는지

단, 사소한 구현 세부사항까지 사용자에게 선택시키지 않는다.
AI가 판단 가능한 것은 알아서 판단한다.

## 구현 전 확인

사용자가 "구현해", "바꿔", "진행해"라고 명확히 요청하기 전에는
기획 논의 중에 프로덕션 코드를 수정하지 않는다.

기획 단계에서는:

- 현재 코드 확인
- 문제 분석
- 변경안 제안
- 영향 범위 확인

까지만 한다.

## 프로젝트 철학

이 프로젝트는 작은 개념들이 명확한 역할을 가지고 조합되어
전체적으로 강력한 시스템이 되는 방향을 선호한다.

각 구성 요소는 가능하면
"이게 무엇을 하는지 한 문장으로 설명할 수 있어야 한다."

한 문장으로 설명하기 어려울 정도로 복잡하다면
구조가 필요 이상으로 복잡해졌는지 다시 검토한다.
