## 한 줄

**"모르는 척"을 AI에게 맡기지 않아요.** 무엇을 모르고 언제 막힐지는 **코드(연출가)**가 정하고, AI는 그 대본대로 **말과 코드만** 써요. 쓴 것은 진짜 채점기와 검사 코드가 다시 확인해요.

## 왜 이렇게 나누나

AI에게 "BFS를 모르는 학생처럼 풀어 봐"라고만 하면 세 가지가 깨져요.
1. **샌다**: 모른다면서 슬쩍 맞게 풀어요.
2. **들쭉날쭉하다**: 같은 설정인데 돌릴 때마다 다른 사람이 돼요. 실험을 다시 못 해요.
3. **비싸다**: 판단까지 맡기면 큰 모델을 길게 여러 번 불러야 해요.

그래서 일을 셋으로 나눠요.

| 조각 | 누가 | 하는 일 | AI |
|---|---|---|---|
| **명세** | 데이터(JSON) | 이 학습자가 무엇을 알고, 어떤 성격인지 | 없음 |
| **연출가** | 코드 | 지금 무엇을 할지, 어디서 막힐지, 배웠는지 정함. 씨앗(seed) 주사위라 다시 돌리면 똑같음 | 없음 |
| **입과 손** | AI (작은 호출) | 연출가가 준 대본대로 질문 한마디, 코드 한 벌을 씀 | luna · terra low |
| **검사** | 코드 + 진짜 채점기 | 쓴 코드가 대본대로 틀리는지, 모르는 걸 쓰지 않았는지 | 없음 |
| **정답지** | 코드 | "이때 이것 때문에 막혔다"를 한 줄씩 남김 → 나중에 리뷰 · 상황 재현을 채점하는 기준 | 없음 |

## 1. 학습자 명세

```jsonc
{
  "id": "npc_minsu", "seed": 7, "name": "민수",
  "lang": "python",                    // 주로 쓰는 언어
  "knows": {                           // 아는 것: 층별 기본값 + 항목별 덮어쓰기
    "base": { "1": "앎", "2": "앎", "3": "애매", "4": "애매", "5": "모름", "6": "모름", "run": "앎" },
    "items": {
      "syntax.py.sort-key":   { "state": "모름" },
      "pattern.bfs-distance": { "state": "잘못 앎", "belief": "방문 표시는 큐에서 꺼낼 때 한다" },
      "concept.queue":        { "state": "앎" }
    }
  },
  "traits": {                          // 성격 (0~1)
    "askEarly": 0.3,      // 막히면 바로 묻는 정도 (낮으면 혼자 버팀)
    "guess": 0.4,         // 이유 없이 고쳐서 다시 내 보는 정도
    "helpRungs": 0.5,     // 도움 칸 · 힌트를 여는 정도
    "copyTutor": 0.2,     // 튜터가 준 코드를 그대로 붙이는 정도
    "confirm": 0.3,       // "이건가?" 확인 요청을 연달아 하는 정도
    "patience": 20,       // 포기 전까지 할 수 있는 행동 수 (기본 20, 옵션으로 8~40)
    "typo": 0.1,          // 아는데도 실수하는 정도 (오타, 경계 하나 빼먹기)
    "terse": 0.7          // 말이 짧은 정도 ("이거 왜 안 됨?")
  },
  "learning": {
    "perExplain": 0.6,    // 설명 한 번에 알게 될 확률
    "perHint": 0.3,       // 힌트만 받고 알게 될 확률
    "fromOwnFix": 0.5,    // 혼자 고쳐서 맞혔을 때 알게 될 확률
    "forgetPerDay": 0.03  // 하루 지날 때 앎 → 애매로 돌아갈 확률 (복습 실험용)
  }
}
```

- **아는 것의 항목**은 새로 짓지 않고 이미 있는 이름을 써요.
  - 5 · 6층: `patterns.ts` 패턴 44개, `concepts.ts` 개념 28개
  - 1층 · 실행: 언어별 문법 목록(언어마다 약 30개, 한 번 만들어 고정). 예) `syntax.py.sort-key`, `syntax.cs.lock`
  - 2~4층: 문제 지식 지도(아래 2번)가 그 문제에서 쓰는 항목을 내요.
  - 실습: 그 실습 계획의 줄기와 스택에서 뽑아요. 예) `concept.race-condition`, `syntax.cs.async-await`
- 상태 네 가지(앎 · 모름 · 잘못 앎 · 애매)는 모르는것_층_설계 그대로예요. **잘못 앎**에는 틀린 믿음을 한 문장으로 적어요. 연출가가 그 믿음대로 코드를 쓰게 해요.

### 옵션: 기본값에 붙이는 조각

기본 학습자(`default.json`) 하나에 **옵션 조각**을 겹쳐서 사람을 만들어요. 조각은 명세의 일부만 담은 작은 JSON이에요.

```jsonc
// options/문법약함-py.json
{ "id": "문법약함-py", "label": "파이썬 문법이 약함", "patch": { "knows": { "base": { "1": "모름" } }, "traits": { "typo": 0.2 } } }
```

```
node lab/npc/run.mjs --problem 11651 --with 문법약함-py,버티기,설명두번 --seed 3
```

처음에 넣을 조각(약 15개):

| 묶음 | 조각 |
|---|---|
| 아는 것 | 문법약함(언어별) · 읽기약함(3층) · 잇기약함(4층) · 원리모름(패턴 지정) · 방법못고름(6층) · 잘못앎(패턴 + 믿음 지정) · 다른언어에서옴(파이썬은 알고 C#은 처음) · 고수 |
| 성격 | 바로묻기 · 버티기 · 찍어내기 · 힌트의존 · 복붙형 · 확인연타 · 포기빠름 · 말짧음 |
| 배움 | 한번에앎 · 설명두번 · 금방잊음 |

- 겹칠 때는 뒤에 쓴 조각이 이겨요. 숫자는 코드가 0~1로 잘라요.
- 조각끼리 부딪치면(고수 + 문법약함) 실행 전에 알려 줘요.

### 옵션을 AI로 만들기

```
node lab/npc/make.mjs "C#은 처음이고 파이썬은 좀 하는 2학년. 질문을 못 참고, 튜터 코드를 그대로 붙여 넣음"
```

- AI 1번(terra low, 출력은 조각 JSON 하나)이 사람 설명을 조각으로 바꿔요.
- 코드가 모양을 검사해요(Zod). 없는 항목 이름은 버리고, 숫자는 범위로 잘라요.
- 결과를 사람이 읽을 수 있게 다시 풀어 보여 줘요: "1층(C#) 모름, 1층(파이썬) 앎, 바로 묻기 0.9, 복붙 0.8 …". 마음에 들면 `options/`에 저장해서 계속 써요.
- **기록에서 만들기**: 실제 풀이 기록(예: 사용자 본인의 2606 층 검증 표)을 주면 그 사람을 닮은 조각을 만들어요. "나 닮은 NPC"로 내가 겪은 흐름을 다시 돌려 볼 수 있어요.
- **한꺼번에 만들기**: "초보 5명을 서로 다르게"처럼 시키면 조각 여러 개를 한 번에 내요. 코드가 서로 너무 비슷한 것(값 차이가 작은 것)은 걸러요.

## 2. 문제 지식 지도 (문제마다 한 번, 모든 NPC가 같이 씀)

NPC가 어디서 막힐지 정하려면 **이 문제가 무엇을 요구하는지**가 있어야 해요.

- 알고리즘은 재료가 이미 있어요(`ProblemModel`): 패턴, 맞는/느린/틀린 접근(`approaches`), 흔한 함정(`pitfalls`), 틀린 상태 설계(`state.wrong`), 검증된 모범 풀이.
- 모자란 건 1~4층 항목이에요. **AI 1번(terra low)**이 모범 풀이를 읽고 "이 풀이는 이 문법 · 이 담기 · 이 순서를 쓴다"를 항목 목록으로 내요. 문제마다 한 번 만들어 `lab/npc/out/maps/<문제>.json`에 두고 다시 써요.
- 항목마다 **증상 후보**를 같이 적어요: 이걸 모르면 코드가 어떻게 틀리나.

| 층 | 모르면 나오는 증상 (예) | 채점기에서 |
|---|---|---|
| 1 문법 | 없는 문법을 지어 씀, 인자 순서 틀림 | 컴파일 오류 · 실행 오류 |
| 2 담기 | 2차원이어야 할 걸 1차원에 담음 | 틀림 · 실행 오류 |
| 3 한 줄 읽기 | 자리와 값을 헷갈림, 하나 차이 | 틀림 |
| 4 잇기 | 조각이 반복문 밖/안에 잘못 있음 | 틀림 · 시간 초과 |
| 5 원리 | 방문 표시를 늦게 함 | 시간 초과 · 틀림 |
| 6 방법 고르기 | `approaches`의 slow · wrong 접근으로 풂 | 시간 초과 · 틀림 |
| 실행 | 입력을 잘못 받음 | 실행 오류 |
| 함정 | `pitfalls` 하나를 빼먹음 | 경계 테스트에서 틀림 |

- 실습은 목표마다 같은 지도를 만들어요(목표 문장 · 완료 조건 · 시작 코드에서). 증상은 "빌드 실패 · 실행해도 출력이 틀림 · 검사 통과 못 함"이에요.

## 3. 연출가 (코드, AI 없음)

명세와 지식 지도를 겹치면 **이 NPC가 이 문제에서 걸릴 빈틈 목록**이 나와요. 연출가는 그 목록으로 한 판을 진행해요.

**알고리즘 한 판의 흐름**

```
읽기 → 첫 코드 쓰기(빈틈들이 들어간 코드) → 예제 실행 → 제출
  └ 틀림 → 반응 고르기(주사위) ─┬ 혼자 고치기      (fromOwnFix로 빈틈 하나가 풀릴 수 있음)
                               ├ 찍어서 다시 내기  (빈틈 그대로, 겉만 바뀜)
                               ├ 도움 칸 · 힌트 열기
                               ├ 튜터에게 묻기     → 답을 읽고 배움 판정
                               └ 포기
  → 맞음 또는 포기 → 나가기 → 풀이 한 장 · 리뷰가 만들어지길 기다림
```

- **반응 고르기**: 성격 값으로 확률을 정해요. 버티는 사람은 "혼자 고치기"를 여러 번 한 뒤에야 물어요. 행동마다 인내심이 1씩 줄고, 0이 되면 포기해요.
- **언제 끝나나는 성격이 정해요** (11/13 사용자 "질문과 제출 제한을 좀 더 널널하게"). 질문 · 제출 횟수를 낮게 묶지 않아요. 많이 묻는 사람은 15번도 묻고, 찍는 사람은 10번도 내요. 상한(질문 20 · 제출 15 · 행동 40)은 고장 나서 끝없이 도는 걸 막는 안전장치일 뿐이에요.
- **빈틈을 푸는 순서**: 아래층부터 드러나요. 문법 오류가 있으면 채점기가 그것부터 잡기 때문에, 5층 빈틈은 그 뒤에야 보여요. 실제 사람도 이 순서예요.
- **배움 판정** (설명을 들은 뒤)
  1. 튜터 답이 그 빈틈을 다뤘나 → 싼 AI 1번(luna, 출력은 예/아니오 + 한 줄)이 "이 답이 항목 X를 설명했나"를 봐요. 키워드로 뻔하면 코드가 먼저 판정해요.
  2. 다뤘으면 `perExplain` 주사위 → 성공하면 그 항목이 **앎**이 되고, 다음 코드에서 그 빈틈이 빠져요.
  3. 실패하면 "아직 모르겠어요"로 한 번 더 묻거나(설명두번), 그대로 찍어 내요.
- **아는데 하는 실수**(`typo`): 빈틈이 아닌데 틀리는 경우를 일부러 섞어요. 리뷰가 이걸 "모름"으로 잘못 잡는지 보는 미끼예요.
- **복붙형**: 튜터가 코드를 주면 그대로 붙여서 맞혀요. 정답지에는 "맞혔지만 배운 것 없음"으로 남아요. 리뷰가 이걸 "도움받고 넘어간 것 = 모르는 것"으로 잡아야 맞아요(리뷰 v16 기준).
- 같은 명세 + 같은 문제 + 같은 씨앗이면 **대본이 똑같아요.** 달라지는 건 AI가 쓴 말투와 코드 겉모습뿐이에요.

## 4. 입과 손 (AI, 작은 호출)

연출가가 대본을 한 줄 주면 AI는 그것만 써요. 고정된 내용(역할 · 문제 · 모범 풀이)은 앞에, 이번 대본은 뒤에 둬서 캐시를 타요.

| 호출 | 모델 | 받는 것 | 내는 것 |
|---|---|---|---|
| **코드 쓰기** | terra low | 모범 풀이 + "이 빈틈들만큼 틀리게: (항목, 증상)" + 직전 내 코드 | 코드 한 벌 (또는 바뀐 부분만) |
| **말 쓰기** | luna | 성격(말투) + 상황("3번 틀림, 시간 초과, 방문 표시를 모름") + 쓰면 안 되는 낱말 | 질문 한두 문장 |
| **배움 판정** | luna | 튜터 답 + 항목 설명 | 다뤘나(예/아니오) |

- 코드 쓰기를 "정답에서 빈틈만큼 망가뜨리기"로 한 이유: 모르는 사람이 쓴 코드를 처음부터 지어내게 하는 것보다 **통제가 되고, 검사할 수 있어서**예요.
- 말 쓰기는 틀려도 큰일이 없어요(뒤에 검사가 있음). 그래서 제일 싼 모델을 써요.

### 실습은 손이 더 필요해요: 작은 하네스

실습은 파일 여러 개를 고치고 명령을 돌려야 해서, 한 번 부르고 끝나는 호출로는 안 돼요.

- NPC의 손은 **도구 세 개만 가진 작은 에이전트 루프**예요: 파일 읽기 · 파일 고치기 · 명령 실행(작업 폴더 안에서만).
- 연출가가 한 걸음씩만 시켜요: "목표 2의 적용 과제를, 빈틈 `concept.race-condition`(모름) 상태로 해 봐. 최대 6걸음."
- 손이 한 일은 **VS Code 확장이 보내는 것과 같은 모양**으로 실습 서버에 알려요: 저장한 파일, 실행한 명령과 출력(`/api/bridge/state` · `/api/bridge/terminal`), 질문(`/api/bridge/ask`), 대화와 "해 봤어요"(`/api/runs/<id>/lesson/<n>/act`). 실습 서버는 사람인지 NPC인지 몰라요.
- 엔진은 실습 튜터가 쓰는 것과 같은 OpenCode를 창 없이 써요(새로 만들지 않음). 도구 권한은 코드가 걸러요.

## 5. 검사 (진짜 같게 만드는 장치)

1. **증상 검사**: 쓴 코드를 **진짜 채점기**(`submit`)로 돌려요. 대본이 "시간 초과"인데 맞아 버리면 그 코드는 버리고 한 번 다시 써요. 두 번 실패하면 그 빈틈은 "재현 못 함"으로 정답지에 적고 넘어가요.
2. **누수 검사 (코드)**: 모르는 문법 항목마다 "쓰면 안 되는 모양" 목록이 있어요(예: `sort-key`를 모르면 `key=`가 코드에 나오면 안 됨). 걸리면 다시 써요.
3. **누수 검사 (말)**: 모르는 개념의 이름을 말에 쓰면 안 돼요(BFS를 모르는데 "BFS로 풀었는데요"라고 하면 안 됨). 금지 낱말로 코드가 검사해요.
4. **다 배운 뒤 검사**: 빈틈이 다 풀린 NPC가 쓴 코드는 맞아야 해요. 안 맞으면 하네스 버그예요.
5. **진짜 사람과 맞춰 보기**: 사용자 본인 기록(2606: 말 34개의 층 분포 — 2층 7, 4층 7, 1층 4, 3층 3, 5층 3)과 "나 닮은 NPC"의 분포를 비교해요. 크게 다르면 연출가 확률을 고쳐요.

## 6. 정답지와 채점

연출가는 한 판 동안 `truth.jsonl`에 사실을 적어요.

```jsonc
{ "t": 3, "item": "pattern.bfs-distance", "layer": 5, "state": "잘못 앎", "size": "big",
  "symptom": "TLE", "shown": "제출 2 · 3", "resolvedBy": "tutor", "learned": true }
{ "t": 5, "item": "(실수)", "layer": 3, "state": "앎", "size": "small", "symptom": "WA", "resolvedBy": "self", "learned": null }
```

이걸 기준으로 제품 쪽 결과를 채점해요.

| 채점하는 것 | 어떻게 |
|---|---|
| **리뷰** | 정답지의 큰 빈틈이 리뷰 [핵심]에 있나(놓침), 리뷰가 없는 빈틈을 지어냈나(헛짚음), 실수를 "모름"으로 잡았나, 크기가 맞나 |
| **기억** | 몰랐던 것만 기억이 됐나 (11/8 실험의 정밀도 · 재현율을 실제 AI 흐름에서 다시) |
| **튜터** | 문법 빈틈에 문법부터 짚었나, 답을 그냥 줬나(복붙형이 몇 걸음에 정답 코드를 받았나) |
| **상황 재현 복습** | 뽑은 "막힌 이유"가 정답지와 맞나. 재현 상황을 NPC가 다시 풀 때 **배운 NPC는 통과, 안 배운 NPC는 또 걸리나** |

리뷰 글과 정답지를 맞추는 일은 AI 1번(terra low, 항목별 예/아니오)으로 해요. 숫자 집계는 코드가 해요.

## 7. 비용

AI는 ChatGPT 구독으로 불러서 돈은 안 나가요. 대신 **Plus 5시간 한도**를 사용자와 같이 써요. 아래는 추정이고, 첫 실행의 호출 기록으로 고쳐요.

**알고리즘: NPC 한 명 × 문제 하나** (보통 판: 질문 6번 · 제출 5번쯤 쓰는 경우)

| 쪽 | 호출 | 토큰 (추정) |
|---|---|---|
| NPC | 코드 쓰기 5 (terra low) | 약 1.5만 |
| NPC | 말 쓰기 6 + 배움 판정 6 (luna) | 약 1.8만 |
| 제품 (원래 드는 것) | 튜터 답 · 힌트 · 풀이 한 장 · 리뷰 | 약 4만~6만 |
| **합** | | **약 8만~9만 → API로 약 110~140원, Plus 5시간의 약 1.2%** |

- **많이 묻고 많이 내는 판**(질문 15 · 제출 10쯤): 약 18만~20만 토큰(약 2.5%). 상한을 넉넉히 둔 만큼, 비용은 판마다가 아니라 **묶음 토큰 상한**으로 지켜요.
- 문제 지식 지도: 문제마다 한 번 약 4천 토큰. NPC가 몇 명이든 한 번이에요.
- 실습: NPC 한 명 × 목표 하나에 약 12만~13만 토큰(약 1.7%). 손이 에이전트 루프라 알고리즘보다 커요.

**싸게 만드는 장치**

1. **연출이 코드**: 가장 비싼 "판단"에 AI를 안 써요. NPC 쪽 호출은 전부 짧은 출력이에요.
2. **모델 나눔**: 말 · 판정은 luna(뒤에 검사 있음), 코드만 terra low.
3. **상한**: 판마다 상한은 넉넉한 안전장치(질문 20 · 제출 15)이고, 실제 지킴이는 묶음의 `--max-tokens`예요. 넘으면 새 NPC를 시작하지 않고, 돌던 판은 "나가기"로 정리해요(기록은 남음).
4. **가짜 AI 모드**(`--dry`): AI 0번. 연출가 · 검사 · 정답지 · 드라이버가 끝까지 도는지만 봐요. 하네스를 고칠 때는 이걸로 해요.
5. **기록 다시 쓰기**(`--replay`): 한 번 만든 판(대화 · 제출 · 정답지)을 저장해 두고, 뒤 단계만 바꿔 다시 돌려요. 리뷰 지시문을 고쳐 다시 채점하면 리뷰 호출만 들어요(약 2만 토큰). **튜터까지 다시 돌리는 건 튜터를 바꿨을 때만** 해요.
6. **캐시**: 고정 지시문 · 문제 · 모범 풀이는 앞에, 이번 대본은 뒤에.
7. **기본 묶음은 작게**: NPC 3명 × 문제 하나 = 약 27만 토큰(약 3.6%). 실행 전에 예상 토큰을 출력하고, 실제 값과 나란히 기록해요.

## 8. 어디에, 어떻게 도나

- 폴더: `lab/npc/` (실험실, 제품 흐름 밖). 결과는 `lab/npc/out/`(깃에 안 올림).
- **사용자 데이터를 절대 안 건드려요.** NPC마다 자기 데이터 폴더(`lab/npc/out/data/<npc>/`)를 써요. 앱 서버(3000) · 실습 서버(4100)는 안 써요.
- 알고리즘: NPC 한 명 = 프로세스 하나. `STUDY_FORGE_DATA_DIR`를 자기 폴더로 두고 알고리즘 기능을 불러요(11/8 실험과 같은 방식). 아래 "정할 것 2" 참고.
- 실습: NPC마다 실습 서버를 따로 띄워요(`PC_DATA_DIR` · `PC_PORT`, 4110번대). 작업 폴더도 따로예요.
- B(알고리즘) · D(실습) 코드는 고치지 않고 부르기만 해요.

| 3 | 채점(리뷰 · 기억). 결과를 `협업/결과보고/`에 | 리뷰 맞추기 몇 번 |

## 어려운 곳 · 한계

- **NPC는 사람이 아니에요.** 연출가의 확률은 우리가 정한 것이라, NPC 결과로 "사람도 그럴 것"이라고 말할 수는 없어요. 쓸 수 있는 말은 "이런 빈틈을 가진 기록이 들어오면 리뷰가 그걸 잡는다/못 잡는다"까지예요.
- **망가뜨리기가 부자연스러울 수 있어요.** 정답에서 출발하니 코드 뼈대가 너무 반듯해요. 4층(잇기) 빈틈과 "엉뚱한 방향으로 한참 가는 사람"은 덜 진짜 같아요. → `approaches`의 틀린 접근으로 처음부터 쓰게 하는 길을 6층에 둬요.
- **배움 판정이 후해질 수 있어요.** 튜터가 스치듯 말한 것도 "설명했다"로 볼 수 있어요. → 판정 기준을 "그 항목의 이유나 쓰는 법을 한 문장 이상"으로 좁히고, 표본을 사람이 몇 개 확인해요.
- **실습의 증상 재현**: 동시성 버그는 매번 똑같이 안 나요. 검사는 "여러 번 돌려 한 번이라도 어긋남"으로 봐요.
- **날짜**: 금방잊음 · 복습 실험은 하루하루 지나가야 해요. 날짜를 가짜로 넣을 수 있는지는 기억 저장소 쪽을 확인해야 해요.

## 정할 것

1. **이 구조로 갈지**: 연출가(코드)가 정하고 AI는 쓰기만. (다른 길: AI 에이전트에게 사람 역할을 통째로 맡김 — 더 자연스럽지만 새고, 들쭉날쭉하고, 3~5배 비쌈)
2. **알고리즘을 부르는 방식**
   - (가) 기능을 바로 부르기: 서버 없이 가볍고 NPC마다 폴더가 깔끔. 대신 화면이 거치는 순서(묻기 → 기록 → 대화 장부)를 드라이버가 똑같이 따라 해야 함.
   - (나) 실험 서버(`run-lab.mjs`)를 NPC마다 띄워 HTTP로: 화면과 완전히 같은 길. 대신 무겁고 느림.
   - 권장: (가)로 시작, 한 판을 (나)로도 돌려 결과가 같은지 한 번 확인.
3. **첫 실험의 NPC 3명과 문제**: 권장은 초보(문법약함 + 바로묻기) · 버티는 중수(원리 잘못 앎 + 버티기) · 복붙형(방법못고름 + 복붙) × 11651.
4. **한 번에 쓸 사용량 상한**: 권장은 묶음마다 30만 토큰(Plus 5시간의 약 4%).
5. 실습(5단계)을 알고리즘 채점(3단계)을 본 뒤에 시작할지.
