## 1. 제품의 목적과 학습 철학

### 1.1 최종적으로 키우려는 능력

우리가 논의했던 두 가지 목표 중 첫 번째를 기본으로 정했어.

- AI가 작성한 코드의 구조와 작동 방식을 이해한다.
- 요구사항을 구현 가능한 작업으로 나눌 수 있다.
- 기술 선택의 이유와 장단점을 이해한다.
- 오류가 발생하면 원인을 추적할 수 있다.
- AI가 작성한 결과물이 올바르게 동작하는지 검증할 수 있다.
- AI에게 적절한 작업을 지시하고 결과를 평가할 수 있다.

반면 모든 코드를 AI 없이 처음부터 직접 작성하는 능력은 필수 완료 조건으로 삼지 않아.

그 능력에도 가치가 있지만, 개발 학습 전체를 그 기준에 맞추면 학습 시간과 강제성이 크게 늘어나기 때문이야.

### 1.2 학습의 기준

코드를 얼마나 많이 직접 타이핑했는가보다, 개발 과정을 얼마나 이해하고 통제할 수 있는가를 중시한다.

다만 코드 독해, 기초 문법, 직접 수정하는 경험은 여전히 중요해. 모든 구현을 AI에게 맡기고 설명만 읽는 방식이 항상 충분하다는 뜻은 아니야.

따라서 기본 정책은 다음과 같아.

| 원칙       | 결정 내용                         |
| -------- | ----------------------------- |
| 학습 주도권   | 에이전트가 다음 활동을 안내               |
| 사용자의 자율성 | 속도·깊이·구현 참여도 조절 가능            |
| 학습 방법    | 설명·작동 예제·실제 구현을 상황에 따라 선택     |
| 이해도 검증   | 원칙적으로 강제하지 않음                 |
| 기능 검증    | 실행과 테스트 등으로 객관적 확인            |
| 학습 기록    | 실제 경험과 확인된 근거를 구분             |
| 진행 방식    | 현재 목표에 집중하되 자유로운 질문과 경로 변경 허용 |

### 1.3 일반 코딩 에이전트와의 차이

일반 코딩 에이전트의 기본 동작은 다음에 가까워.

사용자 요청 → 코드 작성 → 실행·검증 → 완료 보고

Recaller 학습 에이전트는 달라.

사용자 목표 → 학습·개발 경로 제안 → 필요한 원리와 설계 이해 → 작은 기능 구현 → 코드 이해 → 실행·검증 → 학습 경험 기록 → 다음 기능

따라서 학습을 이끄는 기능이 제품의 중심이고, 코드 작성은 그 목표를 수행하는 수단이야.

## 2. 사용자 목표를 해석하고 학습 경로를 만드는 방법

사용자가 항상 구체적인 프로젝트를 가지고 시작하는 건 아니야.

네 가지 출발점을 모두 지원하는 방향으로 논의했어.

| 출발점       | 사용자 발화 예시        | 에이전트 역할          |
| --------- | ---------------- | ---------------- |
| 구체적인 프로젝트 | "마리오 게임을 만들고 싶어" | 개발 목표와 작업 단계 구성  |
| 막연한 프로젝트  | "백엔드 서비스 만들고 싶어" | 프로젝트 범위와 기능 구체화  |
| 배우고 싶은 기술 | "Redis를 배워보고 싶어" | 선수 지식과 적절한 실습 탐색 |
| 넓은 학습 목표  | "개발을 잘하고 싶어"     | 관심 분야와 학습 방향 구체화 |

### 2.1 학습 목표 구체화

사용자가 "Redis를 배우고 싶다"고 했을 때 곧바로 캐시 서버 프로젝트를 생성하는 것은 적절하지 않을 수 있어.

먼저 사용자가 무엇을 알고 싶은지 확인해야 해.

Redis가 무엇인지, 직접 실행해 보고 싶은지, 실제 서버에서 사용하고 싶은지에 따라 필요한 학습이 달라지니까.

단, 질문만 계속해서는 안 돼.

사용자 목표를 수행 가능한 첫 번째 경험으로 연결하는 데 필요한 만큼만 확인한다.

### 2.2 선수 지식 진단

사용자가 Redis를 공부하고 싶어 한다면, 해당 목표에 필요한 선수 지식을 확인해.

다만 모든 선수 지식을 전부 공부하도록 강제하지 않아.

예를 들어 Redis 캐시를 적용하려고 한다면 API 요청과 응답, 데이터 조회, 캐시의 역할을 이해하는 게 중요할 수 있어.

반면 Redis 명령어를 몇 개 직접 실행해 보는 데는 그 모든 지식이 필수는 아니야.

선수 지식은 두 종류로 다룬다.

- 필수 선수 지식: 지금 하려는 작업을 이해하거나 수행하는 데 필요한 개념
- 보조 선수 지식: 몰라도 진행할 수 있지만 이해에 도움이 되는 개념

확인은 기존 지식 이력과 짧은 대화를 활용하고, 나머지는 실제 구현 과정에서 파악하는 혼합 방식이야.

### 2.3 프로젝트 계획 수립

전체 목표는 큰 단계로 나누되, 모든 세부 작업을 시작부터 확정하지 않아.

예를 들어 간단한 할 일 관리 API라면 다음 정도의 목차를 제시할 수 있어.

예시: Todo API 개발 과정

1. Node.js HTTP 서버 실행
2. 요청 주소에 따라 다른 응답 반환
3. 할 일 목록을 JSON으로 반환
4. 할 일 추가·수정·삭제
5. 데이터베이스 연결 및 저장
6. 실제 동작 확인 및 오류 처리

전체 목차는 언제든 볼 수 있지만, 메인 학습창은 현재 진행 중인 단계에 집중한다.

계획은 변경 가능해야 해.

사용자가 다른 기능부터 구현하고 싶어 하거나, 예상하지 못한 선수 지식 부족이 발견되면 현재 목표와 의존 관계를 확인한 뒤 순서나 작업 크기를 조절해.

## 3. 학습 단계의 구성과 동적 분해

### 3.1 큰 단계는 개념이 아니라 구현 목표 중심

우리는 `HTTP → 콜백 → 라우팅 → JSON`처럼 개념 강의를 나열하는 방식보다, 실제 기능을 만드는 흐름을 기본으로 선택했어.

예를 들면 다음과 같아.

- HTTP 서버 실행
- URL에 따라 다른 응답 반환
- JSON 데이터 반환
- 데이터 저장

그 과정에서 HTTP, 콜백, 라우팅, JSON 등의 개념을 필요한 시점에 배워.

### 3.2 처음부터 과도하게 쪼개지 않는다

작업 크기를 정할 때 고려할 요소는 다음 세 가지야.

1. 사용자가 해당 기술과 관련된 지식을 얼마나 갖추고 있는가?
2. 이번 작업에서 새롭게 등장하는 핵심 개념이 얼마나 많은가?
3. 해당 작업을 독립적으로 실행하거나 검증할 수 있는가?

기본적으로 적당한 크기로 계획하고, 사용자가 어려워하면 더 작게 나눠.

처음부터 모든 함수를 독립된 학습 단계로 만들지 않아.

### 3.3 임시 학습 단계

아까 시뮬레이션에서는 HTTP 서버 코드를 이해하는 과정에서 콜백 함수를 몰라 진행이 막혔어.

그때 필요한 동작은 다음과 같아.

원래 목표: HTTP 서버 이해하고 실행하기

발견된 막힘

`createServer(handleRequest)`가 이해되지 않음

임시 학습: 콜백 함수

함수 전달과 호출 시점 이해

원래 목표로 복귀

HTTP 요청에 따라 콜백이 실행되는 과정 확인

임시 학습 단계는 다음 상황에서 활용해.

- 짧은 설명으로 해결되지 않는 경우
- 현재 구현을 진행하는 데 중요한 선수 지식이 부족한 경우
- 별도의 작동 예제나 실습이 필요한 경우

반면 단순한 API 이름이나 문법 질문이라면 별도 단계를 생성하지 않고 현재 활동에서 답해.

이때 임시 학습 단계가 끝났다는 사실과 해당 개념을 완전히 습득했다는 판단은 구분한다.

## 4. 학습 진행 엔진

이 부분이 시스템의 핵심이야.

현재 학습 목표, 사용자 질문, 코드 상태, 기존 지식 이력을 바탕으로 다음 행동을 결정하는 엔진이 필요해.

### 4.1 기본 행동 유형

| 행동          | 목적                 |
| ----------- | ------------------ |
| `EXPLAIN`   | 코드·개념·작동 원리 설명     |
| `DEMO`      | 작은 작동 예제 제시 또는 실행  |
| `GUIDE`     | 사용자가 직접 할 작업 안내    |
| `DIAGNOSE`  | 이해 부족이나 오류 원인 분석   |
| `VERIFY`    | 코드 동작·결과·선택적 이해 확인 |
| `NAVIGATE`  | 목표 변경·분해·복귀·단계 진행  |
| `SUMMARIZE` | 학습 정리 및 기록         |

이 행동들은 고정된 학습 순서가 아니야.

에이전트가 상황에 따라 선택하는 내부적인 행동 유형이야.

예를 들어 사용자가 "콜백이 뭔데?"라고 물었다면 설명부터 시작할 수 있어.

설명을 듣고도 어려워하면 작은 예제로 바꾸고, 사용자가 이해했다면 원래 코드로 돌아오겠지.

### 4.2 행동 결정의 기본 우선순위

1. 사용자의 명시적인 요청과 의사를 존중한다.
2. 현재 학습을 막고 있는 문제를 우선 해결한다.
3. 가능한 경우 현재 프로젝트의 실제 코드와 연결한다.
4. 이미 이해한 내용은 불필요하게 반복하지 않는다.
5. 너무 긴 설명이나 과도한 확인 질문을 피한다.
6. 임시 설명이 끝나면 원래 구현 목표로 돌아간다.
7. 사용자의 수준과 현재 작업의 복잡도에 따라 설명과 구현의 비중을 조절한다.

여기서 중요한 점은 AI가 학습을 주도하지만 모든 학습 활동을 강제하지는 않는다는 것이야.

사용자가 질문하면 방향을 바꾸고, 다음으로 넘어가자고 하면 가능한 범위에서 넘어가며, 직접 해보고 싶다면 구현을 맡길 수 있어.

### 4.3 학습 방법 선택

우리가 시뮬레이션하면서 구분한 네 가지 상황을 반영해야 해.

| 상황             | 기본 접근             |
| -------------- | ----------------- |
| 처음 보는 함수·라이브러리 | 작은 작동 예제부터        |
| 처음 접하는 원리      | 직관적 설명과 실제 코드 연결  |
| 복잡한 기능 구현      | 전체 구조와 설계 판단부터    |
| 실제 오류          | 발생 위치·원인·수정 과정 분석 |

예를 들어 Pygame으로 창을 띄우는 방법을 모르는 사용자에게는 작동하는 최소 예제가 효과적일 수 있어.

반면 로그인 시스템을 처음 만드는 사용자에게는 완성 코드 수백 줄보다, 요청·검증·세션·인증의 전체 구조를 먼저 이해시키는 방식이 적절하겠지.

## 5. OpenCode와 학습 에이전트의 역할 분리

우리는 두 역할을 논리적으로 분리하는 방향을 선택했어.

### 5.1 학습 에이전트

학습 에이전트는 전체 과정을 이끄는 역할이야.

주요 책임은 다음과 같아.

- 사용자 목표와 선수 지식 파악
- 개발 및 학습 계획 수립
- 현재 구현 범위 결정
- 기술 선택과 설계 이유 설명
- OpenCode에 작업 지시
- 구현 결과를 학습 가능한 형태로 설명
- 학습 이력과 현재 상태 유지
- 사용자의 질문에 따른 학습 경로 조정

### 5.2 OpenCode 기반 코딩 실행 계층

OpenCode는 코드 작업을 담당해.

- 프로젝트 파일 탐색과 분석
- 코드 작성 및 수정
- 필요한 라이브러리·환경 구성
- 터미널 명령 실행
- 오류 로그 확인
- 테스트 실행
- 구현 결과와 변경 사항 반환

이 역할 분리는 LLM 두 개를 반드시 운영해야 한다는 뜻은 아니야.

하나의 LLM이 학습 진행을 맡고 코딩 도구를 호출하는 방식도 가능하고, 별도의 코딩 작업 에이전트에 위임하는 방식도 가능해.

이는 현재 OpenCode 통합 상태를 확인한 뒤 결정해야 하는 구현 세부 사항이야.

### 5.3 작업 범위는 학습 에이전트가 통제

예를 들어 현재 목표가 로그인 요청을 처리하는 API 구현이라면, 코딩 실행 계층에 다음과 같이 작업을 맡길 수 있어.

코딩 작업 지시 예시

목표: `POST /login` 요청을 받아 입력 데이터를 검증하는 기능 구현

범위: 요청 처리와 필수 입력값 확인

제외: 실제 비밀번호 검증, 세션 발급, 인증 미들웨어는 다음 단계에서 다룸

검증: 유효한 요청과 잘못된 요청에 대한 응답 확인

반환: 수정 파일, 주요 코드, 실행 결과, 설명할 핵심 부분

이렇게 하면 코딩 에이전트가 기술적으로 필요한 판단을 하면서도, 학습하지 않은 기능까지 한꺼번에 구현하는 일을 줄일 수 있어.

다만 보안상 중요한 기능은 잘못된 부분 구현이 완성된 기능으로 오인되지 않도록 구분해야 해. 위 로그인 예시도 실제 인증이 아니라 입력 처리 학습 단계로만 취급해야 하지.

### 5.4 코드 변경과 실행에 대한 통제

이 부분은 아직 세부 정책을 확정하지 않았지만, 다음 구분이 필요해.

- 코드 탐색·읽기: 학습 맥락 확인을 위해 자율 수행
- 작은 코드 수정: 현재 승인된 작업 범위 안에서 수행
- 파일 삭제·대규모 변경·외부 서비스 작업: 별도 권한 확인
- 테스트 실행: 가능한 경우 자동 실행
- 변경된 코드: 사용자에게 주요 변경 내용 제공

학습 에이전트가 작업 범위를 지정했다고 해서 모든 파일 수정에 무제한 권한을 부여하는 구조는 피해야 해.

## 6. 코드를 실제로 가르치는 방법

우리가 합의한 핵심은 전체 구조를 이해한 뒤 핵심 로직으로 들어간다는 거야.

### 6.1 코드 설명의 순서

예를 들어 OpenCode가 100줄짜리 기능을 구현했다고 하자.

학습 에이전트는 처음부터 100줄을 모두 설명하지 않아.

1. 전체 구조

   어떤 파일이 생겼고, 파일마다 어떤 책임이 있는지 설명
2. 실행 흐름

   사용자의 요청부터 결과가 반환될 때까지 어떤 함수와 파일을 거치는지 보여줌
3. 핵심 로직

   현재 기능을 이해하는 데 중요한 코드 부분을 집중해서 설명
4. 실제 동작

   실행 결과를 보여주고, 입력을 바꾸거나 오류 상황을 확인
5. 활용과 확장

   사용자가 원하는 경우 직접 수정하거나 다음 기능에서 활용

여기서 코드 설명의 기본 단위는 파일 전체나 코드 줄 수가 아니라 사용자가 이해할 수 있는 실행 흐름과 책임 단위야.

### 6.2 이해 수준에 따른 설명 조절

예를 들어 HTTP 서버 시뮬레이션에서는 처음에 `http.createServer()` 자체를 이해하기 어려웠어.

그때 학습 에이전트는 콜백 함수 개념으로 잠시 이동했지.

반면 사용자가 마지막에 "URL에 따라 `if`나 `switch`로 분기하면 되겠네"라고 했을 때는 조건문을 처음부터 설명할 필요가 없었어.

따라서 다음처럼 조절해야 해.

- 처음 접한 개념: 기초부터 설명
- 이미 경험한 개념: 현재 코드에서 어떤 역할인지 연결
- 사용자가 스스로 방법을 제시한 경우: 과도한 설명을 줄이고 구현으로 연결
- 이해하지 못한 경우: 설명을 반복하는 대신 작은 예제나 다른 관점 제공

이때 학습자의 한 번의 답변만으로 이해도를 확정하지 않아야 해.

## 7. 오류 발생 시 학습과 디버깅

우리는 오류를 무조건 자동 수정하는 방식보다, 왜 오류가 발생했는지 이해하도록 돕는 방식을 선택했어.

### 7.1 오류 대응 흐름

실행 실패 또는 오류 발견

실제 로그와 코드 확인

오류 발생 원인과 실행 흐름 설명

사용자가 수정하거나 AI가 수정

재실행 · 검증 · 필요한 학습 이력 기록

### 7.2 오류별 대응 차이

| 오류 종류     | 학습 에이전트의 행동           |
| --------- | --------------------- |
| 단순 오타     | 짧게 설명하고 수정            |
| 낯선 문법     | 작은 예제로 설명             |
| 런타임 오류    | 값과 호출 흐름을 추적          |
| 설계 문제     | 구조와 선택 이유 재검토         |
| 복잡한 환경 문제 | 로그·설정·의존성 확인 및 단계적 해결 |

사용자가 직접 고치고 싶다면 직접 수정하도록 안내하고, AI에게 맡기고 싶다면 코딩 에이전트가 수행해.

오류 수정 방법의 선택은 유연하게 두되, 학습할 가치가 있는 원인은 설명하는 것이 기본이야.

### 7.3 해결하지 못한 오류

아직 구체적인 정책을 정하지 않았지만, 오류가 반복되어도 무한히 같은 방식으로 재시도해서는 안 돼.

예를 들어 다음과 같은 전환이 필요해.

- 이전과 다른 원인 가설 세우기
- 더 작은 재현 예제로 분리
- 변경 사항을 되돌리고 정상 동작 지점 확인
- 사용자에게 선택지를 설명하거나 도움 요청

실제 구현에서는 재시도 횟수, 코드 변경 범위, 실행 중단 조건을 추가로 설계해야 해.

## 8. 학습 상태와 기능 완료를 분리

이건 이번 논의에서 중요한 결정 중 하나야.

코드가 동작한다는 사실과 사용자가 코드를 이해했다는 사실은 다르다.

이를 분리해서 관리해야 해.

| 상태       | 무엇을 의미하는가       | 판단 근거      |
| -------- | --------------- | ---------- |
| 개발 완료    | 기능이 요구사항대로 동작   | 테스트·실행 결과  |
| 학습 활동 완료 | 현재 설명이나 활동이 종료  | 대화·사용자 의사  |
| 지식 경험    | 특정 개념을 접하고 사용   | 질문·코드 작업 등 |
| 이해 자기평가  | 사용자가 이해했다고 보고   | 사용자 응답     |
| 적용 근거    | 사용자가 실제로 개념을 활용 | 관찰된 작업 결과  |

### 8.1 이해도 시험은 기본적으로 강제하지 않는다

사용자가 "이해했어, 다음으로 가자"라고 하면 원칙적으로 그 의사를 존중해.

매 단계마다 퀴즈를 내고 통과해야만 다음으로 넘어가도록 만들지 않아.

선택적으로 이해 확인을 요청하거나, 이후 실제 작업에서 관련 개념을 다시 활용하게 할 수는 있어.

### 8.2 기능 완료 판정은 자동화한다

코드가 정상적으로 작동하는지는 가능한 경우 실행·테스트로 확인해.

다만 테스트가 통과했다고 모든 요구사항이 완벽하게 만족됐다고 볼 수는 없어.

따라서 검증 결과에는 테스트 범위와 확인되지 않은 부분도 남길 수 있어야 해.

### 8.3 학습 이해도가 부족해도 다음으로 진행 가능

기능이 완성됐고 사용자가 다음 단계로 넘어가고 싶다면 진행을 허용해.

이해가 부족했던 개념은 지식 시스템과 학습 이력에 남겨 이후에 다시 다룰 수 있게 해.

## 9. Recaller 지식 시스템과 연동

현재 Recaller에는 PDF와 웹 글에서 지식을 추출하고, 알고리즘 문제 풀이를 지식으로 연결하는 구조가 있어.

코딩 학습 에이전트도 같은 지식 체계를 활용해야 해.

다만 코드에 등장한 개념을 무조건 지식 카드로 생성하는 방식은 채택하지 않았어.

### 9.1 지식 후보가 되는 상황

사용자가 어떤 개념과 의미 있는 학습 상호작용을 했을 때 후보로 기록하는 방향이야.

예를 들어:

| 학습 사건            | 처리            |
| ---------------- | ------------- |
| 라이브러리 함수가 코드에 등장 | 자동 지식 생성하지 않음 |
| 사용자가 함수 역할을 질문   | 지식 후보         |
| 같은 개념에서 반복적으로 막힘 | 막힘 이력 추가      |
| 직접 코드를 수정하며 사용   | 적용 경험 추가      |
| 중요한 개념을 깊게 설명받음  | 지식 후보         |
| 이미 저장된 개념을 다시 학습 | 기존 지식에 이력 연결  |

사용자가 질문하지 않았더라도 실제로 중요하게 학습한 개념은 후보가 될 수 있어.

### 9.2 학습 사건과 지식 카드를 구분

이 부분은 C형 혼합 방식으로 결정했어.

학습 중 상호작용

질문 · 막힘 · 설명 · 코드 수정 · 실행

학습 사건 저장

발생 시점에 가볍게 기록

단계 또는 세션 종료 시 정리

중요도 판정 · 중복 검사 · 기존 지식 연결

Recaller 지식 카드와 학습 이력 갱신

학습 사건은 진행 중에 저장해서 갑자기 종료되어도 정보가 사라지지 않도록 해야 해.

반면 지식 카드를 생성하거나 병합하는 작업은 나중에 정리할 수 있어.

### 9.3 기존 지식 상태와의 관계

기존 Recaller의 `만남·몰랐음·앎·졸업` 상태 체계를 바로 폐기하거나 변경할 필요는 없어.

대신 코딩 학습에서 발생하는 경험을 별도 이력으로 연결하는 편이 좋아.

예를 들면 `콜백 함수`라는 지식에 다음과 같은 기록이 연결될 수 있어.

## 콜백 함수

기존 지식 연결

출처: Todo API 프로젝트 · server.js

- HTTP 서버 코드에서 처음 접함
- 함수 전달과 실행 시점을 여러 번 질문함
- 작은 `run(callback)` 예제로 설명받음
- 사용자가 이해했다고 표현함
- 독립적으로 활용했는지는 아직 확인되지 않음

이런 기록을 통해 '앎'이라는 상태 하나만으로는 표현하기 어려운 학습 경험을 보존할 수 있어.

다만 코드 수정의 주체가 AI였다면 사용자가 직접 작성한 경험으로 기록하면 안 돼.

## 10. 기존 지식 자동 검색

이 부분은 비용이 낮다면 자동 검색을 기본으로 사용하자는 쪽으로 의견을 모았어.

### 10.1 검색 방식

기존 Recaller의 임베딩 검색 구조를 활용해 다음과 같이 처리하는 방향이야.

1. 현재 목표 또는 질문을 기반으로 검색 질의 구성
2. 이름·별칭 검색
3. 임베딩 유사도 검색
4. 중복 후보 통합
5. 현재 학습과의 관련성 평가
6. 필요한 지식과 이력만 LLM 맥락에 제공

### 10.2 검색 시점

기본적으로 다음 상황에서 자동 검색할 수 있어.

- 새로운 학습 목표 설정
- 개발 단계 변경
- 사용자가 특정 개념 질문
- 중요한 선수 지식이 필요한 상황
- 과거 경험을 재활용하면 도움이 되는 상황

반면 파일이 수정될 때마다 모든 지식을 검색하는 방식은 필요하지 않을 수 있어.

### 10.3 규모 확장

지식 카드가 수만 개로 늘어나더라도 매번 모든 지식을 LLM에 전달할 필요는 없어.

로컬 임베딩 비교나 검색 인덱스를 사용해 후보를 좁히면 돼.

다만 검색 자체가 저렴해도 검색 결과를 LLM에 계속 넣으면 입력 토큰 비용과 맥락 잡음이 발생해.

따라서 검색과 LLM 주입은 별개로 관리해야 해.

### 10.4 남은 검증 과제

- 관련 지식 검색 정확도
- 지식 수 증가에 따른 검색 지연
- 검색 결과가 실제 설명에 도움이 되는 비율
- 유사하지만 무관한 지식이 잘못 연결되는 문제
- 기존 카드와 새로운 학습 사건의 중복 처리

이건 초기부터 정교한 모델을 만드는 것보다 실제 데이터로 측정하며 조정하는 게 적절해.

## 11. 학습 세션과 맥락 관리

에이전트는 사용자가 작업하는 동안 현재 상황을 지속적으로 알고 있어야 해.

하지만 이것이 매 순간 LLM을 호출해야 한다는 뜻은 아니야.

### 11.1 관리할 맥락은 네 종류

| 맥락     | 주요 정보                      |
| ------ | -------------------------- |
| 프로젝트   | 파일 구조, 기술 스택, 실행 환경, 변경 사항 |
| 개발 진행  | 현재 기능, 완료 조건, 구현 결과, 다음 작업 |
| 학습 진행  | 현재 활동, 막힌 개념, 임시 학습, 복귀 위치 |
| 학습자 지식 | 기존 지식 카드, 질문 이력, 적용 경험     |

이 정보들을 전부 매번 LLM에 넣지 않고, 현재 작업에 필요한 부분을 선별해 제공해야 해.

### 11.2 상태 관리 데이터 구조 초안

아래는 지금까지 논의를 구현 형태로 옮긴 제안 데이터 구조야. 확정된 스키마는 아니야.

```

type LearningSession = {
  id: string;
  projectId: string;

  // 전체 학습 목표
  goal: string;

  // 현재 개발 단계
  currentStepId: string;

  // 지금 진행하는 활동
  currentActivity: {
    type:
      | "explain"
      | "demo"
      | "guide"
      | "diagnose"
      | "verify"
      | "navigate"
      | "summarize";

    target: string;
    status: "active" | "paused" | "done";
  };

  // 임시 선수 지식 학습 등
  detourStack: Array<{
    topic: string;
    reason: string;
    returnStepId: string;
    returnContext: string;
  }>;

  // 이번 세션에서 관찰한 학습 사건
  recentEventIds: string[];

  // 진행 상태
  status: "active" | "paused" | "completed";
};

```

`detourStack`을 둔 이유는 임시 학습이 한 번만 발생한다는 보장이 없기 때문이야.

예를 들어 HTTP 서버를 공부하다 콜백으로 이동했는데, 콜백을 이해하려다 함수 자체를 잘 모른다는 사실이 드러날 수도 있어.

이런 경우에도 원래 돌아갈 위치를 잃지 않아야 해.

다만 실제 구현에서는 중첩을 무제한 허용하지 말고, 지나치게 깊어지면 학습 목표를 재조정하는 정책이 필요해.

### 11.3 개발 단계 구조

```

type DevelopmentStep = {
  id: string;
  projectId: string;

  title: string;
  goal: string;

  // 이번 단계에서 얻을 결과물
  deliverables: string[];

  // 기능 검증 기준
  acceptanceCriteria: string[];

  // 예상되는 핵심 개념
  relatedKnowledgeIds: string[];

  // 작업 사이의 의존성
  dependencies: string[];

  status:
    | "planned"
    | "in_progress"
    | "blocked"
    | "completed"
    | "skipped";
};

```

여기서 `relatedKnowledgeIds`는 이미 존재하는 지식만 연결할 수 있어. 아직 카드가 없는 개념은 별도 후보로 관리해야 해.

또한 단계가 완료됐다는 사실은 `acceptanceCriteria`가 실제로 확인됐다는 근거와 함께 보관하는 편이 좋아.

### 11.4 학습 사건 구조

```

type LearningEvent = {
  id: string;
  sessionId: string;
  stepId: string;

  timestamp: string;

  type:
    | "question"
    | "confusion"
    | "explanation"
    | "demo"
    | "code_edit"
    | "execution"
    | "self_report"
    | "application";

  // 어떤 개념과 관계된 사건인가
  knowledgeId?: string;
  conceptCandidate?: string;

  // 사용자가 실제로 한 것과
  // AI가 수행한 것을 구분
  actor: "user" | "agent" | "system";

  description: string;

  // 대화나 실제 코드 등 근거 연결
  evidenceRefs: string[];
};

```

이렇게 하면 학습자의 능력을 하나의 숫자로 임의 평가하지 않고도, 실제로 어떤 경험을 했는지 추적할 수 있어.

기존 Recaller의 이벤트 로그와 통합할지, 코딩 학습 전용 이벤트를 분리할지는 현재 저장소 구조를 확인해 결정해야 해.

## 12. 실제 에이전트 동작 흐름

지금까지의 합의안을 하나의 실행 흐름으로 결합하면 다음과 같아.

사용자 목표 입력

프로젝트 제작 또는 기술 학습

목표 해석 · 선수 지식 확인

전체 개발 경로 구성

목차 제시, 현재 단계 선택

현재 구현 목표와 원리 이해

OpenCode를 통한 기능 구현

코드 구조 · 실행 흐름 · 핵심 로직 설명

실행 · 검증 · 오류 해결

학습 사건 저장 · 다음 단계 진행

실제 실행에서는 이 순서를 기계적으로 강제하지 않아.

예를 들어 사용자가 설명 도중 질문하면 설명으로 돌아가고, 오류가 발생하면 디버깅을 진행하며, 사용자가 이미 아는 내용이라면 건너뛸 수 있어.

이 흐름은 고정된 강의 절차가 아니라 학습 에이전트가 유지해야 하는 기본적인 진행 방향이야.

## 13. 학습 종료와 다음 세션 재개

사용자가 "오늘은 여기까지"라고 하면, 다음 항목을 보존해야 해.

- 프로젝트의 현재 구현 상태
- 완료한 개발 단계와 검증 결과
- 진행하다 중단한 작업
- 사용자가 질문하거나 어려워했던 개념
- 관련 학습 사건
- 다음에 이어갈 위치

지식 정리와 중복 확인은 별도 작업으로 수행할 수 있어.

다만 종료 처리가 실패하거나 중단되더라도, 진행 중에 저장된 사건과 개발 상태를 통해 복구할 수 있도록 해야 해.

다음 학습을 시작하면 에이전트는 이전 상태를 읽고 간단히 이어서 안내할 수 있어.

> 지난번에는 HTTP 서버를 실행하고 `/hello` 요청을 처리했어. 콜백과 `req`, `res`도 살펴봤지. 오늘은 URL에 따라 다른 응답을 보내는 기능을 만들어 보자.

중요한 건 이미 배운 내용을 처음부터 다시 가르치는 게 아니라, 이전 학습 경험을 현재 작업으로 자연스럽게 연결하는 것이야.

# 14. 두 차례 시뮬레이션의 결과

우리가 실제로 두 가지 시뮬레이션을 진행했어.

## 시뮬레이션 A: 트랜스포머 이해

사용자는 트랜스포머의 작동 원리를 배우고 싶어 했어.

진행 내용은 토큰, 임베딩, 위치 정보, Q·K·V, Self-Attention까지였지.

### 발견된 문제

- 개념 설명이 길어지면서 강의처럼 변함
- 자명한 확인 질문이 반복됨
- 실제 코드 실행까지 도달하기 어려웠음
- 한 세션의 종료 지점이 불명확했음
- 사용자가 학습 피로를 호소함

여기서 배운 건 학습 에이전트가 주도하는 것과 끊임없이 가르치는 것은 다르다는 점이야.

사용자가 현재 배우는 내용이 실제 결과물과 어떻게 연결되는지 느낄 수 있어야 해.

## 시뮬레이션 B: HTTP 서버 만들기

이번에는 실제 개발을 배우는 상황으로 진행했어.

### 관찰된 변화

1. 변수·반복문은 알지만 서버 개발 경험은 부족하다고 보고
2. `createServer`, `require`, `req`, `res`, 콜백이 낯설다고 질문
3. 작은 함수 예제를 통해 콜백 구조를 설명
4. HTTP 요청과 응답의 역할을 점차 이해
5. 사용자가 URL별 분기를 `if`나 `switch`로 처리하겠다고 스스로 제안

이 사례는 중요한 근거를 제공했어.

사용자가 처음에는 코드 전체를 몰라도, 필요한 개념을 이해하고 나면 자신이 이미 가진 지식을 활용해 다음 구현 방법을 제안할 수 있다.

다만 코드를 직접 작성하고 테스트하는 단계까지 시뮬레이션하지는 못했어.

따라서 이 사례는 학습 대화와 선수 지식 보충의 타당성을 보여준 것이지, 전체 프로젝트 학습 방식의 효과가 검증됐다는 뜻은 아니야.

# 16. Claude에게 실제 구현을 맡길 때의 추천 순서

이제부터는 방향을 계속 논의하는 것보다 기존 코드베이스를 확인하고 설계안을 실제 구조에 대응시키는 과정이 필요해.

다만 바로 전체 시스템을 구현하라고 지시하는 건 권장하지 않아.

나는 다음 순서가 적절하다고 생각해.

1\. 기존 구현 조사

현재 Recaller의 지식 모델, 학습 기록, OpenCode 연동, VS Code 학습창, 프로젝트 코스 실험 코드를 조사한다.

목표: 이미 있는 기능과 새로 만들 기능을 구분

2\. 학습 진행 엔진 설계

학습 세션, 개발 단계, 임시 학습, 학습 사건을 정의하고 행동 결정 흐름을 구체화한다.

목표: 대화가 길어져도 현재 학습 목표를 유지

3\. OpenCode 통합

학습 에이전트가 작업 범위를 지정하고, 코드 실행 계층이 수정·실행·검증 결과를 돌려주도록 연결한다.

목표: 실제 개발 작업을 학습 과정과 연계

4\. Recaller 지식 연동

사건 저장, 관련 지식 검색, 후보 추출, 중복 병합, 학습 이력 연결을 구현한다.

목표: 학습 경험이 프로젝트를 넘어 축적되도록 함

5\. VS Code 학습 경험 완성

현재 목표, 단계 목차, 코드 위치, 실행 결과, 질문·설명, 진행 상태를 연결한다.

목표: 자연스럽게 따라갈 수 있는 학습창

6\. 실제 학습 시나리오 평가

초보자의 HTTP 서버 만들기부터 시작해 목표 탐색, 구현, 오류, 임시 학습, 재개까지 검증한다.

목표: 기능 작동뿐 아니라 학습 진행 품질 평가

여기서 1\~3번은 기반을 만들고, 4\~6번은 이를 기존 Recaller의 학습 체계에 통합하는 작업이야.

구현 범위를 단순한 데모로 축소하라는 뜻은 아니야. 최종적으로는 일반적인 개발 프로젝트에서도 활용 가능한 구조를 지향하되, 실제 동작을 확인할 수 있는 순서로 구축하자는 거지.

## 17. 이번 설계에서 가장 중요한 세 가지

첫째, 학습의 중심은 개념 강의가 아니라 실제 구현 경험이다.

개발하면서 모르는 개념을 만나고, 그것을 이해한 뒤 다시 실제 코드로 돌아오는 구조가 핵심이야.

둘째, 사용자 이해도를 억지로 판정하지 않는다.

확실하게 관찰된 경험만 기록하고, 사용자가 원하는 깊이로 학습하게 한다. 학습 에이전트는 시험 감독보다 개발을 이끄는 튜터에 가까워야 해.

셋째, 상태 관리와 LLM 판단을 분리한다.

현재 목표, 코드 상태, 학습 이력, 복귀 위치는 시스템이 명시적으로 관리하고, LLM은 이를 바탕으로 설명·구현·검증·경로 변경을 결정하도록 한다.

이렇게 해야 학습이 길어져도 일관성을 유지하고, LLM이 모든 과거 대화를 매번 기억해야 하는 구조를 피할 수 있어.

## 최종 평가

현재 설계안은 Claude에게 프로젝트 구조를 조사시키고, 상세 기술 설계를 시작하도록 지시하기에는 충분한 수준이야.

하지만 이것만으로 전체 구현을 맡기기에는 아직 중요한 공백이 있어. 특히 학습 엔진의 실제 판단 로직, OpenCode 실행 인터페이스, 지식 카드의 데이터 계약, 예외 상황과 평가 기준은 더 구체화해야 해.

내가 추천하는 다음 행동은 이 설계안을 기준 문서로 고정하고, Claude에게 현재 저장소에서 재사용할 수 있는 기능과 필요한 신규 모듈을 분석하게 하는 것이야.

그 분석 결과를 바탕으로 실제 아키텍처와 인터페이스를 확정하면, 추상적인 구상에서 구현 가능한 명세로 넘어갈 수 있어.
