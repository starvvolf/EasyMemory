## 2. Whole-Document-Core 범위 선정 평가

### 2.1 핵심 범위 coverage

WholeDocumentCorePlan은 Deadlock gold/reference의 상위 필수 범위를 모두 포착했다.

- 데드락 정의와 네 필요조건
- 자원 할당 그래프의 노드·간선과 사이클 판정
- 예방·회피·탐지 및 복구의 차이
- 필요조건별 예방 정책
- 안전·불안전 상태와 요청 승인 판단
- 클레임 간선 전이와 다중 인스턴스 경계
- 탐지 후 프로세스 종료와 자원 선점 복구

Prepare 결과도 이 범위를 `LU-01~22`에 실제로 포함했다. 특히 다음 중대한 의미를 정확히 보존했다.

- 네 필요조건이 동시에 성립해야 데드락이 발생할 수 있음
- 요청 간선과 할당 간선의 방향
- 사이클이 없으면 데드락이 아님
- 단일 인스턴스와 다중 인스턴스에서 사이클의 의미가 다름
- 불안전 상태가 곧 현재 데드락은 아님
- 예방·회피와 탐지 및 복구의 개입 시점 차이

WholeDocumentCorePlan 또는 Prepare에서 gold의 critical failure에 해당하는 명백한 사실 오류는 발견되지 않았다.

### 2.2 낮은 가치 내용과 예시 처리

WholeDocumentCorePlan은 다음 내용을 의도적으로 핵심 단위에서 제외했다.

- 1쪽 장 제목과 2쪽 학습 목표 목록
- 14쪽 반복 요약
- 3쪽 세마포어 코드 순서의 세부 문장
- 7쪽 개별 그래프의 고유 노드·간선 배치
- 12쪽 특정 `P1`, `P2`, `R1`, `R2` 배치
- 자료에 없는 Banker 알고리즘의 상세 계산 절차

이는 gold/reference의 `metadata`, `redundant_summary`, `example_specific_detail` 제외 기준과 일치한다. 세마포어 예시와 개별 그래프는 일반 원리를 발견하거나 적용하는 보조 근거로만 사용했고, 고유 기호 자체를 암기 대상으로 만들지 않았다.

### 2.3 영역별 비중

배정은 `5·4·5·5·3`으로 균등하지 않다. 개념·조건, 예방, 회피에 상대적으로 더 많은 단위를 두고 탐지·복구를 3개로 묶은 것은 자료 분량과 gold의 의미 범위에 대체로 부합한다.

과거 문제였던 “PDF의 모든 내용을 비슷한 중요도로 취급하고 거의 모두 카드화”하는 경향은 **WholeDocumentCorePlan과 Prepare 단계에서는 뚜렷하게 나타나지 않았다.** 메타데이터, 반복 요약, 사례의 고유 배치가 제거됐고, 상세가 없는 Banker 알고리즘을 확장하지 않았다.

다만 이 판단은 한 개의 구조가 명확한 강의자료에 대한 한 번의 run에 한정된다.

### 2.4 집중 영역 선택 필요성에 대한 현재 근거

이번 run에서는 사용자가 한 영역을 강제로 고르지 않아도 AI가 전체 자료의 핵심 범위를 충분히 선별했다. 따라서 Deadlock 사례만 놓고 보면 강제 집중 영역 선택은 핵심 범위 품질을 유지하기 위한 필수 조건으로 보이지 않는다.

그러나 다음은 아직 검증되지 않았다.

- 분량이 훨씬 큰 자료
- 여러 학습 목표가 충돌하는 혼합 자료
- 시험 범위와 비범위가 문서에 명시되지 않은 자료
- 사용자가 특정 목적을 가져 전체 핵심과 다른 범위를 원하는 경우

현재 증거는 집중 영역 선택을 제거해야 한다는 결론이 아니라, **강제 단계가 아닌 사용자 override로 완화할 가능성을 검토할 근거**다.

## 3. 단일 Recall Design 분석

선택된 recall structure는 모든 LearningUnit을 “조건·상황·비교 정보 → 결론과 근거” 형태로 만들도록 했다. 이 구조는 Deadlock 자료의 판정형 내용에는 강하게 맞았지만, 정의·표기·절차·복구처럼 성격이 다른 단위에는 적합도가 달랐다.

### 3.1 잘 맞은 사례

- `LU-02~05`: 상황에서 네 필요조건의 성립 여부를 판정
- `LU-09`: 사이클과 인스턴스 수에서 데드락 여부를 판정
- `LU-12~14`: 예방 정책에서 차단하는 필요조건을 판정
- `LU-15~16`: 요청 후 상태와 안전·불안전 관계를 판정
- `LU-19`: 가상 승인 후 사이클 형성 여부에서 승인·거부를 판단

특히 `LU-09`는 세 가지 조건부 결론을 각각 카드로 만들었다.

1. 사이클 없음 → 데드락 아님
2. 사이클 있음 + 단일 인스턴스 → 데드락
3. 사이클 있음 + 다중 인스턴스 → 데드락 가능성

이 범위는 판정형 recall이 원문 경계조건을 보존하면서 실제 문제 적용을 연습하게 한 좋은 사례다.

### 3.2 사용 가능하지만 다소 억지인 사례

- `LU-01`: 데드락 정의를 직접 설명하게 하기보다 정의에 해당하는 상황을 제시하고 “데드락 상태”라는 명칭을 판정하게 했다.
- `LU-02~04`: 조건 이름을 보고 의미를 설명하는 대신 정의를 보고 조건 이름을 맞히게 했다.
- `LU-06`: 그래프 정점의 종류를 상황 문장으로 우회해 묻는다.
- `LU-17`: 회피에 필요한 사전 정보라는 사실을 상황형 문장으로 감쌌다.

이 카드들은 사실적으로 틀리지 않고 학습에도 사용할 수 있다. 다만 gold가 기대한 “용어 → 정의·설명” 능력보다 인식과 분류에 가까워졌다. 학습자가 데드락을 스스로 정확히 설명할 수 있는지는 Card 1만으로 충분히 검증되지 않는다.

### 3.3 다른 recall form이 더 자연스러운 사례

- `LU-01`: `데드락 → 정의 설명`
- `LU-06~08`: `그래프 표기·간선 방향 → 관계 의미`
- `LU-10`: `예방·회피·탐지 및 복구 → 개입 시점과 전제 비교`
- `LU-18`: `자원 이벤트 → 간선 전이 순서`
- `LU-20`: `탐지 및 복구 → 탐지 시점과 적용 범위`
- `LU-21~22`: `복구 방식 → 사이클을 해소하는 방법`

최종 Card 12는 `LU-10`에 대해 예방과 회피를 “데드락 진입 전에 막는 전략”으로 함께 답하게 했다. 이는 탐지 및 복구와의 큰 차이는 포착하지만 예방과 회피의 차이, 특히 회피의 사전 정보 요구를 이 카드에서 구분하지 못한다. `LU-17`이 사전 정보 요구를 별도로 다루므로 CardSet 전체에서 사실이 사라진 것은 아니지만, 전략 비교 단위의 학습 의도는 부분적으로만 구현됐다.

### 3.4 단일 design이 실제 품질 제약을 만들었는가

이번 run은 “모든 카드가 같은 strategy여야 한다”는 수준으로 고정되지는 않았다. 최종 카드의 strategy는 `concept`, `recognition`, `application`, `contrast`, `procedure`로 달라졌다. 즉 카드 생성 모델이 LearningUnit 성격에 따라 일부 지역적 조정을 수행했다.

그럼에도 전역 cue-target 문체가 모든 단위에 적용되면서 정의형 단위가 상황 판정형으로 바뀌고, 전략 비교가 큰 양자 비교로 압축되는 현상이 있었다. 따라서 단일 Recall Design은 이번 baseline에서 **치명적 실패는 아니지만 실제 적합성 손실을 만든 제약**으로 볼 수 있다.

다만 탐지·복구 카드 누락을 단일 Recall Design만의 결과로 단정할 수는 없다. 같은 run에서 hard card count와 1:1 규칙도 동시에 적용됐기 때문에 원인이 교란되어 있다.

## 5. LearningUnit별 또는 그룹별 Recall Design 가능성

현재 구조는 다음과 같다.

```text
전체 학습 범위
→ 전역 Recall Design 하나 선택
→ LearningUnit 추출
→ 동일한 cue-target 계약을 전체 카드에 적용
```

대안은 LearningUnit을 먼저 추출하고 지식 구조에 맞는 retrieval form을 선택하는 것이다.

```text
전체 학습 범위
→ LearningUnit 추출·분류
→ LearningUnit 또는 의미 그룹별 retrieval form 결정
→ 카드 생성
```

이번 baseline은 후자의 필요성을 일부 지지한다. 다만 22개 단위마다 완전히 다른 UI 선택을 요구하는 구조는 복잡도와 사용자 부담이 지나치게 크다.

### 5.1 검토 가능한 중간 구조

#### KnowledgeType별 Recall Design

- 장점: 이미 `concept`, `relationship`, `procedure`, `problem_solving_pattern` 분류가 있어 구현 경계가 명확하다.
- 한계: 같은 `concept`에서도 정의와 조건 판정은 적절한 recall form이 다를 수 있다.

#### 의미적으로 비슷한 LearningUnit 그룹별 Recall Design

- 예: 정의·조건, 그래프 해석, 예방 정책, 회피 판정, 복구 방법
- 장점: 이번 Deadlock 자료의 실제 학습 행동에 가장 자연스럽게 맞는다.
- 한계: 그룹 생성 품질과 그룹 수가 새로운 설계 변수로 추가된다.

#### 기본 Recall Design + 일부 예외 Override

- 기본은 현재 선택한 판정·근거 구조를 사용한다.
- 정의, 절차, 복구처럼 부적합도가 높은 단위만 다른 form을 허용한다.
- 장점: 현재 사용자 선택을 유지하면서 변경 범위와 복잡도를 제한할 수 있다.
- 한계: 어떤 단위를 예외로 볼지 판단 기준이 필요하다.

#### AI 추천 + 사용자 확인

- AI가 단위 그룹별 form을 추천하고 사용자는 소수 그룹만 확인한다.
- 장점: 사용자 통제와 자동화를 함께 유지한다.
- 한계: 이번 baseline 하나만으로 필요한 UI와 확인 수준을 결정할 수 없다.

현재 증거로는 **기본 Recall Design + 소수 예외 override** 또는 **의미 그룹별 design**이 가장 작은 대안 후보로 보인다. 이는 설계 후보일 뿐 production 정책 결론이 아니다.

## 6. 사전 LearningUnit 개수 고정 분석

### 6.1 현재 코드에서 개수가 강제되는 방식

이번 run에서는 다음 단계에서 22가 반복적으로 강제됐다.

1. WholeDocumentCorePlan이 영역별 예상 수 `5·4·5·5·3`과 총 22를 결정했다.
2. 합성 guideline의 `selectedGroup.itemCount`가 22가 됐다.
3. Recall Design instruction이 영역별 카드 수와 총 22장을 명시했다.
4. Prepare prompt가 `selectedGroup.itemCount`만큼 LearningUnit을 추출하도록 요구했다.
5. Cards JSON schema가 `minItems = maxItems = 22`를 강제했다.
6. Critic JSON schema도 카드 수 22를 유지했다.

따라서 `estimatedLearningUnitCount`라는 이름과 달리 실제 pipeline에서는 soft estimate가 아니라 exact contract로 작동했다.

### 6.2 Prepare에서 나타난 분할·병합 징후

Prepare의 22개 단위는 전반적으로 높은 품질이었지만 숫자에 맞춘 것으로 보이는 구조가 있다.

- `LU-05`는 순환 대기의 정의와 네 조건의 동시 성립 관계를 함께 담았다.
- `LU-09`는 사이클 없음, 단일 인스턴스 사이클, 다중 인스턴스 사이클이라는 세 판정을 한 LearningUnit에 담았다.
- `LU-11`은 예방의 기본 원리와 상호 배제 제거의 한계를 한 LearningUnit에 합쳤다.
- `LU-15`는 안전 상태 정의와 요청 승인 기준을 함께 담았다.
- `LU-19`는 단일 인스턴스 승인 판단과 다중 인스턴스 Banker 알고리즘 경계를 함께 담았다.
- 반대로 요청 간선과 할당 간선은 `LU-07`, `LU-08`로 나뉘었다.

특히 gold/reference는 예방 기본 원리와 상호 배제 제거 한계를 별도 의미 단위로 둔다. `LU-11`에서 두 내용을 합친 뒤 카드 단계에서 다시 두 장으로 분리된 것은 LearningUnit 경계가 카드의 실제 retrieval target 경계와 맞지 않았다는 직접적인 징후다.

### 6.3 Cards에서 확인된 실제 왜곡

Card generator는 “LearningUnit 하나당 카드 하나”라는 prompt 규칙을 따르지 않았다.

- `LU-09` → 3장
- `LU-11` → 2장
- `LU-20~22` → 0장

총 카드 수 22를 지켜야 했기 때문에 앞쪽의 복합 LearningUnit을 여러 장으로 펼친 수만큼 뒤쪽의 탐지·복구 단위를 제거한 결과가 됐다. 이는 다음 위험이 실제로 발생한 사례다.

- 총 개수 일치가 의미 coverage보다 우선됨
- 하나의 복합 LearningUnit이 여러 카드로 분해됨
- 다른 필수 LearningUnit이 카드화되지 않음
- `LearningUnit 수 = Card 수`라는 계약이 실제 의미 구조와 충돌함

### 6.4 이번 run에서 나타나지 않은 문제

다음은 우려할 수 있지만 이번 Prepare에서는 명확히 확인되지 않았다.

- 숫자를 채우기 위해 메타데이터나 반복 요약을 LearningUnit으로 포함
- 세마포어 코드나 개별 그래프 배치를 불필요하게 암기 단위로 포함
- 원문에 없는 상세 알고리즘을 추가

즉 hard count가 항상 저가치 내용을 추가한 것은 아니다. 이번에는 주로 의미 단위의 병합·분할과 CardSet coverage 손실로 나타났다.

## 7. EstimatedLearningUnitCount 역할 비교

### A. 사전에 정확한 개수를 정하고 일치시킴

장점:

- 비용과 결과 분량을 예측하기 쉽다.
- UI 진행률과 사용자 기대를 안정적으로 만들 수 있다.
- 영역별 누락을 숫자 수준에서 빠르게 발견할 수 있다.
- 동일 입력 baseline 간 형식 비교가 쉽다.

단점:

- 의미 단위보다 목표 숫자에 맞춰 병합·분할할 수 있다.
- 1:N 카드가 필요한 단위가 생기면 다른 단위 coverage가 밀려날 수 있다.
- “22개 생성”은 충족하면서 탐지·복구 전체가 빠지는 이번 결과처럼 숫자가 의미 coverage를 가릴 수 있다.

이번 baseline은 A 방식의 단점을 실제로 확인했다.

### B. 영역별 대략적인 범위 또는 Soft Budget

예: 개념·조건 약 4~6개, 그래프 약 3~5개

장점:

- 중요도 기반 분포와 비용 예측을 어느 정도 유지한다.
- 자연스러운 LearningUnit 경계가 예상치에서 조금 벗어나는 것을 허용한다.
- 특정 영역의 과잉·과소 생성을 감시하는 신호로 사용할 수 있다.

단점:

- 범위의 상한·하한을 어떻게 정할지 추가 판단이 필요하다.
- 모델이 항상 상한을 채우거나 하한만 만드는 경향이 있는지 검증해야 한다.
- soft budget이 실제 prompt와 schema에서 다시 hard constraint로 변하지 않게 해야 한다.

이번 결과를 기준으로는 A의 통제력을 일부 유지하면서 의미 왜곡을 줄일 수 있는 가장 작은 비교 후보다.

### C. 사전 개수 없이 의미적 완결성으로 추출

장점:

- LearningUnit 경계를 학습 의도와 원자성에만 맞출 수 있다.
- 자료별 자연스러운 결과 수를 수용한다.
- LearningUnit과 Card의 1:1 여부를 별도 문제로 다룰 수 있다.

단점:

- 과도한 추출과 비용 증가 가능성이 있다.
- 과거 모델에서 나타난 “모든 내용을 카드화”하는 경향을 다시 통제해야 한다.
- run 간 카드 수 변동이 커져 비교와 사용자 예측이 어려워질 수 있다.

이번 WholeDocumentCorePlan의 선별 품질은 C 방식도 시험할 근거를 제공하지만, 한 번의 Deadlock run만으로 C를 production 정책으로 선택할 수는 없다.

## 8. LearningUnit과 Card 관계 분석

### 8.1 1 LearningUnit = 1 Card가 항상 옳은가

항상 옳지 않다. LearningUnit은 하나의 의미적 지식 또는 판정 규칙을 나타낼 수 있고, 그 규칙이 여러 독립 조건에서 다른 결론을 낼 수 있다.

`LU-09`는 하나의 상위 규칙인 “사이클을 자원 인스턴스 수와 함께 해석한다”를 담지만 세 개의 독립 retrieval target을 가진다. 이를 세 카드로 만든 것은 학습 행동 관점에서 자연스럽다.

1. 사이클 없음
2. 사이클 + 단일 인스턴스
3. 사이클 + 다중 인스턴스

Gold의 `LU-G03`도 이 세 조건을 하나의 의미 범위 안에 두므로, 이 경우 1:N 변환은 정상적인 구현으로 볼 수 있다.

### 8.2 LU-11은 왜 다른가

`LU-11`은 다음 두 대상을 포함한다.

- 예방의 기본 원리
- 상호 배제 조건 제거의 한계

두 내용은 관련은 있지만 서로 다른 질문으로 독립적으로 인출할 수 있다. 실제로 Cards 단계도 두 장으로 분리했다. Gold도 `LU-P01`, `LU-P02`로 구분한다.

따라서 `LU-11 → 2 Cards`는 자연스러운 1:N이라기보다 **LearningUnit 자체가 너무 크게 합쳐졌다는 신호**에 가깝다.

### 8.3 정상적인 1:N과 과대 LearningUnit 구분 기준

이번 사례에서 사용할 수 있는 개념적 기준은 다음과 같다.

- 여러 카드가 같은 상위 판정 규칙의 서로 배타적인 조건 분기인가?
- 각 카드를 합치면 하나의 조건표 또는 규칙 집합으로 자연스럽게 설명되는가?
- 카드마다 서로 다른 학습 의도와 독립된 근거가 필요한가?
- 한 카드만 맞혀도 나머지 카드의 답을 자동으로 알 수 있는가?

`LU-09`는 같은 판정 함수의 조건 분기에 가깝다. `LU-11`은 서로 다른 학습 의도를 가진 독립 대상에 가깝다.

따라서 LearningUnit 1개가 여러 카드가 되는 것을 전부 금지해서도 안 되고, 모든 1:N을 허용하면서 CardSet coverage를 확인하지 않아도 안 된다.

## 9. Pipeline 최초 오류 지점 분석

### Analyze

- 문서 구조, 핵심 주제와 예시 역할을 대체로 정확히 파악했다.
- 명백한 최초 오류 없음.

### WholeDocumentCorePlan

- Gold의 핵심 상위 범위를 모두 선정했다.
- 예시·메타데이터·반복 요약을 적절히 낮은 우선순위로 처리했다.
- 다만 `estimatedLearningUnitCount`를 exact count로 전달하는 구조적 위험이 시작됐다.
- 이 단계의 영역별 숫자 자체가 명백히 틀렸다고 단정할 근거는 없다.

### RecallDesign

- 판정형 단위에 적절한 option을 만들었다.
- 총 22장과 영역별 정확한 카드 수를 명시해 estimate를 hard contract로 강화했다.
- 모든 단위에 같은 cue-target 문체를 강제해 정의형 단위의 자연스러움을 낮출 위험을 만들었다.
- 아직 이 단계만으로 필수 범위가 누락된 것은 아니다.

### Prepare/LearningUnit

- 22개 모두 원문 근거가 있고 핵심 범위를 포착했다.
- `LU-05`, `LU-09`, `LU-11`, `LU-15`, `LU-19`에서 복합 단위 징후가 나타났다.
- 이는 hard count의 영향으로 의심되지만, 이 단계에서도 탐지·복구는 `LU-20~22`로 보존됐다.

### Cards

- 최초의 명백한 결과 실패 지점이다.
- `LU-09`와 `LU-11`을 총 5장으로 확장했다.
- 동시에 `LU-20~22`를 전부 누락했다.
- 총 22장 제약은 지켰지만 “학습 단위 하나당 카드 하나”와 핵심 coverage를 위반했다.

### Critic

- 카드 매핑과 수를 그대로 유지했다.
- Card 14의 `일반적으로 불가능하다`를 원문에 맞춰 `불가능하다`로 수정한 것은 적절했다.
- 그러나 `LU-20~22` 누락을 발견하거나 복구하지 못했다.
- 현재 Critic은 카드 수와 UI type을 유지하며 최소 수정하도록 되어 있어 CardSet coverage 복구에 구조적으로 약하다.

따라서 이번 run은 **범위 선정과 추출에는 전반적으로 성공했지만, Cards 단계에서 hard count와 1:N 변환이 충돌하면서 CardSet coverage가 실패한 run**이다.

## 10. A/B/C 위험 분류

분류 기준:

- A: 실제 baseline에서 이미 품질 문제를 만듦
- B: 이번 baseline에서는 큰 문제가 없지만 다른 자료에서 높은 위험이 보임
- C: 현재 증거만으로 문제라고 판단하기 어려움

| 항목 | 분류 | 근거 |
|---|---|---|
| 강제 집중 영역 선택 | **C** | 집중 영역 없이도 WholeDocumentCorePlan과 Prepare가 핵심 범위를 잘 선별했다. 이번 사례에서는 강제가 필요하지 않았지만 다른 자료까지 일반화할 증거는 없다. |
| 전체 LearningUnit에 단일 Recall Design 적용 | **A, 경도** | 정의형 단위가 상황 판정형으로 바뀌고 전략 비교가 압축되는 실제 적합성 손실이 있었다. 다만 factual failure나 전면 실패는 아니며 local strategy 변화가 일부 보완했다. |
| 사전 LearningUnit/Card 수 고정 | **A, 명확** | 총 22장을 맞추면서 `LU-20~22`가 누락됐다. Prepare에서도 일부 의미 단위 병합·분할 징후가 있었다. |

추가 구조 위험:

| 항목 | 분류 | 근거 |
|---|---|---|
| 개수 없이 완전 자유 추출 | **B** | 이번 plan의 선별력은 가능성을 보였지만 다른 자료에서 과다 생성이 재발할 수 있다. |
| LearningUnit마다 완전히 다른 Recall Design | **B** | 적합성은 높일 수 있지만 설계 복잡도와 사용자 부담이 크다. |
| 1:N Card 변환 자체 | **C** | `LU-09`처럼 정상적인 1:N과 `LU-11`처럼 과대 LearningUnit 신호가 모두 있어 일률적으로 문제라 할 수 없다. |

## 11. 현재 증거로 내릴 수 있는 결론

1. **Whole-document-core 범위 선정은 이번 Deadlock 자료에서 성공했다.** 과거의 균등·전량 카드화 경향은 plan과 prepare에서 나타나지 않았다.
2. **강제 집중 영역 선택은 이번 사례의 품질을 위해 필수적이지 않았다.** 선택적 override 가능성을 검토할 근거는 생겼지만 일반 정책을 바꿀 근거는 아직 부족하다.
3. **단일 Recall Design은 사실 정확성을 크게 해치지는 않았지만 학습 행동 적합성을 평탄화했다.** 정의, 비교, 절차, 판정이 모두 상황→결론 문체로 수렴했다.
4. **가장 명확한 구조 문제는 exact count다.** 총 수를 맞추는 동안 CardSet의 필수 의미 coverage가 사라졌다.
5. **LearningUnit 수와 Card 수는 동일한 개념이 아니다.** `LU-09`는 자연스러운 1:N이 가능하지만, 이때 다른 LearningUnit을 누락하지 않는 별도 coverage 기준이 필요하다.
6. **Critic은 이 유형의 실패를 복구하지 못했다.** 개별 카드 오류 최소 수정과 CardSet coverage 검증은 다른 책임이다.

## 12. 아직 결론내리면 안 되는 사항

- 집중 영역 선택을 production에서 제거할지 여부
- WholeDocumentCorePlan이 모든 과목과 긴 문서에서도 안정적인지 여부
- LearningUnit마다 서로 다른 recall form을 반드시 가져야 하는지 여부
- knowledgeType만으로 recall form을 충분히 결정할 수 있는지 여부
- exact count를 완전히 제거해야 하는지 여부
- soft budget의 적절한 범위와 상·하한
- 하나의 LearningUnit이 허용할 수 있는 최대 카드 수
- `LU-09` 같은 조건 분기를 하나의 LU로 둘지 여러 LU로 나눌지에 대한 일반 schema
- coverage 누락을 Critic이 수정해야 하는지 별도 CardSet 검사가 맡아야 하는지 여부
- 이번 한 번의 run에서 나타난 누락이 모델의 반복 가능한 경향인지 여부

## 13. 다음 최소 실험

다음 실험은 다른 변수를 바꾸지 않고 **hard exact count만 soft budget으로 바꾸는 동일 Deadlock 재실행**이 가장 작다.

- 같은 PDF
- 같은 whole-document-core 범위
- 같은 모델 설정
- 같은 `option-2`와 template variant
- 영역별 숫자는 정확한 장수가 아니라 대략적인 범위로 제공
- LearningUnit은 의미적 완결성으로 추출
- Card 수는 LearningUnit 수와 강제로 같게 두지 않음

비교할 핵심은 다음 두 가지뿐이다.

1. `LU-20~22`에 해당하는 탐지·복구 coverage가 최종 카드에 남는가?
2. `LU-09`, `LU-11`과 같은 복합 단위의 경계와 1:N 변환이 더 자연스러워지는가?

이 실험은 단일 Recall Design을 그대로 유지하므로, 결과 차이를 개수 고정 완화의 영향에 더 가깝게 해석할 수 있다.
